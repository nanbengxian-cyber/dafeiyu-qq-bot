# 77 · `[贴纸:装酷]` 为什么还能漏出来：`event.send()` 是一条没人管的出口

**日期**：2026-09-13
**改动**：`dsh-sticker` 1.0.1 → 1.1.0（新增出口兜底闸）
**触发**：群主报「还是会发贴图纸文字」

---

## 一、先说我查错了方向

群主报这个现象之后，我把**全量日志里 15350 条机器人发出的正文**扫了一遍，
`[贴纸` / `[表情` / `[sticker` / `[图片:` / `[语音` **各 0 次**，
于是我的结论是「复现不出来，需要你给我一个具体例子」。

群主给的例子是：

```
叫谁臭鱼呢，找禁言是吧[贴纸:嘲笑]
```

我去日志里搜，还是搜不到。**差一点就把它当成群主凭印象编的例子**。
幸好我又搜了一遍「引用消息」——真语料在群里躺着：

```
00:52:39  怪企鹅(下线版): [引用消息(大肥鱼: 零基础上太空？先学会在群里别被禁言吧[贴纸:装酷])] [At:3752949000] 教我零基础上太空
00:53:29  怪企鹅(下线版): [引用消息(大肥鱼: 零基础上太空？先学会在群里别被禁言吧[贴纸:装酷])] [At:3752949000] 我有被禁过吗
```

**群友把机器人那条话引用回来了，引用块里带着 `[贴纸:装酷]`。**
标记真的发出去了。而 `零基础上太空？先学会在群里别被禁言吧[贴纸:装酷]`
这串文字在**全量日志里只出现在这两条引用里** ——
它从来没有作为一条出站消息被记录过。

**这两件事同时成立，只有一个解释：这条消息没走 `respond.stage`。**

---

## 二、根因：两道装饰钩子只覆盖「走管道」的那条链

`dsh-sticker` 在 v2.0 已经修过一次同类泄漏，它的注释里记着当时的现场：

```
#     14:01:11.667 Prepare to send … 得嘞，这就把群主画飞[贴纸:嘲笑]  ← 漏了
```

**注意 `Prepare to send` 里有它。** 那次的泄漏是"管道内的顺序问题"
（`event.send` 抛异常 → 赋值被跳过 → 标记原样进群），v3 用「先剥、后发」
修好了，而且**修好之后 `Prepare to send` 里再没出现过标记**。

但这次的泄漏在 `Prepare to send` 里**看不到**。区别就是：

| | 谁管 | 这次 |
|---|---|---|
| `on_llm_response` | dsh-sticker | 只管**走管道**的最终回复 |
| `on_decorating_result` | dsh-sticker | 只管**走管道**的结果链 |
| **`event.send()`** | **没人管** | ← **这次走的是它** |

`event.send()` 是**平台直发**：不过装饰钩子、不过 `respond.stage`，
拿到什么链就发什么。实测现在至少有 5 个插件在用它
（`dsh-welcome`、`dsh-imagegen`、`dsh-video`、`dsh-guard`、`dsh-poke`），
**以后每加一个用它的插件，就是一条新的漏法。**

`dsh-initiate` 的头注释里其实早就写过这个坑，只是当时针对的是**另一个**绕法：

```
# dsh-welcome 当初直接调 llm_generate，绕过了管道，结果 dsh-sticker 的
# on_llm_response 钩子不触发，模型输出的 `[贴纸:探头]` 原样漏进群聊。
# 凡是绕过管道的地方，贴纸剥离、分段回复、@ 策略都得自己复制一份。
```

「凡是绕过管道的地方都得自己复制一份」—— 这就是问题所在：
**每绕一次就要复制一份，早晚有人忘。** 与其继续一个一个补，
不如把补丁挪到绕不过去的地方。

## 三、修法：唯一绕不过去的那个点

所有出站路径最终都汇到 `AstrMessageEvent.send`（`astr_message_event.py:478`）。
把类方法包一层：

```python
_ORIG_SEND = AstrMessageEvent.send

async def _guarded_send(self, message, *args, **kwargs):
    try:
        guard_outgoing(message)      # 复用同一个 strip_markers 纯函数
    except BaseException:
        pass                          # fail-open
    return await _ORIG_SEND(self, message, *args, **kwargs)

if not getattr(AstrMessageEvent.send, "_dsh_sticker_guard", False):
    _guarded_send._dsh_sticker_guard = True
    AstrMessageEvent.send = _guarded_send
```

三条设计约束，每条都有理由：

1. **只剥、不改别的。** 复用同一个 `strip_markers` 纯函数 —— 兜底闸的行为
   必须和另两道钩子**逐字节一致**，否则就成了第三个真相来源。
   只碰 `Plain`，图片/At/Reply 一律不碰。
2. **fail-open。** 这一步抛任何异常都照原样发出去。宁可漏一个标记，
   也绝不能因为兜底闸自己出问题而把消息吞掉 —— 吞消息比漏标记严重得多。
3. **剥到东西就 WARNING 一次，把原文和剥后文本都打出来。**
   这条日志是**证据**，不是噪音：下次再有人报「发出标记了」，
   直接搜 `出口兜底剥标记` 就知道是哪条路径、哪句话漏的。
   修完还留着未知（见第六节），所以必须让它自己开口。

同时把 `send_streaming` 也包了 —— 见第五节，第一版包错了。

## 四、测试（`test_outbound_guard.py`，8 节）

1. **生产里真漏出来的那条**：`零基础上太空？先学会在群里别被禁言吧[贴纸:装酷]`
   → 剥成 `零基础上太空？先学会在群里别被禁言吧`。
2. 5 条干净文本（含 `[At:3752949000] 在吗`、`1+1=2`、`这个 [不是标记] 是方括号`）
   零改动 —— 别误伤别的方括号写法。
3. **只碰 Plain**：图片组件对象本身不变（`is` 比较），文字剥干净。
4. 非链对象（`None`/`str`/`int`/`object()`/空链）都不抛。
5. `AstrMessageEvent.send` 和 `send_streaming` 都真的带上了 `_dsh_sticker_guard` 标记。
6. **端到端**：把 `_ORIG_SEND` 换成记录器，真的调一次
   `AstrMessageEvent.send(...)`，断言**平台真正收到的**文字已经剥干净、
   返回值原样透传。
7. **兜底闸自己坏了也不能吞消息**：让 `guard_outgoing` 故意抛异常，
   断言消息照发（只是这次没剥）。
8. **重复装载不套娃**：`importlib.reload` 之后再断言 `send` 还是同一个包装
   （不然日志会出现多层，排查时看不到真实层数）。

## 五、我自己这个修复里的一个地雷

第一版我是这样包的：

```python
async def _guarded_send_streaming(self, message, *args, **kwargs):
    guard_outgoing(message)
    return await _ORIG_SEND_STREAMING(self, message, *args, **kwargs)
```

**是错的。** `send_streaming` 的第一个参数不是链：

```python
async def send_streaming(self, generator: AsyncGenerator[MessageChain, None], ...)
#                        ^^^^^^^^^ 异步生成器
```

对着生成器调 `guard_outgoing` 只会 `getattr(gen, "chain", None)` 拿到 `None`
然后返回 0 —— **等于没装，而且不会报错**。这个错误今天完全看不出来，
因为**本部署流式是关的**（全局 `streaming_response = False`，没有任何 provider
打开，日志里 0 处流式痕迹）。哪天有人为了降延迟打开流式，这个闸就会静静地不管用。

正确写法是包住生成器本身：

```python
async def _guarded_gen():
    async for chain in generator:
        guard_outgoing(chain)
        yield chain
```

**教训：包装一个不熟悉的函数之前，先去读它的签名。**
「不报错」和「起作用」在 monkey-patch 里长得一模一样 ——
这跟第 76 篇那个「0 次注入」是同一类错误：**没触发 ≠ 没问题**。

## 六、还没有答案的部分（诚实记账）

**具体是哪条路径发的，我不知道。**

我能确定的只有「它没走 `respond.stage`」，因为那串文字在全量日志里只出现在
群友的引用里。可能的具体路径有：某个插件的 `event.send()`、
`send_message_to_user` 内建工具（它也是直接 `event.send`，不过全量日志里
`send_message_to_user` 出现 0 次，暂时排除）、或者我还没读到的第三条路。

**我没有继续往下挖，是权衡过的**：出口兜底闸装在**所有**路径的汇合点上，
所以「是哪条路」已经不影响修复效果了；而兜底闸每次触发都会 WARNING 打出原文，
**下次它自己会告诉我们是哪条路**。用一次未知换一个不会再漏的修复，划算。

顺带修正我之前一个过强的结论：我说过「空文本的 `Prepare to send` 行 100% 是
幻影（沉默/回戳）」。**太重了。** 有些空行其实是「正文通过 `event.send`
在外面发出去了，`respond.stage` 拿到的是空链」—— 泄漏那会儿正好有一条
空行。以后看到空行要先分一次类，别一律当幻影划掉。

## 七、这一轮真正的教训：测量口径的覆盖范围

我这轮差点犯的最大错误，是把「我扫了 15350 条，0 次」当成「它不存在」。
**那 15350 条本身就是有偏样本** —— 它只统计了 `respond.stage` 打印的行，
而 `respond.stage` 恰恰不覆盖出事的那条路。我拿一个有盲区的尺子量了半天，
量出「0」，然后反过来怀疑用户看错了。

正确的读法是：**用户说看见了 + 我量出 0，先怀疑尺子，再怀疑用户。**
具体动作就是去问「我的样本是怎么来的、它能覆盖哪些情况、覆盖不到什么」——
这次一问就发现，`Prepare to send` 只覆盖走管道的那部分。

所以在文档里、也在插件注释里写下的规则是：

> 报「XX 从来没发生过」之前，先说清这条结论的**样本来自哪一行日志**，
> 以及**哪一类情况根本不会留下那一行**。
