## 一、NapCat 网页「老是连接不好」——根因不是网络，是少了个路径前缀

### 症状与误导

用户描述的是「连接不好」，很容易往网络/隧道方向查。实际是**每个子请求 404**。

### 根因

实例的 WebUI 只监听服务器的 `127.0.0.1:<实例端口>`，手机必须经管理服务
`/proxy/<实例名>/` 转发。但 NapCat 的网页是 React 应用，**用绝对路径引资源**：

```html
<link rel="icon" href="/webui/favicon.ico" />
<script src="/webui/assets/index-CaeQ89K8.js"></script>
```

WebView 于是去请求 `http://127.0.0.1:<隧道端口>/webui/assets/...`，
而管理服务上那条路径是 404（它只认 `/proxy/<实例名>/webui/...`）。
结果：HTML 出来了、JS 和 CSS 全 404 → **白屏或一直转圈**。

### 实测证据（远程测试服务器，实例 `api01`）

```
未改写 404  →  改写后 200   /webui/assets/index-BMxti49L.css
未改写 404  →  改写后 200   /webui/assets/index-CaeQ89K8.js
未改写 404  →  改写后 200   /webui/assets/qface-BZLvZXJ8.js
未改写 404  →  改写后 200   /webui/assets/react-hot-toast-cGcFZPSt.js
```

页面引用的每个资源都 404 → 200，与症状完全吻合。

### 修法

改写请求。但**必须两层**，只做一层会静默坏掉登录 —— 这是本轮最重要的发现。

#### 第一层：HTTP 层（静态资源）

`WebLoginActivity` 用 `shouldInterceptRequest` 拦截浏览器自己解析的资源
（HTML 里的 `src`/`href`），改写成带 `/proxy/<实例名>/` 前缀的地址。
前端代码一行不改。

要点：
- **只改路径**：主机部分一律丢掉（WebView 请求的主机不是真正要去的地方）；
- **查询串原样保留**：NapCat 有接口靠它传参；
- **不重复套前缀**：已是 `/proxy/` 开头就返回 null，否则会变成
  `/proxy/x/proxy/x/...`；
- **非 HTTP 地址不处理**：`data:` / `blob:` / `about:` / `javascript:`
  交给 WebView，别去代理；
- **直连模式（无隧道）完全不改**，保持原有行为。

#### 第二层：JS 层（页面自己发的 API 调用）—— 不能省

页面发的请求分两类，第二类**在 HTTP 层改不了**：

| 类型 | 例子 | 能否在 HTTP 层改 |
|---|---|---|
| 浏览器解析的资源 | `<script src="/webui/assets/x.js">` | ✓ 能（GET、无 body） |
| 页面 JS 发的 API | axios `baseURL="/api"` + `POST /auth/login {hash,totpCode}` | ✗ **不能** |

原因：**WebView 的 `shouldInterceptRequest` 拿不到 POST body**
（安卓公开 API 的限制，Google issue tracker 原文：
"There is nothing to read the body of this request"）。
硬在 HTTP 层拦，登录请求会变成**空 body** ——
页面能显示、但一登录就失败，而且看起来一切正常。

> 这是本轮我自己实现里的一个真实缺陷：写完第一层后我以为「拦截每一个请求」
> 就够了，直到去读 NapCat 的前端代码才发现登录是带 JSON body 的 POST。

所以第二层在**页面 JS 里**改地址：注入一小段脚本，包住
`XMLHttpRequest` / `fetch` / `EventSource`，把 URL 换成代理地址，
**body 原样交给真正的请求**（我们只换地址，不碰内容）。

```
var _o = XMLHttpRequest.prototype.open;
XMLHttpRequest.prototype.open = function (m, u) {
  try { u = fix(u); } catch (e) {}
  var a = [].slice.call(arguments); a[1] = u;
  return _o.apply(this, a);      // body 是后续 send() 传的，不经过这里
};
```

#### 注入时机：插进 HTML，而不是 evaluateJavascript

一开始我用 `onPageStarted` + `evaluateJavascript` 注入，但那是**异步**的 ——
可能在页面自己的脚本**之后**才执行，而页面脚本一执行就把
`XMLHttpRequest` / `fetch` 的原始引用拿走了，再包也没用。

改成在 `shouldInterceptRequest` 里**把脚本直接插进 HTML 的 `<head>` 之后**
（`WebProxyPath.injectIntoHtml`）—— 确定性最高，保证先于页面任何脚本执行。
`onPageStarted` 保留作为双保险（脚本是幂等的，重复注入无害）。

实测注入真实 NapCat 页面：脚本位置 44、页面脚本位置 1736 → 顺序正确。

另外把管理口令从 `Authorization` 挪到 `X-Dafeiyu-Token`
（`Authorization` 要留给 NapCat 自己的凭据）。

#### 另一个小 bug

初始加载地址原本是 `base + "/"`（即 `http://127.0.0.1:<端口>/`），
在管理服务上是 404 —— WebUI 的正确入口是实例的 `/webui/`。
改为经代理时直接加载 `/proxy/<实例名>/webui/`。

## 二、「API 不显示是否连通」——测试必须在服务器上做

新增两个接口 + App 两个按钮：

| 接口 | 作用 |
|---|---|
| `POST /instance/api/test` | 在**服务器上**发一次真实请求，返回分层结论 |
| `GET  /instance/api/models` | 拿地址和 Key 去问服务商要**当前**模型列表 |

### 为什么必须在服务器上测，不能在手机上

真正要用这个 API 的是服务器上的 AstrBot。**手机能连通而服务器连不上**
（境外 API、服务器没网、DNS 不同）是很常见的情况 ——
在手机上测会给出「通的」这个错误结论，用户就再也查不出机器人为什么不回话。

### 为什么分三层报结果

`reachable` / `auth_ok` / `model_ok` 分开说。混成一句「失败」，
用户不知道下一步该改哪里：地址错要改一个字母，Key 错要去官网重抄，
模型名错要从列表里挑 —— 三件事的修法完全不同。

### 真实聊天请求是唯一可信的判据

`/models` 的成功**不能**用来证明 Key 可用：实测 OpenRouter 的 `/models`
用**任何** Key 都返回 200（它不鉴权），但 `/chat/completions`
用同样的无效 Key 返回 401：

```
models  Key='sk-totally-invalid-key-x' -> HTTP 200  ← 无需鉴权也 200
models  Key=''                         -> HTTP 200
chat    Key='sk-totally-invalid-x'     -> HTTP 401  {"error":{"message":"Missing Authentication header"}}
chat    Key=''                         -> HTTP 401
```

所以最终判据是一次真实的 `max_tokens=1` 聊天请求（成本可忽略）。
只用 `/models` 会给出**假绿灯**：用户看到「通了 ✓」，然后发现机器人根本不回话 ——
比不做检测更糟，他会以为是别的地方坏了，查很久。

## 三、「没有获取默认模型的能力」

新增「获取可用模型」按钮：拿用户填的地址和 Key 去拉当前列表，弹窗点选。

### 为什么内置模型名只能当示例

模型名是这套东西里烂得最快的部分：

- `deepseek-chat` / `deepseek-reasoner` **已于 2026-07-24 官方停用**，
  旧名直接报错；当前是 `deepseek-flash` / `deepseek-v4-pro`；
- 通义千问、豆包、混元的模型名几个月换一茬。

> 本轮起草 `ApiGuide` 时，初稿就写了 `deepseek-chat` ——
> 正是这个陷阱。经查官方 Change Log 后改成当前名，并加了回归测试
> （`不含已停用的模型名 deepseek-chat`）。

所以设计上：内置名只作「大概是长这样」的提示，**真正的答案是让用户点按钮**。
这样 App 放半年也不会因为模型改名而失效。

## 四、「有些人不知道 API 怎么获取」——加强引导

新增 `ApiGuide`，引导页里放 8 家服务商的：

- 官方申请地址（点「去申请」直接开浏览器）
- 可直接填的接口地址（点「用这家」自动填好）
- 模型名示例
- **有坑的地方如实写出来**

### 地址都实测核实过

每个 `base_url` 都用**无效 Key** 打 `/models`，返回 401/403 才算数 ——
证明「地址真实存在」且「是 OpenAI 兼容鉴权端点」。这是防止
「编造申请地址、用户白跑一趟（注册→实名→充值→发现页面打不开）」最硬的手段。

```
DeepSeek   401 ✓     阿里百炼  401 ✓     智谱GLM  401 ✓     Kimi     401 ✓
硅基流动   401 ✓     火山方舟  401 ✓     千帆     403 ✓     OpenRouter 200（不鉴权）
```

申请页面也逐个 curl 过，8 家全部 200。

### 如实写出来的坑

| 服务商 | 坑 |
|---|---|
| 智谱 | 接口地址结尾是 `/api/paas/v4` **不是** `/v1` |
| 火山方舟 | ① 要先「开通模型服务」，只申请 Key 不够；② 通常要「创建接入点」并把接入点 ID 填到模型名那栏 |
| 阿里百炼 | 地址结尾的 `compatible-mode` 不能少，否则不是 OpenAI 兼容接口 |
| OpenRouter | 境外服务，国内服务器可能连不上（超时）—— 必须带警告 |
| 硅基流动 | 模型名带斜杠，要从它给的列表里复制 |

### 安全说明如实告知

阿里云官方文档明确警告「请勿在客户端代码（如浏览器、移动应用）或不可信环境中
配置或使用长期有效的 API Key」。我们确实是在手机 App 里让用户填 Key，
所以**必须如实告诉他**，并说清我们做了什么：

- Key 不存手机，只在保存时经加密隧道传到用户自己的服务器，写进 600 权限的文件；
- 建议为机器人**单独建一个 Key**，万一泄露去官网删掉即可，不影响别的服务；
- 建议给 Key 设**消费上限**。

隐瞒这个风险比风险本身更糟 —— 用户有权知道，然后自己决定用哪个 Key。

## 五、真机实测发现并修掉的 3 个 bug

这一轮的收获主要来自**把新接口部署到真机跑一遍**，而不是单测通过就收工。

### bug 1：域名写错 → 甩锅给「服务器网络」

把 `api.deepseek.com` 打成 `api.deepsek.com`，底层报：

```
<urlopen error [Errno 101] Network is unreachable>
```

和「服务器没网」**一模一样**。照字面翻译就是「检查服务器网络」——
把用户指去折腾服务器，而真正的问题只是少打了一个字母。

原因：域名写错时会解析到某个不相干的 IP（`deepsek.com` → `31.13.82.33`，
一个 Facebook 地址段），连过去自然 unreachable。

修法：连不上时先确认「别人能不能连通」——能连通说明问题在这个地址，
连不通才是服务器网络的问题。只在失败路径上多花一次探测。

```
修前：网络不可达 —— 服务器出不去，检查服务器网络。
修后：服务器能上网，但这个地址连不上 —— 多半是地址写错了。
      请逐字对照官网复制（常见的错：少一个字母、把 /v1 漏掉、结尾多了斜杠）。
```

### bug 2：响应体截断 → 把正常接口判成「不是 JSON」

`MAX_API_BODY` 原设 200000 字节，而 OpenRouter 的 `/models` 实测
**737075 字节**（444 个模型）：

```
完整长度 = 737075 字节
截断到 200000 后能否解析 JSON: 不能 -> Unterminated string starting at: line 1 column 199988
完整能否解析: 能
```

于是把一个**完全正常**的接口判成「对方返回的不是 JSON ——
这个地址可能不是 OpenAI 兼容接口」，用户会以为这家不能用，转头换一家。

这个 bug 只在「模型列表特别长」的服务商上出现，用一个小列表在本地测
**永远发现不了**。修法：上限提到 8MB，并加测试专门造一个 753790 字节的列表，
走真实的 `json.loads` 路径。

### bug 3：假绿灯（最严重）

见第二节 —— `/models` 不鉴权导致坏 Key 被判成「通了 ✓」。

```
修前：reachable=true auth_ok=true  message=通了 ✓ 模型 openai/gpt-4o-mini 可用。   ← 谎话
修后：reachable=true auth_ok=false message=Key 不对（对方返回 401）。检查有没有复制全、有没有多余空格。
```
