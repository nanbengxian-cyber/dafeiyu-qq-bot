# 69 · 两个把内部机制播进群的口子：文字版贴纸与语音假报错

- 日期：2026-09-13
- 现象来源：群主反馈「他有时候会直接发文字版贴纸，还有发出语音的时候他会说没有发出语音」
- 涉及插件：`dsh-sticker` 1.0.0 → **1.0.1**、`dsh-voice` 1.2.2 → **1.2.3**
- 生产备份：`/opt/qqbot/backups/dsh-sticker-pre-贴纸泄漏与语音假报错-20260912-164620/`、`/opt/qqbot/backups/dsh-voice-pre-贴纸泄漏与语音假报错-20260912-164620/`
- 镜像提交：`6333dec`

## 一句话结论

两个看起来无关的毛病，是**同一个根因**：QQ NT 内核的发送回执超时（`ActionFailed ... retcode=1200`）。

插件在「发媒体」这一步撞上它之后，都选择了把失败**说出来**——一个把标记原样当文字发进群，一个把自己发没发出去当口播念出来。真人不会汇报自己的故障码。

---

## 一、文字版贴纸：不是正则漏了，是顺序错了

### 现象

群主给的原话是：

> 乖宝宝这称号我自己都叫上了？[贴纸:装萌]就是类似这种的

群里收到的不是贴纸，而是把 `[贴纸:装萌]` 这个**内部标记原样当文字发出去**的消息。

### 先排除的假设

按常规思路先怀疑正则：

```
MARKER_RE = re.compile(r"[\[【]\s*(?:贴纸|貼紙|sticker)\s*[:：]\s*([^\]】]+?)\s*[\]】]")
```

覆盖了半角/全角方括号、`贴纸`/`貼紙`/`sticker`、半角/全角冒号、首尾空白。核对下来没有漏网：

| 检查 | 结果 |
|---|---|
| `grep -ah "\[贴纸" *.log \| grep -v "Plugin dsh-sticker"` | 0 条 |
| `grep "Prepare to send.*贴纸:"` 全量日志 | 0 条 |
| `未知贴纸名` 计数 | 0 |
| `${贴纸名}` 在 `data/stickers/` 的 18 个目录里 | 全部有效 |

两个钩子（`on_llm_response` 的 `stickerize` + `on_decorating_result` 的 `stickerize_fallback`）也都是**无条件剥**的。所以标记能漏出去，只能是这两个钩子**根本没执行到剥那一步**。

### 真因

`dsh-sticker` 1.0.0 的 `_handle()` 把两件事写在了一个函数里：

```python
async def _handle(event, text, where):
    markers = MARKER_RE.findall(text or "")
    if not markers:
        return None
    cleaned = MARKER_RE.sub("", text).strip()
    ...
    path = _resolve_sticker(tag)
    if path:
        await event.send(MessageChain(chain=[Image.fromFileSystem(path)]))   # ← 会抛
        _cooldown_remember(gid, tag)
    ...
    return cleaned
```

调用方是这样用的：

```python
cleaned = await _handle(event, text, "llm_response")   # ← 这里抛出去
if cleaned is not None:
    response.completion_text = cleaned                  # ← 永远执行不到
```

**剥标记是纯字符串操作、不可能失败；发图是网络动作、随时会失败。** 两者绑在一起，一旦 `event.send()` 抛 `ActionFailed(retcode=1200)`：

1. 异常从 `_handle` 里冒出去；
2. 被 `except BaseException` 吞掉，只留一行 `[贴纸] 处理失败`；
3. `response.completion_text = cleaned`（以及兜底钩子里的 `comp.text = cleaned`）**整个被跳过**；
4. 标记原样进群。

日志里这条失败是真实存在过的，而且不罕见：

```
[2026-09-09 20:21:39.639] [ERRO] [dsh-sticker.main:276]: [贴纸] 处理失败: <ActionFailed status='failed', retcode=1200, ...>
```

09-06 ~ 09-09 合计 **100+ 次**。

### 复现

用修复前的代码（`git show HEAD:plugins/dsh-sticker/main.py`）跑一遍同样的调用序列，`event.send` 一律抛 `retcode=1200`：

```
旧版 completion_text = '乖宝宝这称号我自己都叫上了？[贴纸:装萌]'
旧版 chain          = '这就来[贴纸:探头]'
旧版是否泄漏标记     = True
```

**和群主贴的那句话一字不差。** 这是根因确认，不是推测。

### 为什么日志里扫不到泄漏

主钩子失败后，兜底钩子的第二道防线**通常**能接住（`Prepare to send` 里看到的都是干净文本）。只有兜底也失手时才漏出去，而兜底确实会失手——日志里有：

```
[2026-09-10 13:02:25.703] [ERRO] [dsh-sticker.main:318]: [贴纸] 兜底处理失败: 'MessageChain' object is not iterable
[2026-09-12 09:58:51.146] [ERRO] [dsh-sticker.main:425]: [贴纸] 兜底处理失败: 
```

兜底自己的循环也是「先 `await _handle` 再 `comp.text = cleaned`」，`_handle` 一抛，赋值同样被跳过、循环也提前中止（后面的组件一起漏）。这解释了为什么是「有时候」。

### 改法（1.0.1）

把「剥」和「发」彻底拆开，并让剥的结果**先落盘**：

```python
def strip_markers(text) -> tuple[str, list[str]]:
    """纯函数：不碰网络、不碰 event，因此不可能失败。"""
    raw = text or ""
    return MARKER_RE.sub("", raw).strip(), MARKER_RE.findall(raw)


async def _send_markers(event, markers, cleaned, where) -> int:
    """**本函数绝不向外抛异常**：贴纸发不出去只是少一张图，
    绝不能连累调用方的文字处理。"""
```

- `stickerize`：先 `strip_markers` 并写回 `response.completion_text`，**之后**才尝试发图；
- `stickerize_fallback`：先 `comp.text = cleaned`，**之后**才尝试发图；
- `_send_markers` 里每次 `event.send` 各自 `try/except`，失败只记 `send_fail` 计数并 `continue`；
- `_maybe_auto_send`（自动补图）同样吞掉发送异常——它原先在兜底钩子末尾被调用，抛出去会把已经剥好的文字的收尾工作一起带走；
- 嵌套 `MessageChain` 由「拆不平就 `return`」改为**多挖几层**，实在挖不动就退化成把整段结果当成一段文本重写一遍（宁可只发文字，也不放标记出去）。

### 残留的第二条通道（已排查，结论：当前无风险）

装饰阶段里如果有插件在 dsh-sticker 之前**转发整条链**，标记同样会漏。逐个核对：

- 唯一的负优先级钩子是 `dsh-followup(priority=-900)`，它只**读** `result` 来记续聊上下文，**不调用任何 `event.send`**；
- 其余插件全是默认优先级 0 或更高（`dsh-noise` 100 / `dsh-typo` 200 / `dsh-humanizer` 300 / `dsh-aiflavour` 400）；
- 框架自己的分段发送在 `respond.stage` 里，晚于全部装饰钩子。

顺带一个副作用值得记一笔：`dsh-followup` 的 `outbound` 现在拿到的是**未剥标记**的文本（它在 −900 跑）。这不影响群，只让续聊相似度上下文里偶尔混进一个 `[贴纸:x]`。

## 二、语音假报错：群里刚听到语音，紧接着就被通知「没发出去」

### 现象

实测日志（2026-09-13 00:30）：

```
00:30:43.168 [voice] 悟声合成成功 voice=c88a920f 18字 128277B 13.2s
00:30:53.726 [WARN] [voice] QQ 发送回执超时，不自动重发（可能已送达）：
             <ActionFailed retcode=1200, message='Timeout: NTEvent .../NodeIKernelMsgService/sendMsg'>
00:30:53.739 [Core] Prepare to send - 怪企鹅(下线版)/3864614070:
             [At:3864614070]  这次语音没确认发出去：QQ 发送回执超时，可能已经送达；为避免重复语音未自动重发
```

触发场景是群友敲 `/说话 你身为AI，不能让别人占了你的便宜啊`。

### 为什么这句话必须删掉

1. **它多半是假的。** `retcode=1200` 是 NapCat 等 QQ NT 内核回执超时，不是发送失败。语音通常已经进群了。群友刚听完语音，紧接着看到一句「没确认发出去」，是**自己打自己的脸**。
2. **它是机制播报。** 「回执超时」「未自动重发」是内核和插件的内部词。`dsh-voice` 自己早就有这条原则——`_INFRA_REASONS` 那段的注释写着「只说给日志听，不给模型当口播素材」，理由一模一样：**机制绝不能变成口播**。这次只是漏在了命令路径上。

### 改法（1.2.3）

- `retcode=1200` / `nodeikernelmsgservice/sendmsg` 走新增哨兵 `RECEIPT_TIMEOUT`，语义改成「按已送达收口」；
- 命令路径见到哨兵**直接 `return`，一个字都不发**；
- LLM 工具路径见到哨兵按成功收口，回一句「语音已经发出去了」，不再让模型去说没发出去；
- 命令路径去掉 `这次语音没确认发出去：` 这个前缀——`err` 本身已经是给人看的一句话，前缀一加就变成机制播报；
- 新增 `_human_err()` 白名单：只有本来就写给人的几句话能原样进群，其余（如 `未配置 DSH_VOICE_API_KEY`、`Edge 返回空音频`、`未知错误`）一律换成 `这次声音没送出去，等一下再试试`，原文只进日志。

## 四、可复用的教训

1. **「不可能失败的操作」和「随时会失败的操作」必须分开，且前者先落盘。**
   剥标记 vs 发图、算字符串 vs 发网络请求。绑在一起时，后者的异常会静默回滚前者的结果。
2. **`except BaseException: logger.error(...)` 会制造看不见的数据损坏。**
   吞掉异常本身没错（插件不该炸框架），但必须在吞之前把「已经确定的结果」写出去，否则就是「日志里只有一行 error，群里却是错的」。
3. **不要把内部状态播报给用户，尤其是在这个状态多半不准的时候。**
   `dsh-voice` 里已经写过一次这条原则（`_INFRA_REASONS`），这次是在另一条路径上又犯了一遍——说明要按**出口**而不是按**模块**来审计「什么话会进群」。
4. **扫描日志找不到痕迹时，先怀疑观测层。**
   这次的结论能定下来，靠的不是 grep 日志，而是**用旧代码复现出用户的原话**。日志没记录 ≠ 没发生。
