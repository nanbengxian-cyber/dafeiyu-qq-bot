# 真人感第二批：黑话词表 · 打字节奏 · 同音错别字 · 注意力漂移 · 回复效果观察

> 2026-09-05。五项改动，四个新插件（`dsh-glossary` `dsh-drift` `dsh-typo` `dsh-effect`）
> 加一处框架配置。全部已在真群 100000001 上线，两个语料群维持完全静音。

这一批的出发点跟前面几批不同。前面修的都是**明确的故障**（答非所问、被骗认输、
认错人、崩溃）。这一批修的是「没有故障，但一眼能看出是 AI」—— 这类问题没有报错，
只能靠拿真人语料量出偏差在哪。

参考项目是 [MaiBot（麦麦）](https://github.com/Mai-with-u/MaiBot)，5882 星，
设计原则写得很清楚：**「最像而不是好」**。它的 `src/maisaka/` 和 `src/learners/`
是这个方向上最完整的开源实现。下面每一项都会写清楚**抄了什么、没抄什么、为什么**。

## 一、`dsh-glossary`：听懂群里的黑话

### 1.1 v1 的两个假命中，以及为什么假命中比不注入更糟

第一版是纯子串匹配。拿三个群 2478 条真语料回测，抓出两类错：

| 词条 | 误命中的原句 | 实际是什么 |
|---|---|---|
| `典` | 大肥鱼**经典**产生幻觉 | 「经典」，不是反讽梗 |
| `token` | `tokenhub.example.com` | 域名 |

这里的关键判断是：**假命中比不注入更糟**。不注入只是少给一点上下文；假命中是
主动告诉模型「群友现在在说反讽」，而人家在说域名 —— 等于喂错语境。

修法是三条结构规则，不是继续加词：

1. 每条词条带一组**排除上下文**（`avoid`）。命中前先把这些串从文本里抠成等长空格，
   位置不变，所以后面按位置排序的结果仍然是原句里的真实位置。
2. 链接整段先去掉。域名里带 `token` / `pro` / `ds` 太常见。
3. 纯拉丁/数字词条要求词边界。否则 `ds` 命中 `friends`、`666` 命中 `1666`。

还有一条容易忽略的：一次最多注入 4 条，按**在句子里出现的位置**排序取前几条，
不按词表顺序 —— 否则表里排在前面的冷词会挤掉句子真正在说的那个词。
（后来实测发现真语料里没有一句命中超过 4 条，这个闸门从没真正卡住过。）

### 1.2 为什么现成的热梗库都不能用

试过三个外部词库，全部拿本群语料回测：

| 词库 | 规模 | 在本群出现过 | 逐条看上下文后**真**命中 |
|---|---|---|---|
| `anime_memes_manual.md` | 192 条带释义 | 23 条 | **8 条** |
| `anime_memes_db.json` | 292 个裸词、无释义 | 14 条 | 不可用 |
| 小红书热词库 | 65 个词 | 1 条（「搭子」） | 1 条 |

第二个尤其说明问题：它命中最多的词是 **`15`**，对应的原句是「被蹲了 15 次」
「总 1500 刀」和一个 QQ 号。没有释义的裸词库根本没法用 —— 释义得人写，
因为**释义错了比没有更糟**（同 1.1 的道理）。

反过来，用 `tools/refresh_candidates.py` 挖本群自己的语料，判据是
**「这条短语被当成一整条消息发出来、且至少两个人发过」**：口头禅、梗、招呼语才会
被单独发出来当一整条消息，而「觉得」「直接」「视频」这类普通词永远不会。
一次就捞出「神了」「人机」「乐子」「何意味」「上号吧」「带带我」。

其中 **「神了」是全表命中最高的词（22 次 / 16 个不同句子），三个外部库里一个都没有。**

挖掘器的第一版走错了路，值得记下来：用 2~4 字 n-gram 按出现条数排序，
排最前面的是「，我」（94）「了，」（80）「吗？」（55）「觉得」「视频」——
30 行输出里一条可用的都没有，等于把筛选成本全推给人。换成「整条消息就是它」
这个结构信号之后立刻可用。

### 1.3 只给释义不够：模型听得懂「典」，但永远不会自己说「典」

v1 只注入释义，于是模型能理解群友说的「典」，但自己一次都没用过群里的说法。
这跟 `dsh-style` 当年的发现是同一件事：**给例子比给规则有效**
（人格里写「一句话 1~10 字」两周没用，注入 6 条真人短句立刻从 16.5 字降到 9.5 字）。

所以每条词条加了 `usage` 字段，一律是**真语料里的原话**。措辞沿用 `dsh-style`
那句「学怎么用、别照抄」。

三条刻意的取舍：

- `破甲` / `逆向` **只给释义不给例句**。例句会把「群里怎么聊这件事」变成可模仿的
  说法，而这两个词的原则是只听懂、不参与。
- `杂鱼` 的真语料全部冲着群主本人（「用日语说<群主昵称>杂鱼」），拿它当例句等于教模型
  对着人喊 —— 只留释义。
- 例句总长超预算就**整体**退化成只有释义，不让词表挤爆上下文。

### 1.4 审查结论：这个插件的价值在语用，不在词典

上线后做了一次自我审查，方法是**拿主模型（`deepseek-v4-flash-0731`，temperature 0）
逐条问这 43 个词在 QQ 群里什么意思**。结果：

**它一条都没说「不确定」，绝大多数直接答对。** 答错的只有 6 个：

| 词 | 模型说的 | 实际 |
|---|---|---|
| `专五` | 技能升到五级 | 专属武器第五档 |
| `典` | 经典/典型 | 反讽 —— **正是 1.1 里花力气排除的那个误读** |
| `破甲` | 打破防御 | 绕开模型限制的提示词 |
| `逆向` | 反着来 | 逆向分析接口 |
| `倍率` | 放大倍数 | 计费倍数 |
| `病友` | 同病相怜的人 | 群名来的自嘲 |

`典` 这条特别说明问题：模型自己的第一反应就是「经典」，跟我们在 `avoid` 里排掉的
假命中一模一样。

**所以释义本身大半是冗余。** 真正不可替代的是三样：答错词的纠正、模型推不出的
本群语用（`杂鱼` 是玩梗不是攻击、`人机` 是拿它开玩笑、`破甲` 不许照做）、以及例句。
按这个结论把「模型本来就懂」的释义压到最短，只在它答错处写明「不是 X，是 Y」。

一个必须注意的边界：这个探针是**单轮、零干扰、temperature 0** 的理想条件。
「模型在隔离条件下知道」不等于「模型在 40 轮群聊上下文里会正确调用」。所以是**压缩**
释义而不是删掉词条。

### 1.5 体积

| 指标 | 审查前 | 审查后 |
|---|---|---|
| 词条数 | 46 | 43（删掉零命中的 `满包` `架枪` `三连`） |
| 命中率 | 8.4% | **8.4%**（没变 —— 证明删掉的确实是死词） |
| 注入块中位长度 | 196 字 | **135 字** |
| 固定说明文字 | 103 字（占 53%） | **55 字**（占 40%） |
| 释义总字数 | 1205 | 984 |

固定说明文字比正文还多，是这次审查里最大的一处纯浪费。

### 1.6 一个已测量但决定不修的重叠

43 条例句里有 22 条同时落在 `dsh-style` 的候选池里，两个插件理论上会在同一轮
各贴一次同一句原话。算了一下概率：`dsh-style` 每轮从 328 条里挑 6 条，
单句撞上约 1.8%；词表 8.4% 的轮次命中、平均 1.3 条。三者相乘，
**期望是每 500 轮重复一次，代价几十个字符**。

为这个去做两个插件之间的耦合（互相传「这句我已经贴了」）不划算 ——
耦合的故障面比省下的字符值钱。记录下来，真要归零只需让例句都长过
`dsh-style` 的 `MAX_LEN=18` 字。

## 二、打字延迟：一行配置，而且原来的行为有时是反的

AstrBot 的分段回复本来就开着，但间隔用的是 `interval_method: "random"`，
固定 1.2~2.8 秒随机 —— **跟消息长度无关**。也就是说一条「典」可能等 2.8 秒才发出来，
一条二十字的可能 1.2 秒就出来了，跟人打字完全相反。

框架其实自带按长度算的模式，我们没开（`core/pipeline/respond/stage.py:100`）：

```python
if self.interval_method == "log":
    if isinstance(comp, Comp.Plain):
        wc = await self._word_cnt(comp.text)
        i = math.log(wc + 1, self.log_base)
        return random.uniform(i, i + 0.5)
    return random.uniform(1, 1.75)
```

改成 `log` 之后（`log_base` 保持默认 2.6）：

| 消息长度 | 改前 | 改后 |
|---:|---|---|
| 1 字 | 1.2~2.8s | **0.73~1.23s** |
| 8 字（本群真人中位数） | 1.2~2.8s | 2.30~2.80s |
| 20 字 | 1.2~2.8s | **3.19~3.69s** |
| 40 字 | 1.2~2.8s | 3.89~4.39s |

核对过发送循环（同文件 :270）：间隔在**每一段之前**都会 `sleep`，包括第一段。
所以短回复现在反而更快出来 —— 这正好也更像人，脱口而出的短话来得快。

MaiBot 用的是线性模型（`calculate_typing_time`：中文 0.3 秒/字、英文 0.15 秒/字、
单个汉字 ×3、末尾加 0.3 秒回车、emoji 固定 1 秒）。没照抄，因为框架自带的对数模型
已经够用，而且改配置比加代码可靠。

## 三、`dsh-decide` 新闸门：有人在跟别的 AI 说话就不抢话

真人不会去接别人对着另一个助手说的话。MaiBot 有个
`OTHER_ASSISTANT_ADDRESSEE_PATTERN` 做这件事，直接抄会出事。

按它的写法（名字后面允许跟空格），拿 1899 条真语料一跑，**两条误伤**：

```
gpt progpt plus
gpt pro的缓存差不多95%左右
```

本群成天在聊模型，`GPT`、`ds` 这些词本身就是**话题词**（「ds后训练后甲上来了」
「掺ds了」「我说什么时候来DSv5」）。所以收紧了两处：

1. **分隔符只认标点，不认空格。** 中文喊人是「DeepSeek，」「豆包：」；
   「gpt pro」用的是空格。这一条就把两条误伤都干掉了。
2. **名字不收 `GPT` / `ds` 这种太短太泛的写法。**

收紧后真语料假命中归零，而「DeepSeek，帮我写个正则」「豆包：这题怎么解」
「claude！你在吗」照样抓得到。

方向上选的是**宁可漏判，不可误闭嘴** —— 这个项目最初的抱怨就是「回复太少」，
误判沉默是往反方向走。

闸门位置有两边约束，都写进了注释并加了断言：

```
静音群  <  被@就放行  <  别的AI不抢话  <  明确要东西就放行
```

- 必须在「被 @ 就放行」**之后**：真被喊了就该答，哪怕他这句话里带着别的模型名。
- 必须在 `_ASK_RE`「明确要东西就放行」**之前**：「豆包，画张图」会命中 `_ASK_RE`，
  放行了就抢了豆包的活。

## 四、`dsh-drift`：允许它被支线勾走一下

### 4.1 问题

真人在群里不是一问一答：别人提到一个细节，他会顺着那个细节歪一句，再绕回来。
AI 的典型形状恰恰相反 —— 永远严格贴着上一条消息回答，一句多余的联想都没有。
**这种「过度切题」本身就是一种 AI 味。**

抄的是 MaiBot 的 `src/maisaka/attention_drift.py`：把漂移写成**分档的提示词**，
而不是让模型自由发散。做了 `subtle` / `active` / `scattered` 三档，
**没做它的 `wild` 档** —— 在真群里放开到「明显跑题」不值得赌。

### 4.2 两条硬边界（这个插件最重要的部分）

这个项目专门修过「答非所问」（根因是注入块堆进历史，不是模型想跑题，
见 [40-答非所问根因与修复](40-答非所问根因与修复.md)）。现在主动加漂移，
必须防止把那个抱怨重新引回来。所以定了两条**结构性**边界，不靠提示词自觉：

1. **只在「自己插话」的轮次漂移，被 @ 时绝不漂移。**
   被点名了还去接支线，那就是字面意义上的答非所问。
2. **当前消息像在提问时不漂移。**
   哪怕没 @ 谁，群里抛出来的问题也是等人答的；用联想去回答问题跟第 1 条是同一类错。

再加两道量上的保险：按概率触发（默认 35%，不是每轮都塞，否则「每次都联想」
成了新的机器规律），以及只在主群生效。

### 4.3 「吧」不是疑问助词

调提问正则时有个语言学上的决定值得记：第一版把句末「吧」也当疑问助词，
结果「但是svg这程度真的离谱了吧」「那这个应该也能用的吧」都被判成提问。

「吗/呢」是疑问助词，「吧」多数时候只是软化或表推测。去掉「吧」之后，
主群 1964 条里误判成提问的少了 60 条（18.3% → 15.2%），
**而那些句子没有一句是在问人**。

### 4.4 实际规模

```
够格漂移 48.8% ｜ 太短(<6字) 36.0% ｜ 像在提问 15.2%
48.8% × 35% ≈ 17% 的轮次会漂移
```

注入块 130 字，标签 `<attention_drift>`（小写+下划线，`dsh-ctxclean` 能结构性清掉
历史里的旧块，不会重演注入块堆积那个坑）。

## 五、`dsh-typo`：偶尔打个同音错别字

### 5.1 为什么不抄 MaiBot 的实现

MaiBot 的 `src/chat/utils/typo_generator.py` 用 `pypinyin` + `jieba` 字频动态生成，
`error_rate=0.3`（每字 30%）。两条都没照抄：

1. **容器里只有 `jieba`，没有 `pypinyin`。** 为一个低概率的门面功能加依赖不值得，
   而且加了会在镜像重建时丢。
2. 更重要的是**可控性**：动态生成意味着输出集合是开放的，可能造出生僻字，或者恰好
   拼成另一个有明确含义（甚至难听）的词。这个号在一个 94 人的真群里说话，
   宁可要一张**每一对都人工看过**的表。

所以用的是手写的 60 组同音混淆表，收录标准三条缺一不可：

1. 真是同音或只差声调（拼音输入法会把它排进候选）；
2. 正确字在本群真语料里出现过（不然这条永远用不上）；
3. 错字一侧人工看过，不会拼成难听或有歧义的词。

按真语料词频排（是 407、的 378、有 224、没 187、就 159、要 144、好 139、他 124…），
高频字自然更容易被抽到。

### 5.2 概率怎么定

拿主群 1967 条真语料找人类的同音错别字，能确认的极少 ——
唯一明确的一条是「作者要**饿似**了」（饿死了）；另一条把某成员昵称改成谐音是故意玩梗，不算打错。
所以真人的错字率其实很低，MaiBot 的 30%/字 放到这里等于满屏错字。

定成 **每条消息 6% 概率、且一条最多错一个字**。实测约 **3.6%** 的消息会带错字。

真语料模拟出来的效果：

```
先点赞再说        → 先点赞在说        (再→在)
不是应该开学吗？    → 不是应改开学吗？    (该→改)
是最新发的表情包    → 是最新发地表情包    (的→地)
不行，我在偷笑     → 不行，我再偷笑     (在→再)
```

### 5.3 自我纠正，以及「\*西真」这个坑

打错之后按 35% 概率补一条「\*的」。第一版想凑成「\*很好」这种更自然的形状，
顺手把前一个字也带上，结果「这个东西**真**的很好用」错在「真」上时，
补出来的是 **「\*西真」** —— 前一个字来自「东西」，跨了词边界，纯属噪音。

改成只补那一个正确字。真人本来就常常只补一个字：「\*的」「\*很」。

### 5.4 三条硬规则

- **保护名单 48 条，一个字都不许动**：所有黑话词条、人名、群内称呼、贴纸标记、
  CQ 码、链接、@、数字和拉丁串。把「新赛季」写成「心赛季」不是拟人，是制造混乱。
- **只改模型生成的回复。** 指令回显（`/黑话状态` 之类）是给人看的清单，
  错一个字就变成误导。
- **纠正消息只在框架分段回复开着时才发。** 关着的时候同一个 chain 里的两个 `Plain`
  会被拼进同一条消息，变成「狠好\*很」—— 比不改还差。
  这条坑是 `dsh-human` 踩过并写下来的。

## 六、`dsh-effect`：说完之后看群里什么反应

### 6.1 为什么这是最大的缺口

在这之前，这个项目做的每一件事都是**开环**的：注入真人短句样本、注入黑话释义、
注入漂移档位，然后祈祷。说出去的话到底有没有落地，系统完全不知道。

真人不是这样的：讲了个笑话没人接，下次就不那么讲了。**这个「说完看反应」的回路是
真人感的分水岭，也是唯一能让它自己变好的机制。**

### 6.2 分类维度（抄 MaiBot，因为设计得确实好）

参考 `src/maisaka/reply_effect/`（`judge.py` / `scoring.py` / `tracker.py`，
`EVALUATION_VERSION=6`）：

| 维度 | 取值 |
|---|---|
| 群里的反应 | 认可 / 跟着玩 / 平淡接着说 / 没看懂 / 指出说错了 / 嫌烦 / **没人理** |
| 反应冲着什么 | 它说的内容 / **它的说话方式和人设** / 话题本身跟它无关 |
| 这句话的作用 | 推进了 / 维持住 / 收尾 / **带偏了** |
| 它用了什么策略 | 回答 / 表达看法 / 开玩笑接梗 / 反问 / 共情 / 应一声 |

三个加粗的是最有价值的：「没人理」是真群里最常见的结果（MaiBot 靠窗口逻辑处理，
这里显式建模）；「冲人设」和「冲内容」必须分开，因为改法完全不同；
「带偏了」是唯一能发现「话说得漂亮但把话题搞死了」的信号。

### 6.3 观察窗口是免费的

这一点是本项目的结构红利：`dsh-memory` 已经把群里每条人类消息写进
`dsh_memory.db` 的 `buffer` / `archive`。所以「它说完之后群里说了什么」不需要额外采集，
按时间戳查就有（`ts` 是 epoch 秒）。

窗口内**一条人类消息都没有**时，结论直接就是「没人理」，**不花一次模型调用**。

一个必须自己解决的问题：**机器人自己的话不在那两张表里**（实测 `buffer` 里
`group_id=100000001` 的机器人消息 0 条）。所以它说了什么必须自己在
`after_message_sent` 里记下来。

结果写独立库 `/AstrBot/data/dsh_effect.db`，不往 `dsh_memory.db` 里加表 ——
那个库是 `dsh-memory` 的资产，多一张表就多一处互相踩的可能。

### 6.4 这一版只测量，不自动改行为

这是刻意的。拿一个还没验证过的信号去自动调机器人的行为，等于在没有仪表的情况下
拧旋钮。先积累几百条真实评分，人看过分布之后再决定怎么闭环 ——
最可能的第一个闭环点：**「没人理」比例长期偏高就压低主动回复率**。

所以本插件不碰任何回复路径、不注入任何东西到上下文，只写自己的库。
把它关掉对机器人的行为零影响。

### 6.5 端到端验证怎么做的

单元测试只能验证解析器（重点是**脏输出绝不能写进库**：模型给
`"stance": "很棒"` 这种不在枚举里的值时退回安全值）。真正证明链路通的是这一步：

往库里插一条 `due` 已过期的记录，窗口指向一段真实历史，然后等后台 60 秒节拍自己结算。
结果：

```
[effect] #1 表达看法→平淡接着说（跟它无关，无）｜后续无人接大肥鱼的话，转而讨论使用顺序
```

后台循环取记录、读到 8 条真实反应、调 `context.llm_generate`、解析成干净枚举、
写库、打中文日志 —— 整条链路一次跑通。另外拿 4 段真历史单独验过分类质量，
4/4 全解析成功、全是裸 JSON，判断合理（正确识别出「没人理」和「群友转去聊别的」，
没有一味给好评）。

## 七、这一批新学到的教训

前面几批的七条教训见 [根 README](../README.md#反复踩到的七个坑)，仍然全部有效。
这一批新增四条：

8. **自己群的语料 > 任何现成词库。** 三个外部热梗库合计 549 个词，在本群真命中 9 条；
   本群语料一次挖掘就贡献了全表命中最高的词。有效的结构信号是
   「这条短语被当成一整条消息发出来、且至少两个人发过」。

9. **先问模型知不知道，再决定要不要教它。** 43 个词逐条问下来，绝大多数它本来就懂 ——
   这直接改变了插件的定位：从「词典」变成「语用层」，释义压到最短，
   力气花在模型答错的 6 个词和它推不出的本群惯例上。
   没做这次探针，就会一直在维护一张模型不需要的词典。

10. **抄参考实现的判据必须重新回测。** MaiBot 的「别的 AI 被喊」正则原样搬过来，
    在本群有两条假命中，因为本群的话题恰好就是模型本身。同理它的 30%/字 错别字率
    放到这里等于满屏错字。**参考实现给的是思路，阈值和边界必须拿自己的语料重定。**

11. **加「更像人」的功能时，先想清楚它会不会把已修的 bug 引回来。**
    注意力漂移和「答非所问」是同一个方向上的两端。所以漂移的两条边界
    （被 @ 不漂移、像提问不漂移）是**结构性**的，不是提示词里的一句提醒。

## 八、指令与旋钮

| 指令 | 权限 | 看什么 |
|---|---|---|
| `/黑话状态` | 群主 | 词条数、带例句数、命中率、最近命中的词 |
| `/漂移状态` | 群主 | 档位、概率、漂移了几轮、没漂移的原因分布 |
| `/错字状态` | 群主 | 错字率设定与实际、补纠正次数、最近打错的字 |
| `/回复效果` | 群主 | 反应分布、策略分布、哪种策略容易被接住 |

主要环境变量（完整清单见各 `main.py` 顶部）：

```bash
DSH_GLOSSARY=1                 # 黑话词表总开关
DSH_GLOSSARY_USAGE=1           # 例句开关（关掉退回纯释义）
DSH_GLOSSARY_MAX_HITS=4        # 单轮最多注入几条

DSH_DRIFT=1
DSH_DRIFT_RATE=0.35            # 漂移概率
DSH_DRIFT_LEVEL=subtle         # subtle / active / scattered

DSH_TYPO=1
DSH_TYPO_RATE=0.06             # 每条消息打错一个字的概率
DSH_TYPO_FIX_RATE=0.35         # 打错后补一条纠正的概率
DSH_TYPO_MIN_LEN=5             # 短于这个字数不碰

DSH_EFFECT=1
DSH_EFFECT_WINDOW=180          # 观察窗口秒数
DSH_EFFECT_TICK=60             # 后台结算节拍
DSH_EFFECT_BATCH=5             # 一轮最多结算几条
```

框架侧那一处配置（`cmd_config.json`，注意文件是 UTF-8 BOM）：

```json
"platform_settings": {
  "segmented_reply": {
    "interval_method": "log",
    "log_base": 2.6
  }
}
```

## 九、离线测试

四个插件都带纯函数单测，不需要跑起 AstrBot，也能在容器里跑：

```bash
python3 dsh-glossary/test_glossary.py   # 真命中 + 防假命中 + 注入块形状 + 说明文字不许膨胀
python3 dsh-drift/test_drift.py         # 两条硬边界 + 判定顺序 + 每档都带约束
python3 dsh-typo/test_typo.py           # 同音表自检 + 48 条保护名单一个字都不许动
python3 dsh-effect/test_effect.py       # 建库幂等 + 脏输出退回安全值 + 枚举完整
```

另有一个只出报告、不写任何文件的候选词体检脚本：

```bash
python3 dsh-glossary/tools/refresh_candidates.py [--no-net] [--top N]
```

它做两件事：把 B 站热搜/排行榜候选词跟本群语料对撞（一向 0 命中，这是正常结果），
以及从本群语料里挖「被当成一整条消息发出来」的短说法。**候选一律要人过目才能入表**，
脚本不会自动写词表 —— 释义错了比没有更糟。
