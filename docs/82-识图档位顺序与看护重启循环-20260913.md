# 82 · 识图档位顺序 与 看护重启循环（2026-09-13）

## 起因

群主问了两件事：

> 第一是他的回复怎么那么慢，第二他每次掉下线的间隔是多少，先帮我去查一下

查完两个都定位到了具体根因，也都修了。本文记录证据、修法和验收方式。

---

## 一、回复慢：根因是识图链的**档位顺序**，不是档位超时

### 1.1 先量清楚慢在哪

当天 157 次「@ → 发出」配对：

| 指标 | 全部 | 带识图(44条) | 不带识图(114条) |
|---|---|---|---|
| 中位 | 6.0s | **16.7s** | 4.5s |
| P90 | 21.0s | **35.4s** | 9.4s |
| 最大 | 61.0s | **61.5s** | 21.2s |

把带图回复按段拆开（44 条）：

| 分段 | 中位 | P90 | 最大 |
|---|---|---|---|
| @ → 首次 vischain 动作 | 5.8s | 11.9s | 17.9s |
| **vischain 内部跨度** | 5.2s | **27.0s** | **49.3s** |
| 识图结束 → 发出 | 3.2s | 13.2s | 17.4s |

结论：中位数里识图只占 5.2s，**但尾巴几乎全是识图**（P90 27s、最大 49.3s）。
群主感觉到「有时候特别慢」，就是这条尾巴。

### 1.2 单次识图调用本身只要 6.4s，78% 一次过

按 vischain 自己的日志统计当天 157 次识图调用：

- 78.3% **零失败一次过**；22% 需要至少一次重试
- 单次调用模拟中位 6.4s

也就是说识图链路本身是健康的，**钱花在「试错的空等」上**。

### 1.3 四档的真实战绩（这是关键）

| 档位 | 成功 | 超时失败 | 成功率 | 成功中位 | 白等秒数 |
|---|---|---|---|---|---|
| `zhipu-vision:glm-4.1v-thinking-flash` | 55 | 17 | **76%** | 5.6s | 157s |
| `vision-scnet` | 64 | 25 | **72%** | 6.1s | 250s |
| `zhipu-vision:glm-4v-flash` | 19 | 10 | 66% | 3.9s | 89s |
| `zhipu-vision`（glm-4.6v-flash） | 4 | 21 | **16%** | 8.8s | 210s |

**而当时的链条顺序是**：

```
vision-scnet → zhipu-vision(base) → glm-4.1v-thinking-flash → glm-4v-flash
      72%           16% ← 最差          76% ← 最好
```

成功率**最低**的那一档被钉死在第 2 位，卡在成功率**最高**的那档前面。
每次第 1 档超时（28% 的概率），都要先掏 10 秒去撞那个 16% 的档，才轮到真正能用的档。

原因是结构性的：`CHAIN` 只认纯 provider id，`MODEL_FALLBACKS` 一律追加在最后，
所以同一个智谱 key 上更好的模型档永远排在基础档后面。

### 1.4 顺便排除了两个「看起来该改」的方向

- **超时 10s 不能降**：成功调用的 P95 = 9.6s、P99 = 13.0s。
  降到 8s 会误杀 15.5% 的成功调用，降到 6s 误杀 41.9%。10s 这个值本身是对的。
- **`RETRY=1` 收益很低**：92% 的成功发生在第 1 次尝试；第 2 次尝试只多换来
  11 次成功，却付出 18 × 10s = 180s 的空等。属于「聊胜于无」，本次不动它
  （留着当韧性缓冲，且改它会影响全挂率）。

### 1.5 修法：让档位顺序成为一等公民

**代码改动**（`plugins/dsh-vischain/main.py`，补丁名 `order-v1`）：

1. `DSH_VIS_CHAIN` 支持 `pid:model` 写法，与纯 `pid` 混排，顺序即配置顺序；
   `MODEL_FALLBACKS` 保留（等价、不破坏老配置）。
2. **保序去重**：`MODEL_FALLBACKS` 有非空默认值，一旦把模型档也写进 `CHAIN`，
   同一模型会出现两次、被连撞两次白花一个超时。所以 `SPEC` 去重且保留首次位置。
3. `_ensure()` 的判据从「只比 CHAIN 里的显式 provider」改成
   **逐档比 `(provider, model)` 签名 + 核对活实例**（`_spec_of` / `_link_alive`）。
   旧判据在 model 档进 CHAIN 后会永远判不等 → 每 30 秒白重建一次链条。
4. 缺失档不再只打日志，也写进 `self.note`，`/识图状态` 能看到「缺失: xxx」
   （WebUI 删掉 provider 时链条会静默少一档，报喜不报忧会让人误判）。

**配置改动**（`/opt/qqbot/imagegen.env`）：

```diff
-DSH_VIS_CHAIN=vision-scnet,zhipu-vision
+DSH_VIS_CHAIN=zhipu-vision:glm-4.1v-thinking-flash,vision-scnet
+DSH_VIS_MODEL_FALLBACKS=zhipu-vision:glm-4v-flash,zhipu-vision:glm-4.6v-flash
```

新顺序（按成功率降序，最差的垫底）：

```
glm-4.1v-thinking-flash(76%) → vision-scnet(72%) → glm-4v-flash(66%) → glm-4.6v-flash(16%)
```

`vision-scnet` 仍在第 2 位，**provider 多样性没有丢**（两个上游都还在链上）。

### 1.6 效果（用当天真实成功/失败序列重排模拟 153 次调用）

| 档位顺序 | 总秒数 | 中位 | P90 |
|---|---|---|---|
| 原顺序 | 1340 | 6.4s | 18.0s |
| 新顺序 | **1240** | **6.1s** | **12.2s** |

**P90 从 18.0s 降到 12.2s（尾巴 -32%）**，中位基本不变。

## 二、掉下线：两件完全不同的事被混在一起了

### 2.1 AstrBot 每 2h00m~2h05m 重启一次 —— 看护脚本的自我循环

`journalctl -u qqbot-observe.service | grep autofix=True` 拿到 **15 次连续记录**，
间隔稳定在 2h00m~2h05m：

```
09-12 03:05:10  05:05:11  07:05:12  09:05:19  11:10:28  13:15:14  15:15:17
      17:20:16  19:20:19  21:25:19  23:30:53
09-13 01:35:19  03:40:20  05:45:16  07:45:19
```

根因在 `observe_watch.py`：

```python
elif st.get("patch_applied") and time.time() - last_patch > 7200:
    # 补丁在但仍复发（>2h 冷却），重启重试一次
    subprocess.run(["docker", "restart", "astrbot"], ...)
```

这条分支的意图是「补丁打过了问题还在，那就重启确认一下」。但**补丁已在位时
重启不会改变任何一行代码**，R1 自然不会因此消失 —— 于是它成了永动机：
24h 内 R1 照样 15 次，一次都没被它治好，净效果只有掉线。
每次重启在 `qq_watchdog` 日志里整齐对应 `online -> degraded -> online`，
收发通道断 **10~21 秒**。

### 2.2 修法：重启额度封顶

`observe_watch.py`（补丁名 `r1-restart-loop-v1`）：

- 决策逻辑抽成**纯函数** `r1_autofix(st, changed, fp, now)`，所有 docker 交互走
  `restart_astrbot()` —— 于是决策能在容器外单测，不用碰生产。
- **补丁首次应用**（`changed=True`）仍然重启：这一次是必要的，不能一起砍掉。
- **补丁已在位**时只给 `R1_RETRY_MAX`（默认 1）次「确认加载」重启，之后只告警。
- **老 state 迁移**：过去已经重启 15 次，迁移时额度直接记满，
  免得升级当天又白重启一次。
- **补丁换代检测**：用补丁脚本的 mtime+size 指纹判断换代并重置额度。
  只看 `patch_applied` 布尔量的话，补丁脚本将来升级了永远走不到「首次应用」分支。

### 2.3 QQ 账号真掉线 —— 这part没修，需要单独决策

同一天还有 5 次真掉线（`/var/log/qqbot-watchdog.log`）：

| 恢复时刻(CST) | 掉线时长 | 距上次 |
|---|---|---|
| 11:10:15 | **3小时57分35秒** | — |
| 14:36:56 | 4分57秒 | 7h20m |
| 15:46:34 | 7分53秒 | 1h07m |
| 15:53:55 | 34秒 | 14分40秒 |
| 16:17:19 | **21分19秒** | 2分39秒 |
| 16:38:44（部署后新发生） | 5分28秒 | 21分25秒 |

间隔完全不规律，越往后越密集。**15:53 那次的因果链最清楚**：

1. `15:53:51 qq-proxy-guard 隧道探活连续失败 2 次，摘除代理规则回到直连（fail-open）`
2. NapCat 开始刷 `Login Error, ErrType: 1  ErrCode: 3`，每 ~2 分钟一次、连刷 12 次
3. `二维码过期，重启 napcat 重新出码`
4. 16:16 容器里出现新 `qrcode.png` → 16:17:19 恢复 —— **这次是扫码救回来的**

qq-proxy-guard 一 fail-open，QQ 出口就从广州（电信）切到美国 `your-server.example.com`，
历史上这会触发 QQ 风控。**这条链路按约定只读检查，未做任何改动。**

| `test_ban_consec.py` / `test_model_fallback.py` / `test_failure_policy.py` | PASS |

`server/observe/test_r1_autofix.py`（新增，14 项，宿主机可直接跑）关键结论：

```
对照：同样「补丁在位且 R1 持续复发」30 天
   老逻辑重启 346 次（约每天 11.5 次，每次掉线 10~21s）   ← 与实测 12 次/天吻合
   新逻辑重启 1 次
```

### 生产验证

- 新档位顺序已生效（`已接管识图` 日志）：
  ```
  zhipu-vision:glm-4.1v-thinking-flash → vision-scnet
    → zhipu-vision:glm-4v-flash → zhipu-vision:glm-4.6v-flash
  ```
- 离线演练（stub 掉重启/邮件、状态写 /tmp）：跑真实日志，**0 次重启**；
  再模拟 30 天共 8640 次 tick，**0 次重启**。
- 生产 state 已按设计迁移：`patch_fp=1788748819-2384`、`patch_retry_used=1`、无重启。
- 探针 `{"online":true,"good":true}`。

### 部署动作与安全边界

- 改了 3 处：`plugins/dsh-vischain/main.py`、`/opt/qqbot/observe/observe_watch.py`、
  `/opt/qqbot/imagegen.env`。
- **env 是创建容器时注入的，`docker restart` 不重读** —— 所以 imagegen.env 的改动
  必须重建容器才生效。用的是
  `docker compose up -d --no-deps --force-recreate astrbot`，
  `--no-deps` 确保**完全不碰 napcat**；重建后核对 napcat 的
  `Created`/`StartedAt` 均未变。
- 全程未触碰：NapCat、QQ 出口、广州反向 SOCKS、`127.0.0.1:11080`、redsocks、
  QQPROXY、qq-proxy-guard/ip-guard、Tailscale、多模态默认配置。
- 重建 astrbot 造成的收发中断 21 秒（`08:44:51 degraded -> 08:45:12 online`），
  与原先每 2 小时自动重启一次的中断幅度相同。

### 回滚

```
/opt/qqbot/backups/vischain-order-v1-20260913-084341/
  main.py.bak              vischain 原文件
  imagegen.env.bak         原 env（旧档位顺序）
  observe_watch.py.bak     原看护脚本
  state.json.bak           原 state
```

回滚 env 后需同样用 `--no-deps --force-recreate` 重建 astrbot 才生效。

## 四、留待观察 / 未做

1. **17:45 前后的那个触发点**：旧逻辑下次该重启的时刻。已改掉，需确认届时不再重启。
2. **群主可见的收益取决于 QQ 出口稳定性**：识图档位顺序修好的是「识图这条尾巴」，
   但当天 5~6 次真掉线每次都断几分钟，那部分体感更重 —— 根因在出口链路，未动。
3. `RETRY=1` 的低收益（第 2 次尝试 38% 成功率、白花 180s）可以先记着，
   等积累几天数据再决定是否改成 0。
4. `_slow`/`_consec` 是**进程内存**，AstrBot 一重启就归零。
   修掉 2 小时循环后重启频率大幅下降，这个问题自然缓解；若后续仍需要，
   再把降权状态落盘。
