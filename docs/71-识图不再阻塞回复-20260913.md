# 71 · 识图不再阻塞回复：把「节奏不自然」从 25.8s 拉回 8.6s

**日期**：2026-09-13
**改动**：`dsh-imgctx` 1.1.0 → 1.2.0
**起因**：目标是"让机器人更像真人"，其中一项是**节奏不自然**。群主在群里说过
「除了速率太慢了，没有办法」——速度就是节奏，这是他自己点名的唯一一条。

---

## 一、怎么把"慢"归因到具体一段代码

只看总延迟没用，得先分组。上一轮造的口径在这里正好用得上：
`Prepare to send` 是**每条 result 一行**、组件用空格拼，所以拆开能直接对齐"这一轮回复"。

按「这一轮有没有夹识图」给被 @ 的回复分组：

| 分组 | n | 中位 | P90 |
|---|---|---|---|
| 没有识图 | 168 | **8.6s** | 52.7s |
| 识图成功并注入 | 54 | **25.8s** | 75.2s |
| 等满预算后放弃 | 1 | 43.8s | 43.8s |

**识图给被 @ 的回复加了约 17 秒。** 而且这些回复**全是纯文字**——有人 @ 了机器人，
打字间隙群里别人发了张图，机器人回一句跟那张图无关的话，却要先把图识别一遍。

再看整体账（09-04 起全部日志）：

```
识图调用 1808 次，累计 11528 秒（均 6.4s，中位 6.4s，P90 9.1s，最长 22.6s）
其中 65% 发生在「当前这条消息根本不是图」的轮次
imgctx 附加 1153 次，缓存命中率只有 31%
因超预算放弃 783 次 / 尝试 2117 次 = 放弃率 40%
```

**40% 的放弃率是最刺眼的**：那段路走了，时间花了，最后什么都没拿到——
因为 `BUDGET` 到点了，`wait_for` 抛 `TimeoutError`，本轮放弃注入。

顺带发现一处**配置与代码意图互相矛盾**：

```python
# 代码注释（第 28 行）
# 整个过程有总超时，超时就放弃注入而不是拖着回复不发——宁可这次没看懂图，
# 也不能让机器人半分钟不说话。
BUDGET = float(os.environ.get("DSH_IMGCTX_BUDGET", "15"))
```
```
# 生产 /opt/qqbot/imagegen.env（2026-09-12 16:57 改）
DSH_IMGCTX_BUDGET=24
```
注释写着"不能半分钟不说话"，env 却把上限设成 24 秒。日志里 24s 那档只出现 31 次
（15s 那档 752 次），是昨天傍晚改的。**这类"env 值悄悄背离代码注释写明的设计意图"
值得定期对一遍**——它不会有任何报错，只会让系统慢慢变慢。

---

## 二、根因

`_emit()` 里 `_caption()` 是**串行阻塞**的（串行本身有理由：智谱并发两张直接 429），
整条 `_run` 又套在 `wait_for(BUDGET)` 里。问题在于**它不区分这张图是哪来的**：

| 图的来源 | 回答当前这句需要它吗 | 原来的行为 |
|---|---|---|
| 当前消息自带的图 | 需要，回答就靠它 | 等 ✅ |
| 用户精确引用的图 | 需要 | 等 ✅ |
| 群里最近出现过、顺带的图 | **不需要** | 等 ❌ |

第三种在注入文案里本来就写明「不是当前这条消息自带的图片……如果和当前话题无关就忽略，
别刻意提起」。**为一条自己都标了"可以忽略"的上下文，把回复拖慢 17 秒。**

---

## 三、改法：按「这张图是不是本轮要回答的东西」分阻塞

```python
if rescue or quote_rescue:
    await self._caption(provider_id, items)     # 当前图/引用图：照旧等到转述完
else:
    cached = self._attach_cached(items)         # 历史图：只吃缓存，零网络请求
    self._warm(provider_id, items)              # 其余丢后台转述，本轮不等
```

- `_attach_cached()`：只把已在 `_caption_cache` 里的转述贴上，一个请求都不发。
- `_warm()`：没缓存的图起 `asyncio.create_task` 后台转述，**转述完照样写进缓存**，
  所以同一张图下一轮就是白拿。用 `_inflight`（key → Task）去重并兼作并发上限
  `DSH_IMGCTX_WARM=4`，防止有人连刷十张时无限起任务。
- 后台任务的 done 回调里**必须取一次 `t.exception()`**，否则 asyncio 在 GC 时会打
  「Task exception was never retrieved」白污染日志。

**为什么敢不等**：丢掉的只是"背景氛围"，而且只丢一轮——下一轮缓存里就有了。
换来的是回复快 17 秒。对"像真人"来说，这笔交易毫无悬念。

## 五、可复用的结论

1. **延迟要按"这一轮发生了什么"分组才有归因力。** 只看总中位数，永远只会得到
   "有点慢"；按「有没有夹识图」一分，立刻看出 8.6s vs 25.8s，直接指向一段代码。
2. **"高放弃率"是比"高耗时"更强的信号。** 40% 的尝试等满预算后一无所获——
   时间花了、结果没有，两头都亏。任何带 `wait_for` 的预算逻辑都该统计放弃率。
3. **env 值会悄悄背离代码注释写明的设计意图。** 注释说"不能半分钟不说话"、
   env 写着 24 秒。定期对一遍这类矛盾，它不报错，只变慢。
4. **`pkill -f <脚本名>` 会自匹配杀掉正在执行它的 shell。** 这个坑又踩了一次
   （第一次在更早的会话）。用 `pgrep -af "[w]atch"` 或 `pkill -f "[/]tmp/xxx"`
   这种不自匹配的写法。**这条要写进肌肉记忆。**
5. **容器内跑测试会污染生产日志，如果测试 import 了 `astrbot.core`。**
   上一轮的结论「从 /tmp 跑测试不会进生产日志」**不完整**：`import astrbot.core`
   会顺带初始化 AstrBot 的日志配置，把文件 sink 挂到
   `/AstrBot/data/logs/astrbot.log` 上。实测本次混进 2 行 `[ic.main:666]`。
   修法：import 之后 `from loguru import logger; logger.remove()`（独立进程，
   只影响自己）。已在 `test_blocking.py` 里加好。
   判断测试是否干净的**唯一可靠办法**：跑前跑后各数一次日志行数。

## 待办 / 未解决

- **后台预转述的收益要实测**：理论上缓存命中率应该从 31% 上去，同一张图第二次
  被引用时就能白拿。正在用 `/tmp/watch_imgctx.sh` 盯生产中
  `[imgctx] 历史图本轮不等` 与「已附加」的行数变化。
- `DSH_IMGCTX_BUDGET=24` 暂时**不改**：这一刀之后 24s 预算只作用于
  "当前消息的图/精确引用的图"，那是真的该等的场景。但要盯住——如果那两条路径
  的放弃率还高，说明 24 秒本身就该往下调。
- `_caption()` 的串行前提（"智谱并发两张会 429"）现在转述 provider 已经被
  `dsh-vischain` 换成 `vision-scnet` 了，**前提从未重新验证**。若 vision-scnet
  能并发，串行还能再省一半。需要单独做一次并发对照实验。
- `dsh-vischain` 生产与镜像不一致（见第四节），需要找时间跟用户确认哪边是最新，
  再决定是否同步镜像——**在用户明确之前不动。**
