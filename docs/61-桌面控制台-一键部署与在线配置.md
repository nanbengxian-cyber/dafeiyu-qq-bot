# 61-桌面控制台：填一次配置，服务器自己部署并跑起来

> 面向完全不懂 Docker 的人：一个 Windows EXE，填服务器和仓库信息 → 点一下 → 服务器自己下载源码、装依赖、起容器；之后在同一个界面里改配置。

---

## 一、这份文档解决什么问题

仓库原有的部署方式是「照着 `10-云服务器部署手册` 一条条敲命令」：装 Docker、写 `onebot11.json`、跑 `docker run`、进 WebUI 配适配器。对熟悉 Linux 的人十分钟，对不熟悉的人要卡好几处——命令打错、端口没放行、容器权限不足、配置写错位置。

桌面控制台把这条路径压成三步：**填表 → 测试连接 → 开始部署**。部署完成后，它还负责第二步以前没有的东西：把服务器上的可调配置项**列出来让你改**，改完自动生效。

## 二、它是什么 / 不是什么

**是**：

- 一个本地 Windows 程序（PyInstaller 打包成单文件 EXE），通过 SSH 操作**你指定的那台服务器**。
- 一个部署器：从你指定的 Git 仓库拉代码，生成容器编排，拉起服务。
- 一个配置面板：配置项清单由**仓库**决定，不写死在 EXE 里。

**不是**：

- 不是远程控制已有机器人的后门——它只连你填的地址，且只管理带专用标记的部署目录。
- 不保存密码、私钥、Token；不读取你本机的机器人文件。
- 不替 AstrBot 做首次初始化（管理员密码、OneBot 适配器、模型 Key、人格）。这些是框架自己在网页里生成的，控制台代填不了，教程第 6 步给了入口。

## 三、三步界面

| 页签 | 你要做的 | 它做的 |
|---|---|---|
| ① 连接与部署 | 填服务器地址/SSH/仓库/目录 | 只读预检 → 拉代码 → 生成编排 → 拉镜像 → 启动 |
| ② 配置与状态 | 改配置、点应用 | 读回配置清单与当前值 → 行级写回 → 需要时重建容器 → 刷新显示 |
| ③ 新手教程 | 照读 | 六步流程 + 常见故障 + 安全提醒 |

## 四、部署链路：每一步在服务器上发生什么

```
你点「开始部署」
  │
  ├─ 1. SSH 连接（默认拒绝未知主机指纹；确认可信后才接受）
  ├─ 2. 只读预检：系统 / Git / Docker / Compose / 权限 / 磁盘
  │     缺 Git 或 Docker 且系统是 Debian/Ubuntu 且勾了「自动安装」→ 才装
  ├─ 3. 目录安全检查
  │     目录已存在但**没有** .dafeiyu-managed 标记 → 直接拒绝，不覆盖
  ├─ 4. 从仓库下载源码
  │     git clone --branch <分支> --single-branch <仓库> <目录>
  │     已有 .git → 走 fetch + checkout --detach（幂等更新，不重复下载）
  ├─ 5. 准备目录与配置
  │     data/napcat、data/astrbot、plugins、deploy
  │     deploy/robot.env 不存在则从 robot.env.example 复制，并 chmod 600
  ├─ 6. 生成 docker-compose.generated.yml（镜像、端口、卷、env_file）
  ├─ 7. docker compose pull → up -d --remove-orphans
  └─ 8. 读回容器状态
```

要点：

- **脚本是本地生成、通过 SSH stdin 执行的**，不落盘到服务器临时目录；所有用户输入都经过 shell 转义。
- **Docker 权限自动降级**：`docker info` 不通就自动改走 `sudo docker`，仍然不通才报「当前账号无权访问 Docker」。
- **幂等**：重复点部署只会更新代码，不会重装或清数据。
- **不碰别人的目录**：标记文件是唯一的「所有权凭证」，没有它就不动。

## 五、配置为什么能「浮动」

控制台不预置任何配置控件。部署完成后它做两件事：

1. 读 `deploy/console-config.json`（仓库里的清单）→ 决定**显示哪些项、什么类型、什么范围**；
2. 读 `deploy/robot.env`（服务器上的真实值）→ 决定**每项当前显示成什么**。

改完点「应用配置」：

- 取值先本地校验（类型、范围、枚举、换行注入），不合法直接拒绝，不做静默钳制；
- 写回是**行级编辑**：只替换目标变量那一行，注释、空行、顺序原样保留；不存在的变量追加到固定的「控制台托管」小节；
- 标了 `restart_required` 的项会自动 `docker compose up -d --force-recreate --no-deps astrbot`，改完即生效；
- 然后**重新读回**文件与状态，界面显示的就是服务器上的真实值。

所以：加一个配置项 = 改仓库里的 JSON 清单 + 在插件里读同名环境变量，**不需要重新发布 EXE**；EXE 遇到不认识的类型会跳过而不是崩溃（向前兼容）。

敏感项（如搜索接口密钥）在界面上只显示「已设置 / 未设置」，真实值**永远不出服务器**。

## 六、安全模型

| 面 | 做法 |
|---|---|
| 凭据 | 密码、私钥口令只在内存；不写配置文件、不进日志 |
| 本地落盘 | 只存非敏感字段（地址、端口、目录、仓库地址）；私钥**路径**也不存 |
| 主机校验 | 默认 `RejectPolicy` 拒绝未知指纹，防止中间人；确认后才接受 |
| 日志 | 远程输出统一过脱敏：URL 内嵌凭据、`token=`/`password=`/`api_key=` 打码；显式敏感值整段替换 |
| 目录边界 | 标记文件保护，无标记的目录一律拒绝；拒绝根目录/主目录本身 |
| 输入 | 部署目录、仓库地址、镜像名、端口、监听地址全部先校验再拼接；shell 参数一律 quote |
| 网络 | 只连你填的一台主机；不做端口扫描、不做横向移动 |

## 七、目录与代码结构

```text
desktop-controller/
├── app.py                 界面与流程编排（三步页签、异步执行、日志脱敏）
├── deployer.py            SSH 传输层 + 预检 + 远程脚本生成 + 状态/配置读写
├── knobs.py               配置清单解析、取值校验、env 行级写回
├── config_schema.py       部署表单字段（界面按它生成，含 auth_type 联动的显隐）
├── build-windows.ps1      Windows 一键打包（独立 venv，不污染系统 Python）
├── requirements.txt       运行时依赖（paramiko，会被打进 EXE）
├── requirements-build.txt 打包工具（PyInstaller）
└── tests/                 70 项离线测试，不需要真服务器
deploy/
├── console-config.json    配置项清单（控制台界面的唯一来源）
├── robot.env.example      运行配置模板
└── robot.env             真实运行配置（.gitignore 忽略，绝不入库）
```

分层原则：**界面不碰 SSH，SSH 不碰配置语义，配置语义不碰文件 IO 细节**。传输层抽成 `Transport` 协议，测试用假传输即可覆盖全部流程。

## 八、验证记录

本机（Linux）实测，`python3 -m unittest discover -s tests` → **70 项全过**。关键几项不是 mock 断言，而是真的执行了脚本：

| 测试 | 真的验证了什么 |
|---|---|
| `test_first_run_deploys` | 在临时 HOME 里真跑生成的部署脚本：克隆成功、`.dafeiyu-managed` 落盘、compose 含正确端口与 `env_file`、`robot.env` 权限是 `0600`、假 docker 收到 `pull` 与 `up -d --remove-orphans` |
| `test_second_run_updates_instead_of_recloning` | 第二次运行走「更新仓库源码」分支，不重新克隆 |
| `test_existing_foreign_directory_is_refused` | 目录里有别人的文件时拒绝部署，且**文件没被删** |
| `test_tilde_deploy_dir_expands_to_home` | 默认目录 `~/dafeiyu-bot` 真被展开到 `$HOME`，不产生字面量 `~` 目录 |
| `test_preflight_script_runs_and_parses` | 预检脚本真执行并解析出 OS/Git/Docker/Compose/权限 |
| `test_script_contains_no_plaintext_password` | 生成的脚本与日志里**没有**明文密码 |
| `test_manifest_matches_env_example` | 配置清单与 env 模板一一对应，防止界面出现「服务器上不存在的变量」 |

复查中发现并修掉的真实缺陷（都补了回归测试）：

1. **SFTP 不展开 `~`** —— 默认目录是 `~/dafeiyu-bot`，直接拿它拼 SFTP 路径会写成 `/home/用户/~/dafeiyu-bot`，配置改了但容器读不到。修法：写文件前先用 `remote_dir()` 解析绝对路径。
2. 部署成功后连接被提前关闭 —— 导致紧接着读配置项失败。修法：连接生命周期交给调用方。
3. 空值语义错误 —— `DSH_X=` 被显示成默认值，而插件读到的是空串（判定为**关**），界面会显示成开。修法：只有变量**不存在**时才回落默认值。

## 九、已知边界（没做的事，如实写在这里）

- **EXE 需在 Windows 上打包**：`powershell -ExecutionPolicy Bypass -File .\build-windows.ps1`。本仓库的 Linux 环境没有 PowerShell，脚本只做过静态复查，没有产出过 EXE 文件。
- **没有对任何真实服务器跑过部署**：所有测试都用假 `git`/`docker`/`uname` 与假传输层。第一次真机部署请先点「测试连接」看预检结果。
- **AstrBot 首次初始化仍在网页里做**：管理员密码、OneBot V11 适配器（主机填容器名）、模型 Key、人格，这些由框架自己生成，控制台不代填。
- **代理/风控链不在控制台范围内**：出口代理属于运行环境话题，见仓库其他文档。

## 十、常见故障

| 现象 | 处理 |
|---|---|
| 首次连接该服务器 | 勾选「首次连接接受服务器指纹」，或先用系统 `ssh` 确认指纹 |
| SSH 登录失败 | 核对用户名、密码/私钥、端口；服务器可能禁用密码登录 |
| 当前账号无权访问 Docker | 用 root，或把用户加入 `docker` 组 |
| 部署目录已存在且不是本控制台创建的 | 换目录；控制台不会删别人的目录 |
| 镜像拉取失败 | 检查服务器能否访问镜像仓库，必要时配代理 |
| 端口被占用 | 在「服务端口」改端口后重新部署 |
| 没有配置项 | 仓库缺 `deploy/console-config.json`，或还没部署成功 |

## 十一、脱敏规则

本文档、代码、模板、日志一律只使用占位符：

- 服务器：`<服务器地址>` / `your-server.example.com`
- 仓库：`https://<你的代码托管域名>/<账号>/<仓库>.git`
- 账号：`<管理员账号>` / `<管理员 QQ 号>`
- 密钥：`<仅在服务器本地设置>`
- 路径：`<服务器上的私有路径>`

真实值由使用者在自己的机器和服务器上填写；`deploy/robot.env` 已在 `.gitignore` 里，**不要**把它提交上来。
