# QQ 智能聊天 AI —— 长期目标与技术方案

> 基于现有实践（PC+手机局域网联动监听 QQ）的演进蓝图

---

## 一、项目概述

当前系统通过 PC 端工具监听 QQ 消息，经局域网转发至手机端 AI 进行处理回复。该方案存在**稳定性差、依赖后台存活、部署分散、无持久记忆**等瓶颈。本方案旨在将现有原型升级为一套**可长期稳定运行、具备多模态交互能力、拥有群友记忆画像**的 QQ 智能体。

---

## 二、核心目标与扩展方案

### 2.1 架构稳定性：从「双端挂机」到「云端常驻」

#### 现状痛点
- PC 与手机需同时在线，通过局域网互联，任一端断线即失效。
- PC 并非 24h 开机，手机后台进程极易被系统杀掉。
- 当前仅作为"实验性脚本"运行，无容错与自动恢复机制。

#### 扩展思路

| 方案 | 原理 | 优势 | 劣势 | 推荐度 |
|------|------|------|------|--------|
| **轻量云服务器** | 租用一台低配置 VPS（1核1G~2G 即可），部署 Linux 环境，运行 QQ Bot 框架 + AI 推理/转发服务 | 7×24 在线、网络稳定、可 root、与手机解耦 | 有月租成本（约 10~30 元/月） | ⭐⭐⭐⭐⭐ |
| **旧手机/树莓派本地服务器** | 利用闲置安卓机 Termux 或刷 Armbian，作为局域网服务器长期插电运行 | 零额外租金、物理可控 | 仍需解决安卓保活、性能受限、无公网 IP | ⭐⭐⭐ |
| **Serverless 函数 + 定时唤醒** | 利用云函数按需触发，配合 QQ 的 Webhook/第三方推送 | 极低费用 | 冷启动延迟、QQ 协议适配复杂 | ⭐⭐ |
| **APK 一体化（纯手机端）** | 将监听、AI 推理、回复全部封装进一个安卓 APK，本地闭环 | 无需 PC、无需网络中转 | 安卓保活仍是难题、大模型本地推理性能受限 | ⭐⭐⭐ |

#### 关键结论
> **首选方案：轻量云服务器 + QQ Bot 框架**。将 PC 的"监听工具"迁移至云端，手机仅作为可选的管理终端。服务器推荐选择可以 root 的境外小厂 VPS 或国内轻量应用服务器（腾讯云/阿里云学生机约 10 元/月）。

### 2.2 多模态交互：从「纯文本」到「图文音视频」

#### 现状痛点
- 当前只能输出纯文字，无法发送表情包、图片、语音、视频。
- 视觉理解依赖智谱免费 API，尚未深度整合。

#### 扩展思路

**A. 表情包与图片**
- **问题根源**：QQ 协议对自定义表情/图片有大小、格式、上传接口限制。
- **解决方案**：
  1. **图床转链法**：AI 生成/检索到表情图片后，上传至免费图床（如 SM.MS、Imgur），通过 QQ 的图文消息接口发送 Markdown 或富文本链接（部分 Bot 框架支持直接发送图片 URL 自动转图片）。
  2. **本地图库映射法**：维护一个本地表情包数据库（关键词 → 图片文件路径），Bot 框架直接调用发送本地图片。
  3. **CQ 码/JSON 卡片**：使用 go-cqhttp、NapCat、LLoneBot 等框架支持的 CQ 码 `[CQ:image,file=xxx]` 直接发送。

**B. 语音消息**
- **TTS 生成**：使用 edge-tts、GPT-SoVITS、ChatTTS 等生成自然语音音频文件（`.mp3`/`.wav`/`.silk`）。
- **QQ 语音格式转换**：QQ 语音实际为 Silk V3 编码。需将生成的音频通过 `silk-v3-decoder` 或 `pysilk` 转换为 SILK 格式，再通过 Bot 框架的 `[CQ:record,file=xxx]` 发送。
- **进阶**：接入语音识别（ASR）实现"语音指令输入 + 语音回复输出"的全语音交互。

**C. 视频理解**
- **当前搁置原因**：视频解析、抽帧、理解的全链路成本（Token + 计算 + 带宽）较高。
- **折中方案**：
  1. **关键帧提取**：对群友分享的视频，使用 FFmpeg 截取前 3 秒/中间帧，送入视觉模型进行内容描述。
  2. **语音转文字**：提取视频音轨，通过 Whisper（本地或 API）转写文字，理解视频主题。
  3. **仅回复文字评论**：暂不发送视频，只针对视频内容生成文字点评。

**D. 视觉模型升级**
- 智谱 GLM-4V 免费额度足够轻量使用。
- 后续可接入：**Qwen-VL、InternVL、本地部署的 LLaVA**（若服务器带 GPU 或利用手机 NPU）。
- **场景扩展**：识别群友发的梗图、截图纠错、识别游戏画面等。

### 2.3 部署与学习成本：从「散装脚本」到「一键交付」

#### 现状痛点
- PC 端工具链分散（监听、转发、AI 调用各自为政）。
- 安卓端无统一封装，配置门槛高。
- 缺乏文档，换设备迁移成本极高。

#### 扩展思路

**A. 服务端 All-in-One 容器化**
- 使用 **Docker Compose** 将以下组件编排：
  - `napcat` / `go-cqhttp` / `LLOneBot`（QQ 协议端）
  - `ai-core`（业务逻辑 + AI 调用）
  - `memory-db`（记忆数据库，如 SQLite / PostgreSQL）
  - `tts-service`（可选语音服务）
- 提供 `docker-compose.yml` + `.env` 配置文件，实现"一键拉起"。

**B. 安卓端 APK 封装（备选方案）**
- 若坚持纯手机方案，使用 **Termux** 或 **Pydroid 3** 运行 Python 脚本，配合 **Auto.js/无障碍服务** 实现 QQ 监听。
- 更优解：开发一个原生安卓 APK，内嵌：
  - 轻量 HTTP 服务（接收消息）
  - AI 推理客户端（调用远程 API）
  - 前台服务 + 通知保活（降低被杀概率）
  - 电池优化白名单引导

**C. 配置教程体系**
- **快速开始**：5 分钟 Docker 部署指南。
- **进阶配置**：记忆系统调参、多模态开关、群友白名单/黑名单。
- **故障排查**：日志查看、常见封号风险规避、QQ 协议风控说明。

### 2.4 记忆系统：从「无状态」到「群友画像」

#### 现状痛点
- AI 每次回复都是"初见"，无法延续上下文，更无法针对不同群友调整语气。

#### 扩展思路

**A. 分层记忆架构**

```
┌─────────────────────────────────────────────┐
│  长期记忆（Long-term Memory）                │
│  • 群友人物画像（Profile）                    │
│  • 群聊重大事件时间线（Timeline）              │
│  • 高频话题与禁忌词（Topic & Taboo）           │
├─────────────────────────────────────────────┤
│  中期记忆（Session Memory）                  │
│  • 最近 N 条对话上下文（滑动窗口）              │
│  • 当前话题分支（Thread）                     │
├─────────────────────────────────────────────┤
│  短期记忆（Working Memory）                  │
│  • 当前输入 + 系统提示词（System Prompt）      │
└─────────────────────────────────────────────┘
```

**B. 群友画像生成机制**
1. **数据采集**：监听并存储每位群友的发言（原文 + 时间戳 + 消息类型）。
2. **关键词提取**：对单用户历史消息进行 TF-IDF / 词频统计，提取高频词汇、口头禅、兴趣标签。
3. **画像压缩**：定期（如每周）由大模型对原始聊天记录进行摘要，生成结构化 Profile：
   ```json
   {
     "user_id": "123456",
     "nickname": "小明",
     "persona": "二次元浓度高，喜欢用熊猫头表情包，擅长Python，讨厌原神黑",
     "tone_preference": " sarcastic but friendly",
     "hot_topics": ["代码", "游戏", "摸鱼"],
     "last_updated": "2026-08-30"
   }
   ```
4. **动态加载**：回复某人时，将该用户的 Profile 注入 System Prompt，实现"见人说人话"。

**C. 重大事件记忆**
- 设定触发器：当群聊中出现"@全体"、"公告"、"红包"、"高频重复关键词"时，标记为 Event。
- 由 AI 生成事件摘要，存入 Timeline。
- 后续对话中，AI 可引用历史事件（"上次你说的那个项目怎么样了？"）。

**D. 记忆存储选型**
- **SQLite**：轻量、零配置、适合单群/小群。
- **PostgreSQL + pgvector**：若未来需要语义检索（向量搜索相似记忆）。
- **本地 JSON**：极简方案，定期由 AI 压缩合并。

## 三、推荐技术栈

| 层级 | 推荐方案 | 备注 |
|------|----------|------|
| **QQ 协议** | NapCat / LLOneBot / go-cqhttp | NapCat 基于 NTQQ，稳定性较好；LLOneBot 轻量易部署 |
| **服务端** | 轻量 VPS (Debian/Ubuntu) | 1核1G 起步，有 Docker 环境即可 |
| **AI 推理** | 远程 API (智谱 / DeepSeek / Claude) + 本地缓存 | 平衡成本与效果 |
| **视觉** | 智谱 GLM-4V / Qwen-VL-Max | 免费额度优先 |
| **语音(TTS)** | edge-tts (免费) / GPT-SoVITS (高质) | 输出后转 silk 格式 |
| **语音(ASR)** | Whisper API / 本地 whisper.cpp | 视频/语音转文字 |
| **记忆存储** | SQLite (初期) → PostgreSQL (后期) | 配合 SQLAlchemy ORM |
| **部署** | Docker Compose | 一键编排 |
| **编程语言** | Python 3.10+ | 生态成熟，Bot 框架支持好 |

## 四、实施路线图

### Phase 1：稳定基石（1~2 周）
- [ ] 采购/配置轻量云服务器
- [ ] 部署 NapCat + 基础 AI 回复逻辑
- [ ] 脱离 PC+手机双端挂机，实现云端 24h 在线
- [ ] 编写部署文档与故障排查手册

### Phase 2：记忆与个性化（2~3 周）
- [ ] 设计 SQLite 记忆表结构（用户、消息、画像、事件）
- [ ] 实现消息持久化与群友词频统计
- [ ] 接入画像生成 Prompt，实现"对什么人说什么话"
- [ ] 引入滑动窗口上下文管理

### Phase 3：多模态突破（3~4 周）
- [ ] 接入视觉模型，实现识图/评图
- [ ] 实现表情包发送（CQ 码图片/图床方案）
- [ ] 实现语音回复链路（TTS → silk → QQ 语音）
- [ ] 视频关键帧提取 + 语音转文字（理解视频内容）

### Phase 4：工程化与生态（持续）
- [ ] 容器化（Docker Compose）
- [ ] 管理后台（Web UI 查看群友画像、记忆检索、配置开关）
- [ ] 安卓 APK 保活实验（作为备用方案）
- [ ] 社区插件化（允许自定义 Prompt、接入更多模型）

## 五、风险与规避

| 风险 | 影响 | 规避措施 |
|------|------|----------|
| **QQ 账号风控/封禁** | 高 | 使用小号；控制消息频率（加入随机延迟）；避免短时间内大量@；模拟人类作息（夜间降低活跃度） |
| **API 费用暴涨** | 中 | 设置 Token 上限；本地缓存高频回复；对长视频/大图进行压缩/降采样 |
| **记忆数据库膨胀** | 中 | 定期由 AI 压缩历史记录；只保留画像摘要，丢弃原始消息；设置存储上限自动清理 |
| **服务器被攻击** | 低 | 仅开放必要端口；使用密钥登录禁用密码；定期备份数据库 |
| **语音/图片格式兼容** | 中 | 建立格式转换中间件（silk/mp3/png/jpg 统一处理） |

## 六、总结

你的 QQ AI 已经从「能跑」迈进了「可用」的阶段，下一步的核心矛盾是**稳定性**与**个性化**。建议立即将架构迁移至云端服务器，摆脱双端挂机的束缚；同时着手构建轻量级记忆系统，让 AI 从"复读机"进化为"懂群友的群友"。多模态是锦上添花，可在地基稳固后逐步迭代。
