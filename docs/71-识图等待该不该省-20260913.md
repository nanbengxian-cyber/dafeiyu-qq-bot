# 71 · 识图等待该不该省：一个"看起来能省 17 秒"的改动，实测只省了 15%

**日期**：2026-09-13
**改动**：`dsh-imgctx` 1.2.0
**起因**：目标是"让机器人更像真人"，其中一项是**节奏不自然**。群主在群里说过
「除了速率太慢了，没有办法」——速度就是节奏，这是他自己点名的唯一一条。

**结论先说**：改动本身是**真实但有限**的（省掉 15% 的识图等待），
**而不是我一开始以为的"回复快 17 秒"**。第三节记录了我怎么推翻自己的判断 ——
那部分比改动本身更值得读。

---

## 一、怎么把"慢"归因到具体一段代码

只看总延迟没用，得先分组。用 `Prepare to send`
（**每条 result 一行、组件用空格拼**）对齐"这一轮回复"，按「有没有夹识图」分组：

| 分组 | n | 中位 | P90 |
|---|---|---|---|
| 没有识图 | 168 | **8.6s** | 52.7s |
| 识图成功并注入 | 54 | **25.8s** | 75.2s |
| 等满预算后放弃 | 1 | 43.8s | 43.8s |

看起来识图给被 @ 的回复加了约 17 秒。整体账（09-04 起全部日志）：

```
识图调用 1808 次，累计 11528 秒（均 6.4s，中位 6.4s，P90 9.1s，最长 22.6s）
其中 65% 发生在「当前这条消息根本不是图」的轮次
imgctx 附加 1153 次，缓存命中率只有 31%
因超预算放弃 783 次 / 尝试 2117 次 = 放弃率 40%
```

两个刺眼的点：

1. **40% 的放弃率**：路走了、时间花了，最后什么都没拿到 —— `wait_for(BUDGET)`
   到点抛 `TimeoutError`，本轮放弃注入。
2. **配置与代码意图矛盾**：
   ```python
   # 代码第 28 行注释
   # ……超时就放弃注入而不是拖着回复不发——宁可这次没看懂图，
   # 也不能让机器人半分钟不说话。
   BUDGET = float(os.environ.get("DSH_IMGCTX_BUDGET", "15"))
   ```
   ```
   # 生产 /opt/qqbot/imagegen.env（2026-09-12 16:57 改）
   DSH_IMGCTX_BUDGET=24
   ```
   注释写着"不能半分钟不说话"，env 却把上限设成 24 秒。这类矛盾不报错，只变慢。

## 二、根因与改动

`_emit()` 里 `_caption()` 是**串行阻塞**的（串行有理由：智谱并发两张直接 429），
整条 `_run` 又套在 `wait_for(BUDGET)` 里。问题在于**它不区分这张图是哪来的**：
连注入文案自己都写着「不是当前这条消息自带的图片……如果和当前话题无关就忽略」，
却要为一个标了"可以忽略"的上下文把回复拖住。

**改动**：按「这张图是不是本轮要回答的东西」分阻塞。

```python
if 当前消息自带的图 or 用户精确引用的图:
    等                          # 回答就靠它
elif 这一轮在说图 or 图是刚发的:
    等                          # 见下：这两个例外是必须的
else:
    只吃缓存 + 其余后台转述        # 本轮不等
```

- `_attach_cached()`：只贴已缓存的转述，零网络请求。
- `_warm()`：没缓存的起 `asyncio.create_task` 后台转述，**转述完照样写进缓存**，
  下一轮白拿。`_inflight`（key→Task）去重并兼作并发上限 `DSH_IMGCTX_WARM=4`。
  后台任务的 done 回调里**必须取一次 `t.exception()`**，否则 asyncio 在 GC 时会打
  「Task exception was never retrieved」。
- **例外**："不等"会引入新失败模式 —— 发完图再问「这图是啥」，那张图算"历史图"，
  就会变成没看图直接答。所以：当轮 `req.prompt` 命中 `图|截图|表情|照片|画的|p的`、
  或图龄 ≤ `DSH_IMGCTX_RECENT`（45s）时，照旧等；**拿不到 `req.prompt` 时也按
  "在说图"处理**。判不准就退回旧行为：慢一点，好过瞎答。

## 三、推翻自己：反事实回放

改完、部署完、看了一次真实生效（见第四节），我觉得可以收工了。
但"能省多少"我一直没量过 —— 于是拿新规则去**回放全部 1337 次历史识图注入**：

```
历史 1337 次识图注入，按新规则回放：
  仍需等待 1138 次（85%）：{'图刚发出来': 1081, '当前在说图': 57}
  本可省掉  199 次（15%）
  图龄 P10 = 3.6s  P25 = 8.3s  P50 = 17.4s  P75 = 31.7s  P90 = 61.8s
  预计省下约 744 秒的识图等待（全量日志 9 天合计 12 分钟）
```

**85% 的等待在新规则下仍然发生**，因为：

**识图绝大多数发生在"有人刚发了张图"的时刻**（图龄中位只有 17.4 秒）。
那个时刻，那张图**确实就是话题** —— 等待是对的，我加的"图刚发出来"例外
把大部分本来合理的等待又请回来了。

所以我最初的框架是错的：

- ❌ 我写的：「识图给被@回复加了 17 秒」→ 暗示这 17 秒大部分是浪费。
- ✅ 实际：「17 秒的差距里，识图本身约 7.4s，其余是"群里正热闹"这个共同原因；
  而其中真正可省的只有 15%。」

那个 8.6s vs 25.8s 的对比本身也有混淆：**夹着识图的轮次往往就是群里正热闹的轮次**
（有人发图 → 多人接话 → 机器人被 @），合并、上下文、LLM 生成都会更慢。
识图是**决定性**的那 7.4s（它严格串在 LLM 之前），但不是全部 17s。

### 那这个改动还留不留？

**留。** 理由：

1. 15% 是真的省，全量 744 秒，且**不增加任何 API 调用** —— `_warm` 只对那些
   本来就会在本轮被转述的图做事，只是从"阻塞着做"改成"后台做"。
2. 后台转述会把结果写进缓存，对 >45s 的图，下一次被引用时就是白拿 ——
   单次回放量不出这个复利。
3. 例外保证"真的需要看图"时行为不变，没有把风险换成绩效。

**但它的定位要摆正：这是一次小幅优化，不是"回复快 17 秒"的胜利。**

## 六、可复用的结论

1. **延迟要按"这一轮发生了什么"分组才有归因力。** 只看总中位数只会得到"有点慢"；
   按「有没有夹识图」一分，立刻指向一段代码。但**分组是相关不是因果**。
2. **分组对比里，只有"严格串在被拖慢的那一步之前"的部分才是因果。**
   7.4s 的 `_caption()` 串在 LLM 之前，是因果；剩下那 10s 的差距是"群里正热闹"
   这个共同原因同时造成的，不能算在识图头上。
3. **任何"加规则"的改动，都要拿历史数据回放一遍，看新加的例外吞掉了多少收益。**
   我加的"图刚发出来"例外吃掉了 81% 的案例，把一次"省 17 秒"变成"省 15%"。
   如果不回放，我会一直以为自己干了个大活，而且**读者也会信**。
4. **"高放弃率"是比"高耗时"更强的信号。** 40% 的尝试等满预算后一无所获 ——
   时间花了、结果没有，两头都亏。任何带 `wait_for` 的预算逻辑都该统计放弃率。
5. **env 值会悄悄背离代码注释写明的设计意图。** 注释说"不能半分钟不说话"、
   env 写着 24 秒。定期对一遍这类矛盾，它不报错，只变慢。
6. **`pkill -f <脚本名>` 会自匹配杀掉正在执行它的 shell。** 这个坑又踩了一次。
   用 `pgrep -af "[w]atch"` 或 `pkill -f "[/]tmp/xxx"` 这种不自匹配的写法。
7. **容器内跑测试会污染生产日志，如果测试 import 了 `astrbot.core`。**
   上一轮的结论「从 /tmp 跑测试不会进生产日志」**不完整**：`import astrbot.core`
   会顺带初始化 AstrBot 的日志配置，把文件 sink 挂到
   `/AstrBot/data/logs/astrbot.log` 上。加静音之前那次跑混进 **5 行**
   `[ic.main:666]` / `[ic.main:730]`；加静音之后两次跑都是 **0 行**。
   修法：import 之后 `from loguru import logger; logger.remove()`（独立进程，
   只影响自己）。**核对方式也要修正**：①不能只 grep 猜的行号（我第一次只查
   `:666`，5 行里只看到 2 行）；②不能靠"跑前跑后数日志总行数"（生产日志同时
   在被真实群消息写入，我第二次核对就被 29 行真实活动骗了）。
   **可靠做法：grep 测试进程自己的模块名** —— 测试放 `/tmp/ic`，日志里就是
   `ic.main`；生产是 `dsh-imgctx.main`，天然可分。

## 待办 / 未解决

- **真正的杠杆是 6.4 秒的转述本身，不是阻塞策略。** 既然 85% 的等待是该等的，
  想把这段路变快只能从转述耗时下手：
  * `_caption()` 的串行前提（原注释："智谱并发两张会 429"）现在转述 provider
    已被 `dsh-vischain` 换成 `vision-scnet`，**前提从未重新验证**。若能并发，
    两张图的时间可以省一半 —— 但 `dsh-vischain` 生产与镜像不一致，动它之前
    必须先跟用户确认哪边是最新。
  * 单张 6.4s 里，模型调用与下载/缩图的占比还没量过。
- `DSH_IMGCTX_BUDGET=24` 暂时不改：这一刀之后 24s 只作用于"当前图/引用图/在说图"，
  那几条路径是真的该等的。但要盯住它们的放弃率，若仍高，说明 24 秒本身该下调。
- **反事实回放这个手法应该固化成习惯**：以后任何"少等/跳过/延后"类改动，
  提交前先回放历史，把"新例外吞掉多少"当成交付物之一。
- `dsh-vischain` 生产与镜像不一致，需要找时间跟用户确认哪边是最新，
  再决定是否同步镜像 —— **在用户明确之前不动。**
