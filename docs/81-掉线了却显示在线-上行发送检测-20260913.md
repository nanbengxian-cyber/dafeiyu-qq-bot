# 81 · 掉线了却显示「在线」：上行发送链路检测

日期：2026-09-13
触发：用户报「**依旧是他掉线了我也不知道，没有通知，这网页显示还是在线**」（状态页 `http://<广州机>:8888/`）

---

## 一、现象

2026-09-13 15:24 起，大肥鱼（3752949000）**一条消息都发不出去**，但：

| 观察点 | 显示 |
|---|---|
| 状态页 `status.json` | `state: online`、`message: 机器人在线` |
| 判定依据 | `探针 get_status online=true` |
| 告警邮件 | **一封都没有**（这段时间零封） |
| 实际情况 | 15:24:28 起每条 `sendMsg` 都失败 |

napcat 日志原始证据：

```
15:24:28 [info] 发送 -> 群聊 [神人乐子群] [大肥鱼] [图片]
15:24:29 [error] 发生错误 Error: EventChecker Failed:
                NTEvent serviceAndMethod:NodeIKernelMsgService/sendMsg
                  "result": -1, "errMsg": "rich media transfer failed"
15:24:32 [info] 发送 -> 群聊 [神人乐子群] [大肥鱼] 张飞那事想了一下午…
15:24:33 [error] 同上 sendMsg
                  "result": 1006514, "errMsg": "网络连接异常!"
```

AstrBot 侧同步报错：`aiocqhttp.exceptions.ActionFailed: retcode=1200 …
EventChecker Failed: NTEvent serviceAndMethod:NodeIKernelMsgService/sendMsg`。

最后一次**成功接收**是 14:52:47 —— 也就是说 14:52 之后 QQ 连接其实已经死了，
只是群里没人说话，直到 15:24 机器人自己开口才暴露。

---

## 二、根因（三层都是「判据不可信」）

### 1. `get_status` 的 online/good 不能证明发得出去

QQ 会话失效后，NapCat 仍返回：

```json
{"status":"ok","retcode":0,"data":{"online":true,"good":true,"stat":{}}}
```

`detect_state()` 里 `p=online` 分支**直接采信**这个值（只额外查了
`probe_ws` 看 AstrBot↔NapCat 通道，而这条通道本来就是通的），于是判 online。
**「连得上」与「说得出去」是两件事，看守只验了前者。**

### 2. `发送 ->` 是「尝试发送」，不是「发送成功」

这行打在 error **之前约 0.2 秒**，是发起调用时打的。而 `last_activity_age()`
正是按 `发送 ->|接收 <-` 取最后一行算「多久没动静」——**把失败的发送算成了活动**。
当时 `status.json` 里 `last_seen_seconds: 239`，那 239 秒前正是 15:24:32
那次**失败**的发送。

### 3. 关键告警被邮件风暴埋掉

同期 llm 探针每 600s 报一次，而 `NOTIFY_MIN_GAP` 恰好也是 600s：

```
06:47:07 ⚠️调不通 → 06:47:18 ✅已恢复 → 06:57:10 ⚠️ → 06:57:21 ✅ → 07:07:13 ⚠️ → …
```

每 10 分钟一对「故障 + 恢复」，一天上百封。LLM 探针测的是
`bigfeiyu-deepseek-flash`（备用模型，返回空内容），却按「全站降级」发信。

---

## 三、修复

### 新增 `/opt/qqbot/qq_send_health.py`

把每个 `发送 ->` 与**紧随其后**的 error 配对，得到：

| 输出 | 含义 |
|---|---|
| `last_ok` | 最近一次**真的发出去**的发送时间 |
| `last_fail` | 最近一次发送失败时间（强证据：`1006514`/`网络连接异常`/`sendMsg`） |
| `last_fail_weak` | 媒体类失败（`rich media transfer failed`，文本可能仍正常） |
| `last_recv` | 最近一次收到消息的时间 |

判定：**`last_fail > last_ok` ⇒ 上行坏了（`uplink_broken`）**。

两个关键设计：

- **只统计「本次容器运行周期」**（用 `docker inspect` 的 `State.StartedAt`
  作为 `docker logs --since`）。因为 `docker restart` **不会**清空容器日志
  （只有 compose 重建才会）。若把重启前的失败算进来，用户刚扫码登录成功、
  还没发第一条消息时就会被判成「仍然发不出」→ **误报一封假告警**。实测对照：
  切片后 `broken: false`（正确），全量 `broken: true`（会误报）。
- **拿不到日志一律回 `unknown`**，绝不把「读不到」当 `ok`。权限不足、
  容器不存在等都会显式识别（否则会静默返回全 0 —— 而全 0 在调用方看来是
  「健康」，正是最危险的假阴性）。

### `qq_watchdog.sh` 六处改动

1. 新增配置：`SEND_HEALTH_PY` / `SENDFAIL_ALERT_AFTER`(120s) /
   `SENDFAIL_RENEW_AFTER`(300s) / `SENDFAIL_RESTART_COOLDOWN`(1800s) /
   `CRITICAL_MIN_GAP`(60s)
2. 新增 `send_verdict()`：`ok` / `broken` / `unknown`
3. `detect_state()` 的 `p=online` 分支加第二判据：`send_verdict=broken` →
   `degraded|探针 online、通道也在，但最后一次发送失败（QQ 会话发不出消息）`
4. 主循环 `degraded` 分支**按原因分流**：
   - `ws`（通道断）→ 重启 AstrBot 自愈（原有行为，不动）
   - `发送失败` → 重启 AstrBot 治不了（通道本来就是通的），改为发信 + 重启
     napcat 换码强制重新登录（此前会误重启 AstrBot，纯属无效动作）
5. `notify_degrade()` 新增 `sendfail` 类型邮件（含「打开状态页扫码」指引），
   并让 `sendfail`/`offline` 走 `CRITICAL_MIN_GAP`，**不被共享冷却吞掉**
6. `llm_check()` 加一次性闸门 + `notify_degrade` 按 kind 记
   `.degrade_sent.$kind`：**一次故障只报一封**，止住 llm 风暴

## 四、验证（live）

安装后 watchdog 一个周期内（1 秒）就抓到了半死状态：

```
07:33:12 watchdog v3 启动
07:33:13 状态变化: online -> degraded
         （依据：探针 online、通道也在，但最后一次发送失败（QQ 会话发不出消息））
07:35:20 已触发降级告警邮件（kind=sendfail 持续 127s）
07:35:23 已发送 -> 2774000001@qq.com ：⚠️ QQ机器人掉线了（账号在、但一条消息都发不出去）
07:38:20 上行发不出消息已 307s，重启 napcat 换码并强制重新登录
```

状态页同步如实显示：

```json
{"state": "degraded",
 "message": "机器人在线但发不出消息（已 2 分钟），需要重新登录",
 "detect_reason": "探针 online、通道也在，但最后一次发送失败（QQ 会话发不出消息）"}
```

解析器实测输出与手工核对逐项吻合：`last_ok=14:52:04`、`last_fail=15:24:33`、
`last_recv=14:52:47`、`uplink_broken=true`。新增探测耗时 **0.088s**，
不拖慢 10 秒循环。

### 上线当晚自查出的两个自己的 bug（已修）

1. **sendfail 告警每 60s 重发**（`CRITICAL_MIN_GAP=60`）：3 分钟发了 3 封，
   把刚修好的通道又变成新的风暴 → 改为按 kind 的一次性标记
   `.degrade_sent.sendfail`，在线/掉线时清除。
2. **重启后误报**：`docker restart` 不清日志 → 改为「本次运行」切片（见上）。

## 五、遗留

- ~~**`ACCOUNT=100000003` 目前被注释掉**……**待用户决定是否恢复**~~
  **【2026-09-15 已解决：已恢复 `ACCOUNT`，且上面这条归因被证伪】**
  用户要求「把快速登录装上」，遂恢复 `ACCOUNT=100000003`。恢复前重新逐段读了
  minified 代码并做了双向实测，发现本条原先的归因**不准确**：

  - 有 `-q` 时，`XEe()` 里快速登录失败的三条路径（`quickLoginWithUin` reject、
    result≠0、「未找到历史登录记录」）**全部**以
    `!success && !attempted && !isLogined && n.getQRCodePicture()` 收尾。
  - 回退函数 `s()` 在**未配置** `NAPCAT_QUICK_PASSWORD(_MD5)` 时返回
    `{success:!1, attempted:!1}` —— `attempted` 为假，故 `!l && !d` 成立，
    **二维码一定会生成**。
  - 所以真正压住二维码的是**密码回退变量**，不是 `ACCOUNT`。
  - 实测：把 `ACCOUNT` 临时指向无登录态的 `1000000000`，重建后日志
    `快速登录失败，未找到该 QQ 历史登录记录` → `未配置回退密码环境变量…将使用二维码登录方式`
    → `二维码已保存到 /app/napcat/cache/qrcode.png`（确实生成了）。
    换回 `100000003` 重建 → `正在快速登录 100000003`，一次成功、无二维码。
  - 结论：`ACCOUNT` + **不配密码回退** 的组合下，快速登录失败会自动退回扫码，
    09-13 那种「永不显示二维码」的死锁配方不存在。9-13 的**现象**是真的，
    但原因是「快速登录『成功』而会话已被服务端作废」（见下方半死会话风险），
    与 `ACCOUNT` 是否传入 `-q` 无关。

  附带做了两件事：① 同步打开 WebUI 的 `autoLoginAccount`
  （`napcat/persist/napcatcfg/config/webui.json`）作为第二层；但实测该层
  `runWebUiConfigQuickFunction()` 全文件只有 1 个调用点、位于「没有 -q」的
  `else` 分支，故 **`ACCOUNT` 存在时它不生效**，只是将来若去掉 `ACCOUNT` 的保险。
  ② 删除 `public/qrcode.png` 里 00:40 那张**已失效的死码**（快速登录成功不再出码，
  留着会误导人对死码扫半天）。

  验证：`docker compose up -d` 与 watchdog 同款 **`docker restart`** 两条路径
  均自动快速登录成功、无二维码；探针 `online:true`；群里真实发出 3 条消息
  （含语音）`n_ok:3 n_fail:0`；容器 IP 两次重建都是 `172.18.0.2`，代理规则未漂移。
  watchdog 的 `mint_new_qr()` 正是用 `docker restart`，所以自愈链路已从
  「重启→等人扫码」变成「重启→自动登录」。
  回滚备份 `/opt/qqbot/backups/docker-compose.yml.bak.quicklogin2.20260914-165050`，
  详见 `大肥鱼QQ聊天计划/免扫码快速登录装上-实施记录.md`。
- **半死会话仍无解（真实残留风险）**：`ACCOUNT` 让快速登录「成功」，但 QQ 服务端
  已作废该会话时（`sendMsg` 返回 `1006514 网络连接异常`），日志里没有失败、
  也就不会出码，人仍无法扫码自救。缓解：watchdog v3 的 `sendfail` 检测
  （30 分钟冷却后重启换码）覆盖此场景；实在卡住就临时注释 `ACCOUNT` 重建出码。
- LLM 探针测的是备用模型 `bigfeiyu-deepseek-flash` 却按全站降级告警，
  降频只治了标；**要不要改成只探主模型（`bigfeiyu-justwoker-sol`）待定**。
- 「群里安静」与「连接已死」在无收发时仍无法区分（本次靠 15:24 那次失败的
  发送才暴露）。若想更早发现，可考虑周期性主动探测（如给机器人自己的小号
  发一条测试消息），代价是增加账号行为特征。
