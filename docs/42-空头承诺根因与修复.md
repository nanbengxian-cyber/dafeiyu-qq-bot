# 空头承诺（答应了却不做）根因与修复记录

时间：2026-09-02
现象（用户原话）：「他都没有做过某件事为什么要为承诺那件事而做呢？」
——群里它张口就是「等着」「这就来」「搜着呢」「这就去宣传」，然后什么都没发生。

## 一句话结论

**不是它不听话，是它手上根本没有工具。**

`cmd_config.json` 里聊天模型 `bigfeiyu-glm` 的 `modalities` 只写了 `["text"]`。
框架在 `tool_loop_agent_runner.py:657 _func_tool_for_provider()` 里有一道检查：

```python
modalities = self.provider.provider_config.get("modalities", None)
if isinstance(modalities, list) and modalities and "tool_use" not in modalities:
    logger.debug("Provider %s does not support tool_use, clearing tools for request.")
    return None          # ← 整个工具集被丢掉
```

于是发出去的 payload 里**没有 `tools` 字段、没有 `tool_choice`**，模型物理上
不可能调用工具，只能用文字答应。改成 `["text", "tool_use"]` 后立刻恢复。

那条解释一切的日志是 `logger.debug`，而线上 `log_level = INFO`——所以一年也
看不到一个字。

## 排查过程（每一步的证据）

### 1. 先量「到底空了多少」

napcat 日志（`docker logs napcat --since 48h`，含 09-01 20:25 → 09-02 20:26）：
1396 条群事件、413 条机器人发言，命中承诺句式 64 条。按能力分：

| 类别 | 条数 | 说明 |
|---|---|---|
| A 插件真能做 | 41 | 要图 / 语音 / 视频 / 搜索 |
| B 现在做不到 | 7 | 跨群宣传、存表情包、「以后」「回头」 |
| C 纯社交话术 | 16 | 「下次再战」「等着看你叫我爹」——不该算承诺 |

### 2. 第一版统计是错的，必须记下来

第一版按「承诺后 300 s 内群里出现 `[图片]`」判兑现，得到 26 兑现 / 25 空头。
**这个数字是假的。** 把 napcat 的 `[图片]` 和 astrbot 侧日志按时间对上以后：

```
重叠窗口内 napcat 发出的媒体 124 条
   [贴纸] 发送      116     ← dsh-sticker 的情绪 GIF
   兜底出图已发送      4
   出片              2
   对不上            2
```

所谓「兑现」几乎全是贴纸巧合。真实产出只有 12 次，且**全部来自兜底钩子**。

坑：astrbot 日志时间戳是容器 UTC（`[12:27:38]`），napcat 是墙上时间 CST
（`09-02 20:26`），差 8 小时，直接比会得出完全相反的结论。

### 3. 排除「模型不会调工具」

- `conversations` 表全部会话：32 条 assistant 轮，**0 条带 `tool_calls`**。
- 直连渠道手拼请求：3/3 命中。
- 换上真实的 3644 字人格 + 6 个真实工具 schema + 注入块 + 聊天历史：**6/6 命中**。
- 拿真实群历史（62 条，其中 31 条 assistant 全部没有 tool_calls）当上下文再问：
  仍然 5/6 命中——**历史里的坏示范不是原因**。

所以模型会调、人格没禁死、历史没污染。问题只能在请求组装上。

### 4. 装临时探针，抓真实 payload

三版探针（`dsh-probe`，用完已删）：

- v1 挂 `@filter.on_llm_request` 打印 `req.func_tool.names()` →
  **9 个工具都在**（6 个自研 + `future_task`/`send_message_to_user`/
  `get_group_message_history`），`system_prompt` 7591 字。
- v2 加 `@filter.on_llm_response` → 每次都是 `finish=stop`、`tools_called=[]`。
  钩子层看到工具，模型层没收到——差别在两者之间。
- v3 猴子补丁包住 `provider.client.chat.completions.create`，落盘真实 kwargs：

```
[13:23:59] 字段=['extra_body','messages','model','stream']
   工具 0 个: []
   tool_choice=None
```

**决定性证据。** 请求里根本没有 tools。此后顺着
`_func_tool_for_provider()` 找到 modalities 那道门。

教训：`req.func_tool` 有工具 ≠ payload 里有 tools。中间还隔着 runner 的一道
静默过滤，且它只在 debug 级别说话。

### 5. 消融实验的一个陷阱

第一轮 A/B（拆掉 Skills 段、Computer Use 尾巴）显示「原样 1/5、去掉 Skills
5/5」，看着像提示词太长压制了工具调用。**结论无效**：把 HTTP 429 当成了
「没调工具」。加退避重试重跑后，各组 4/8～8/8 没有显著差异，语音更是 8/8 全中。
提示词长度不是原因。

## 改动

唯一一处：

```
/opt/qqbot/astrbot/data/cmd_config.json
provider[id=bigfeiyu-glm].modalities:  ["text"]  →  ["text", "tool_use"]
```

备份 `cmd_config.json.bak.tooluse.1788355573`。改配置须
`docker compose up -d astrbot`（`restart` 不重读 env）；此处因同时改了插件也做过
`docker restart`。

## 顺带发现

### 兜底钩子一直在替它干活

`dsh-imagegen` / `dsh-voice` / `dsh-video` 的 `on_llm_response` 兜底路径是过去
唯一让媒体发得出去的东西。这也解释了为什么**没有兜底的能力 100% 空头**：搜索
（有 `dsh-web` 预搜救着）、跨群宣传、「以后/回头」、「存了」。

现在工具路径通了，两条路靠 `event.set_extra("<x>_done")` 互斥，实测没有重复发送。

### 人格白名单其实拦不住内置工具

`astr_main_agent.py:601` 按 `persona["tools"]` 建白名单，但 `future_task`
（:1632）、`send_message_to_user`（:1635）、`get_group_message_history`（:1655）
是在白名单之后 `add_tool` 的，绕过白名单。所以人格里那句

> 不要调用 send_message、future_task、定时任务等任何没在下面列出的工具

写了也没用——现在这三个是真的可用了。

### 定时任务（future_task）是真的能落地的

实测「你过 40 秒主动说句话」：模型建 `cron_jobs` 行 → 到点唤起 agent →
调 `send_message_to_user` 发出。链路完整。假群那次报
「你已被移出该群」是因为假群号不存在，不是链路坏。

两个已知风险，尚未处理：
1. 主动发言走 `Context.send_message`，**不过 `ResultDecorateStage`**，
   和 `dsh-welcome` 踩过的坑同源——模型写的 `[贴纸:x]` 会原样漏进群。
2. 手写 payload 时 session 前缀必须是 `default:`（平台 id），写
   `aiocqhttp:` 会被静默丢掉，只留一条
   `cannot find platform for session ...`。

## 结论：还剩什么问题

工具能力类的空头承诺（A 类 41/64）已从「结构上不可能兑现」变成「正常调用」。
剩下的两类需要分开处置，尚未动手：

- B 类（7 条，跨群宣传、存东西、「以后」）：能力确实不存在。要么接受它偶尔嘴上
  应付，要么在人格里给出明确的替代话术（实测它已经会说「拉我进去我能吆喝」
  「下次喊我我现画」，这是好现象）。
- C 类（16 条，「下次再战」）：本来就是社交话术，不该修。

## 复用教训

1. **`logger.debug` 级别的静默降级是最贵的坑。** 一道 `return None` 让整个工具
   系统失效一年，日志一个字都没有。凡是「能力被关掉」的分支，都该是 INFO。
2. **`req.xxx` 里有 ≠ 发出去了。** 钩子层的观察不能代替出口处的观察。要证明
   payload 的内容，只能包住真正的 client 调用。
3. **拿日志里的媒体计数当兑现证据，必须先排除同类干扰源**（这里是贴纸）。
   跨容器对时前先确认时区。
4. **消融实验必须把请求失败和「没触发」分开计数**，否则 429 会伪造出一个
   完美的假因果。
