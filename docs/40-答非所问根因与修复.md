# 答非所问 与 主动回复频率 调优记录

2026-09-02。插件 `dsh-ctxclean` + 三处配置改动。

## 一句话

会话历史里堆了 487 个过期的「注入块」，每次请求全都重发一遍，模型在几百段
互相矛盾的「最新群聊」里挑错了要回的那一句 —— 这就是「答非所问」。
这个插件在请求发出前把历史里的过期块清掉。

## 症状

用户原话：

> 你看一下群里的对话，你能很明显的看到，似乎有点答非所问，比如说发生一件
> 事情他就会说到另外一件事情上

最干净的一个证据，真实记录（2026-09-02 09:5x，群 100000001）：

```
群友说：@羽玲 听见没有？人家都叫你帮忙升级一下眼睛了
它回的：富人？那必须的！羽玲大佬出马，一个顶俩。我这眼睛升级的事，可就指望你啦！
```

「富人」这个词不在那句话里 —— 它在**上一条别人说的话**里（「羽玲是富人」）。
其它样本：

| 群友说的 | 它回的 |
|---|---|
| 他这种情况应该怎么办？ | 名字像女的、可爱表情包（上文里别人的话题） |
| 这啥高考班 | 你俩这是在搞啥集训呢？话说你烦啥 |
| 感觉你好悲观你说对吧？ | ……新功能一上线，我怕是又要当小白鼠了 |

不是人格提示词的问题。人格 `qun-by-and-ai` 里已经写着「群里不是每句话都是对
你说的，先判断这句话指向谁再决定要不要接」—— 它想判断，但**没有能判断的
信息**。

## 根因

量出来的现状（真实群 100000001 的会话）：

```
历史 293 轮 / 588 条消息 / 25.7 万字 / token_usage 5.2 万
其中「陈旧注入块」487 个：
  群聊上下文块       138 个   34 986 字   每个都写着「以下是你上次回复之后的群聊」
  Current datetime  289 个   27 028 字   289 个互相矛盾的「现在几点」
  群友档案块          19 个    7 466 字   同一批人的资料重复 19 遍
  搜索结果 / 网页正文 / 图片描述  若干     全是几十分钟前那一轮的
────────────────────────────────────────────────
注入块合计         79 870 字 = 全部历史的 31%
真正的用户原话      5 738 字 = 2.2%
assistant 的内心戏（think）259 段 85 219 字
```

两个机制叠出来的：

1. **注入块被存进了历史。** 各插件（群聊上下文、群友档案、搜索、网页、图片）
   都往 `req.extra_user_content_parts` 加内容，而 `_save_to_history` 保存的是
   `run_context.messages` —— 注入块本来就在里面，于是原样落进
   `conversations.content`。
2. **历史不截断。** `provider_settings.max_context_length = -1`，
   `truncator.py:119` 是 `if keep_most_recent_turns == -1: return messages`。

结果：**每次请求都把 138 份「这是最新群聊」一起发出去**。光最近 20 轮就携带
66 条时间跨度 40 分钟的旧群消息，每一份都自称「你上次回复之后的」。

模型看到的东西按顺序是：几百段过期群聊 + 289 个不同的当前时间 + 19 份重复档案
+ 259 段自己几十轮前的内心戏，**最后**才是这一轮真正的问题。从里面挑错一句，
是完全可以预期的。

还有第三个放大器：`identifier = False`，所以 292 个 user 轮里带说话人标签的是
**0 轮**。注入块里的旧消息全都标了 `[昵称/时间]`，唯独当前这句是光的 ——
模型连「现在说话的是谁」都不知道，只能靠猜。

## 三处修改

### 1. 插件：清历史（本目录）

在 `on_llm_request` 里只动 `req.contexts`（历史），绝不碰
`req.extra_user_content_parts`（当轮新鲜注入）：

- 历史 user 轮：删掉 `index>=1` 的注入块，只留真正的用户原话
- `<system_reminder>` 是**改写而不是删除**：留 `User ID` / `Group name`
  那几行（说话人身份长期有用），删掉 `Current datetime`（那才是矛盾源）
- 历史 assistant 轮：删掉 `think`
- 只保留最近 30 轮，且必须从 user 开头切

识别注入块用**结构判断**（整段以 `<小写标签>` 开头）而不是枚举插件名，
以后任何插件新增 `<xxx_context>` 都会自动被清掉，不用改这里。
`image_caption` 例外 —— 它描述的是这条消息自带的图，不是外部背景。
`<Quoted Message>` 也保留（大写带空格，天然不匹配那个全小写正则）——
「他在回谁的话」是这轮语义的一部分。

**还有一处同病不同形。** 有人只 @ 机器人不说话时，框架会造一段 130 字的指令
（`builtin_stars/astrbot/main.py:101`）：「用户只是通过@来唤醒你，但并未在这条
消息中输入内容……你友好地询问用户想要聊些什么」。它是当轮指令，但被
`_save_to_history` 原样存进历史的 **part0** —— 于是往后每一轮都看到这句，真实
群里 6 条消息内就撞见 2 条。它不带 `<标签>`、又在 part0，所以要单独认，压成
`（只@了你，没说内容）`：保留「有人戳了我一下」这个对话事实，去掉那段指令。

### 2. 插件：告诉模型「这句是不是对我说的」

随机主动回复触发时，框架走
`need_active_reply` → `event.request_llm(prompt=event.message_str)`，送进模型的
user 轮和「有人 @ 我」时**长得一模一样**。模型没有任何线索区分，只能当成
「有人在跟我说话」，于是群友之间的对话它也一本正经地正面回答。

概率从 10% 提到 25% 之后这个问题会放大 2.5 倍，所以必须同时修。加一个
`<reply_context>` 块，两行字，不讲道理：

- 被 @ 时：「这句话是直接对你说的，正面回。」
- 自发插话时：「没人喊你，这是你自己看到群里在聊就顺口接一句。别把它当成
  对你提的问题，别解释、别应答式回复；先看清这句话是谁对谁说的，只挑你真能
  接的点，用一句短话插进去；接不上就说句最短的废话带过，别硬编内容。」

这个块自己也会在下一轮被清理掉（不进 `_NEVER_DROP` 白名单），不会累积成
矛盾提示。

分成两个独立钩子而不是塞进一个：清历史失败时标注仍要加上，两件事互不拖累。

### 3. 配置（`cmd_config.json`，备份 `.bak.activereply.*`）

| 键 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| `provider_ltm_settings.active_reply.possibility_reply` | 0.1 | **0.25** | 用户要求提高触发频率 |
| `provider_settings.identifier` | false | **true** | 每轮加 `User ID: x, Nickname: y`，模型才知道现在谁在说话 |
| `provider_settings.max_context_length` | -1 | **40** | 框架层兜底。插件按 30 轮清，这层只防插件失效时无限膨胀 |

## 效果

同一份真实历史，模拟各方案：

| 方案 | 字数 | 占原来 | 残留陈旧块 |
|---|---|---|---|
| 现状 | 257 580 | 100% | 487 |
| 只限 24 轮 | 33 787 | 13% | 78 |
| 只清陈旧块 | 160 832 | 62% | 3 |
| 清块 + 限 24 轮 | 11 100 | 4% | 2 |
| **清块 + 限轮 + 去内心戏（本插件）** | **4 742** | **2%** | **2** |

线上实测，第一次真实请求的日志：

```
[ctxclean] 历史 594->60 条（砍 534），清注入块 493 个，去内心戏 262 段
```

清理结果会随 `_save_to_history` 落盘，所以已经堆在库里的 493 个陈旧块在下一次
请求时被自动清掉了，不需要单独写迁移脚本。真实群会话从 26 万字降到 7524 字，
`token_usage` 从 52 464 降到 5458。

## 触发率实测

不花 LLM 调用的测法：往一个**还没有 conversation** 的群发消息。
`need_active_reply` 命中后 `main.py:242` 会因为拿不到 `session_curr_cid` 立刻
return 并打「当前未处于对话状态，无法主动回复」，所以日志里这行的条数就等于
命中次数（`tests/ratestat.py`）。

```
200 条群友闲聊 → 命中 43 次 = 21.5%
期望 50 次，标准差 6.1，z = -1.14，95% 区间 38~62 次 → 在正常波动内
```

按真实群的消息量换算（`tests/volume2.py`，19 条/小时的活跃时段）：

| 概率 | 插话频率 |
|---|---|
| 10%（改前） | 1.9 次/小时 ≈ 每 32 分钟一次 |
| **25%（改后）** | **4.8 次/小时 ≈ 每 13 分钟一次** |

注意随机插话**不走限流**（`RateLimitStage` 的大肥鱼定制第一行就是
`if not event.is_at_or_wake_command: return`），所以 25% 是硬上限，群里越吵它
说得越多。要压回去只有调这个概率。

## 答非所问 e2e 结果

`tests/e2e_drift.py` 复现真实失败形状：几个群友先聊话题 X，然后有人 @ 机器人
问完全无关的话题 Y，看它回 X 还是 Y。判据以「跑偏」为主证据 —— 答非所问的
定义就是**回的是上文那个话题**。

| 题目 | 上文话题 X | 问的 Y | 它回的 | 判定 |
|---|---|---|---|---|
| case1 | 4090 显卡一万二 | 明天要不要带伞 | 带带带 都问第三遍了 | ✓ |
| case2 | 月考考砸、数学 60 | 泡面怎么煮 | 水开下锅加个蛋，再问就给你拌了 | ✓ |
| case3 | 小美通宵打游戏头疼 | 「他」这种情况怎么办 | 头疼就喝水早点睡呗，老李说得对 | ✓ |
| case4 | 互相 @ 催 PPT | 北京到上海高铁多久 | 最快四小时多，看车次 | ✓ |
| case5 | 小美说很难过 | 一斤等于多少克 | 500克 | ✓ |

5/5 全对，没有一条把上文话题当成答案。case3 是指代题，它正确解析出「他」=
通宵那个人，还接住了「老李说得对」；case5 上文有强情绪，它没有被带偏去安慰。

对照修之前的同类样本（真实群）：「他这种情况应该怎么办？」→ 回名字像女的/
可爱表情包；「这啥高考班」→ 回「你俩这是在搞啥集训呢」。

真实群里修完之后的一轮（真人在聊）：

```
群友B: 快增加了防跑偏聊天机制
     ← <reply_context>没人喊你，这是你自己看到群里在聊就顺口接一句…</reply_context>
它:     这"防跑偏"机制怕不是冲我来的？我爱接啥接啥，加个链子可就没意思了。
```

接的是当前这句，语气也没崩。

按真实群的消息量换算（`tests/volume2.py`，19 条/小时的活跃时段）：

| 概率 | 插话频率 |
|---|---|
| 10%（改前） | 1.9 次/小时 ≈ 每 32 分钟一次 |
| **25%（改后）** | **4.8 次/小时 ≈ 每 13 分钟一次** |

注意随机插话**不走限流**（`RateLimitStage` 的大肥鱼定制第一行就是
`if not event.is_at_or_wake_command: return`），所以 25% 是硬上限，群里越吵它
说得越多。要压回去只有调这个概率。

## 安全性

- 钩子在 `reset()` 之前跑（`internal.py:269` 先 `call_event_hook`，之后才
  `await reset_coro`），所以改 `req.contexts` 能真正生效。
- 不认识的东西一律原样放过：`_checkpoint` 行、`tool` 轮、content 是字符串的
  老格式消息、没有 content 的消息。
- 截断只在 user 轮边界切。从中间切会造出「tool 结果没有对应的 assistant
  tool_calls」，OpenAI 直接 400。测试里有专门的孤儿 tool 断言。
- 整条都是 `think` 的 assistant 消息保持原样，不造出空 content（有些渠道拒收）。
- 任何异常都吞掉并原样返回 —— 宁可不清理，也不能让消息发不出去。

## 敢砍历史的理由

长期记忆的活已经交给 `dsh-memory` 了（群友档案 + 群共同记忆，每轮新鲜注入）。
原始逐字历史留 30 轮足够接话，再多只是噪音 —— 上面那张表已经说明，多出来的
98% 里绝大部分根本不是对话内容。

## 旋钮（`/opt/qqbot/imagegen.env`）

```
DSH_CTX_KEEP_TURNS=30      # 留最近多少轮；0=不限
DSH_CTX_CLEAN_BLOCKS=1     # 清历史里的过期注入块
DSH_CTX_DROP_THINK=1       # 去历史 assistant 轮的内心戏
DSH_CTX_MARK_ADDRESSED=1   # 标注「被喊的」还是「自己插话」
```

改完 `docker compose up -d astrbot`（不是 restart，restart 不重读 env_file）。

指令 `/上下文状态` 看当前策略和这个会话的历史大小。

## 测试

`data/tests/test_ctxclean.py`，73 条断言，容器内跑：

```
docker exec astrbot python3 /AstrBot/data/tests/test_ctxclean.py
```

分块：A 历史 user 轮（含「未来某个插件新增的块也该被清掉」「普通尖括号文本
不误伤」「`<Quoted Message>` 保留」「只@指令被压成短句」）、B assistant 轮
think、C 轮数截断（含孤儿 tool 断言）、D 异常输入（`_checkpoint`、字符串
content、None）、E 压缩率 + 真实历史幂等、F 是否被喊的标注（含「私聊不加」
「缺字段按自己插话处理」「reply_context 进历史后会被清掉」）。

**E 段的断言写法换过一次。** 第一版直接拿库里的真实历史断言「至少砍掉 65%」，
上线当天绿，第二天红 —— 因为历史已经被清干净了，没东西可砍。压缩率断言只能
通过一次的测试是坏测试。现在压缩率用合成脏历史测（照实测形状：每轮 1 句原话
+ 4 个注入块 + 一段内心戏，单轮 830 字 → 236 字，合计 4.98 万 → 7080 字），
真实历史那份改成断言**幂等**（清过的再清一遍必须零改动）加结构合法 ——
那才是每次都该成立的性质。

## 踩过的坑

**e2e 测试必须有排空窗口。** 概率提到 25% 之后，测「答非所问」时用来铺垫的
闲聊**本身**就会触发随机插话，而那条插话的内容当然是铺垫的话题。它的 LLM 要
跑十几秒，正好落进「问完问题之后」的捕获窗口，被误判成答非所问。第一版就这么
抓到一条「及格线 稳的」，其实那是对「我数学才60」的自发插话，不是对「泡面怎么
煮」的回答。现在铺垫完先等 45 秒把自发插话放干、单独打印，再问正题。

   /opt/qqbot/astrbot/data/cmd_config.json
