# 83 · 内在状态总线（P0：只读聚合观测）（2026-09-13）

## 起因

群主原话：

> 有没有一种方案可以整合目前的主动行为，比如说情绪欲望等，而不再是独立分支的独岛

这不是审美问题。到 2026-09-13，机器人有 **11 个各自独立的状态存储**、**33 个插件往同一次请求里各塞各的块**，
而**没有任何一处代码知道**这一轮有几个「岛」在说话、它们互相矛不矛盾、加起来占多少字。

本文记录：先把「独岛」量化清楚（第一节），再落地一个**零行为变更**的观测层（第三、四节），
以及它要回答的三个问题和据此决定 P1 合并范围的判据（第五节）。

---

## 一、先量化「独岛」到底有多独

### 1.1 11 个状态存储，各有各的格式

| 状态 | 存储 | 格式 | 读者数 |
|---|---|---|---|
| 情绪 | `dsh_emotion_state.json` | JSON（整体覆写） | 4 |
| 欲望 | `dsh_desire.db` | SQLite `drive_state` | 3 |
| 关系 | `dsh_social.db` | SQLite `relations` | 6 |
| 逆反 | `dsh_agency.db` | SQLite `agency_state` | 2 |
| 疲劳 | `dsh_fatigue_state.json` | JSON | 2 |
| 兴趣 | `dsh_interest_state.json` | JSON | 5 |
| 自身利益 | `selfworth.json` | JSON（私有账本） | 2 |
| 群感知 | `dsh_awareness.db` | SQLite `event` | 3 |
| 自我认知 | `dsh_selfaware.db` | SQLite `sense_event` | 2 |
| 效果 | `dsh_effect.db` | SQLite | 2 |
| 记忆 | `dsh_memory.db` | SQLite | **15** |
| 主动开口额度 | `dsh_proactive_state.json` / `dsh_initiate_state.json` | JSON | 2 |

**第一个结论：总线早就存在了，只是以最差的形态存在** —— N×M 的点对点读文件。
`dsh_memory.db` 一个库有 15 个读者、`dsh_social.db` 有 6 个、`dsh_interest_state.json` 有 5 个。
每个读者都自己实现一遍「打开、解析、读不到就当中性」，而这份实现**只在自己插件内部有测试**。

### 1.2 已经有人在手搓「总线」了，而且是第三次

| 插件 | 它做了什么 | 代价 |
|---|---|---|
| `dsh-guard` | `mood_logic.MoodReader` 读情绪/欲望/关系/逆反/疲劳 → 压成一个「宽容度」标量 ∈ [-3,+3] | 116 项测试，五路衰减口径必须跟各自的 owner 逐字对齐 |
| `dsh-agency` | 读情绪/兴趣/欲望/关系 → 渲染一个 `<agency_state>` 块 | 又实现了一遍解析 + fail-neutral |
| `dsh-mind` | 本次要写的第三个 | —— |

前两个都是**对的**（都用只读 + 失败即中性，都在生产里跑住了），但第三个再手搓一遍就是浪费。
所以这次的定位不是「再写一个读者」，而是「把这件事变成一次性的」。

### 1.3 一次请求里塞了多少东西

实测（当日日志窗口）：**33 个插件**通过 `extra_user_content_parts` 注入，**约 50 种块标签**，
状态类块的预算上限合计约 **3270 字/轮**：

```
agency 620 + selfaware 1400 + awareness 810 + social 260 + desire 180 = 3270
```

（历史侧另有一笔：`dsh-ctxclean` 上线前 25.7 万字历史里注入块占 31%，见 docs/40。）

### 1.4 情绪这块尤其「贫信息」

同一窗口内 `dsh-emotion` 注入 **252 次**，其中 `curious(2)` 一种占了 **186 次（74%）**。
也就是说「情绪」这个岛大多数时候只是在重复同一个词，但它自己占着一整个块的位置。

### 1.5 还有一个岛**根本看不见**

`dsh-spine`（脊梁）的「被牵着走多少轮」状态**只存在于内存**，没有文件、没有表。
任何其它插件都读不到它，AstrBot 一重启它就归零，而它却在影响行为。

**这是「独岛」里最坏的一类：不是读起来麻烦，是压根读不到。**
P0 把它明确记成 `unreadable`，而不是当成「中性」——把「读不到」和「就是平静」混为一谈，
会让后面的统计凭空乐观。

## 二、方案：三层，但**先只做第一层**

```
① 传感器         ② 总线                ③ 仲裁
各自的状态库  →   只读聚合快照    →   单一出口
（谁的状态谁拥有）（本次 P0 建的）（当前仍然是 N 个出口）
```

为什么不直接跳到 ③ 合并注入块 —— 这个仓库有两条同族教训：

- **docs/71（识图等待该不该省）**：按「本轮夹没夹识图」分组量出 8.6s vs 25.8s，
  据此改了策略；回放 1337 次历史识图后发现图龄中位只有 17.4s（等待其实是对的），
  新加的两个例外吞掉 81% 的收益，**实测只省 15%**。分组相关 ≠ 因果。
- **`dsh-initiate` 合成事件上线**：为了让它发出去的消息不被自己的下游插件误伤，
  要给 decide / ctxclean / mention 各打一处兼容补丁。**合并出口的代价不在写代码，在兼容。**

所以 P0 的产出**不是行为，是数据**。它只回答三个问题：

1. 一次对话里到底有几个岛在说话？
2. 合并成一个块是多少字，现在各自为政又是多少字？（收益的**上限**）
3. 岛与岛之间有多少条**真冲突**？

答不出这三点就动手合，等于把 docs/40 的「注入块堆积」重演一遍。

## 三、P0 做了什么

新增 `plugins/dsh-mind/`（`mind_logic.py` 纯逻辑 + `main.py` 插件壳）。

### 3.1 它读什么

| 岛 | 判据（「亮着」的条件） |
|---|---|
| 情绪 | 有活跃情绪且未过期 |
| 欲望 | 驱动强度高于基线（底层驱动 `continuity/fear` 不算） |
| 关系 | 有该群该人的关系记录 |
| 逆反 | 逆反值高于基线 |
| 疲劳 | 档位 ≥ 1（优先取 `dsh_fatigue_level` extra，取不到才用答复次数代理） |
| 兴趣 | 今日馋 或 该群热词 |
| 自身利益 | 近期有损己发言 |
| 群感知 | 窗口内有事件 |
| 自我认知 | 窗口内有能力失败 |
| 行动额度 | 今日已开口/主动次数 |

十路摆出来是 **10** 个；第 11 个是上面说的 `dsh-spine`（记为不可观测）。
日志里统一写 `岛=N/11`，**分母固定**，这样「少了一个岛」会自己显形，而不是悄悄变成 4/4。

### 3.2 它输出什么

每个 LLM 轮次**恰好两样东西**：

1. **一行日志**（这是 P0 的主要产物，因为日志已经有现成的分析脚本）：
   ```
   [mind] gid=476573490 岛=4/11 注入块=4/2330字 草稿=118字 冲突=0 连接 96(基线16)|今日馋白米饭、蛋糕|...
   ```
2. **一条观测记录**（自己的 SQLite `/AstrBot/data/dsh_mind.db`），
   存的是**每轮的字数、块数、岛数、冲突数、草稿长度，以及每个块的「标签 + 字数」**。

**它绝不存别人的原文。** `<scene>` 之类块里装的是群聊原文，把它复制进一个新库，
等于凭空多出一份群聊副本，而且这个副本没有 `dsh-ctxclean`、没有过期清理。

### 3.3 硬边界（写在代码里，不是写在文档里）

| 边界 | 实现 |
|---|---|
| 绝不注入 | `main.py` 不 import `TextPart`、不碰 `req`；`DSH_MIND_MODE=inject` 被**明确拒绝**并写 WARNING，退回 observe |
| 绝不写别人的状态 | 外部状态一律只读 JSON / SQLite `mode=ro`（`dsh-emotion` 是整体覆写 JSON，抢写必然丢状态） |
| 绝不阻止回复 | 整个观测体包在 `try/except BaseException` 里，只计数不出声 |
| 失败即中性 | 读不到就当平静，记进 `errors`；「无该群/无此人记录」与「读取失败」分开记 |
| 权限 | `/心智状态` 只对群主/群管理/机器人管理员开放（公开等于给群友一份攻略，与 `/禁言状态` 同理） |
| 顺序 | `priority=-1` —— AstrBot 是 `sort(key=lambda h: -priority)`，数字大的先跑，所以 -1 排在**所有注入器之后** |

最后一条是**正确性前提**，不是洁癖：排在注入器之前看到的是半成品，
量出来的块数和字数会**静默偏小**，不会报任何错。所以它有一条专门的测试守着（见 4.2）。

## 四、验证

### 4.1 纯逻辑测试（宿主机 py3.8 就能跑）

```
$ python3 dsh-mind/test_mind.py
MIND_LOGIC_TEST_OK passed=90 failed=0
```

覆盖：五路衰减口径与各自 owner 对齐（含「updated_at 在未来也不放大」）、档位阈值、
疲劳代理的窗口边界与「别人追问不算我的」、请求形状解析（`TextPart`/裸 str/脏数据）、
岛判定与排序、7 条冲突规则**每条都带反向用例**、草稿预算（预算 5 字也要返回合法块）、
以及真实 fixture 下的只读读取器 —— 包括**路径全坏、JSON 坏、extra 抛异常**三种故障下
「不抛、记 errors、仍返回合法快照」，还有一条**「跑完之后 fixture 的 JSON 一个字节都没动」**。

### 4.2 钩子级集成测试（要在 astrbot 容器里跑）

```
$ sudo docker exec astrbot python3 test_mind_hook.py
MIND_HOOK_TEST_OK passed=18 failed=0
```

跑**真实的 `observe` 处理器**（假事件 + 假 req，不碰真群、不发消息），抓的是纯函数测试抓不到的东西：

- `req.extra_user_content_parts` **原样返回**、`req` 没有多出任何字段（P0 的「零行为变更」是真的）；
- `get_extra` 抛异常 → 退回中性但**继续观测**；连 `gid` 都拿不到 → 吞掉、计数、不入库；
- 非生效群与合成事件（主动开口/探头）**不入库**，否则统计口径会被稀释；
- 观测库里**没有注入块原文**（直接扫 DB 文件字节）；
- `/心智状态` 对非管理员闭嘴；
- **从框架的 `star_handlers_registry` 里读回 `priority`，断言它等于 -1**。

> 踩坑：`handler.handler_module_path` 是**字符串**（`'dsh_mind_pkg.main'`）不是模块对象，
> 第一版按模块取 `__name__` 拿到空串，检查静默失效（`passed=16 failed=1` 里那 1 条就是它）。

### 4.3 生产加载

```
[Core] Loading plugin dsh-mind ...
[mind] 自检：读到 欲望,疲劳(代理),兴趣,自身利益,群感知,自我认知,行动额度；无记录项 3；读取失败 0
[mind] 已加载：开 模式=observe 群=476573490 预算=900字 采样=1.00 观测库=/AstrBot/data/dsh_mind.db
```

自检那行是刻意的：**读不到的状态必须在启动时就喊出来**，而不是等到第二天看统计时
把「读不到」误读成「它就是平静」（1.5 节那个坑）。

部署后 `sudo docker ps` 确认只重建了 `astrbot`（`docker compose up -d --no-deps astrbot`），
napcat 的 `CreatedAt` 未变。

### 4.4 开销：每轮 7 毫秒

群主此前明确抱怨过回复慢（docs/82），所以观测层**必须自证不是新的负担**。
在容器里拿生产状态库实测 50 轮：

| 项 | 耗时 |
|---|---|
| 每轮 `observe` 全程（读 11 个状态源 + 算冲突 + 写观测库） | **7.2 ms** |
| 其中纯读 11 个状态源 | 3.1 ms |
| 占一次回复（中位 6000ms）的比例 | **0.12%** |

### 4.5 上线后第一批真实数据（13 轮）

> 这才是 P0 存在的意义 —— 下面这些数，在写这个插件之前**没有任何地方量得出来**。

| 指标 | 中位 | P90 | 最大 |
|---|---|---|---|
| 注入块数 | **19** | 20 | 22 |
| 注入字数 | **4747** | 4953 | 4992 |
| 同轮历史字数 | 6544 | — | — |
| **注入字数 / 历史字数** | **69.3%** | — | — |
| 活跃状态岛 | 5 / 11 | 5 | 5 |
| 统一草稿长度 | **136 字** | 155 | 155 |

三个立得住的结论：

1. **「独岛」是字面意义的**：每轮往 prompt 里塞 **19 个块、约 4700 字**，
   而其中真正「活着的」状态岛只有 **5 个**。剩下 14 个块是不管状态死活都照塞的内容块。
2. **注入已经比历史还占地方**：注入占同轮历史字数的 **69.3%**。
   docs/40 当年量的是「历史里注入块占 31%」，现在这个比例是在 `dsh-ctxclean` **已经上线**的前提下量到的。
3. **大字块根本不是「情绪欲望」**。按总字数排的块 Top：

   | 块 | 字数 | 属于 |
   |---|---|---|
   | `member_memory` | 514 | 记忆 |
   | `join_review_history` | 472 | **入群审核历史** |
   | `current_machine_self` / `self_capabilities` / `recent_self_actions` / `long_term_machine_self` | 414 / 394 / 306 / 302 = **1416** | 机器自我（4 个块） |
   | `style_samples` | 265 | 说话风格 |
   | `agency_state` / `scene` / `desire_state` / `social_context` | 207 / 191 / 137 / 123 | 状态岛 |

   **「机器自我」四个块合计 1416 字，比全部状态岛（ags+desire+social+scene ≈ 658 字）还多一倍。**
   所以「整合情绪欲望」这一刀能省下的字，远小于字面直觉 —— 真正的大头在记忆/自我/风格。
   这条直接改写 P1 的靶子（见第五节）。

4. **`desire` 岛常年钉在天花板上**：`connection` 驱动连续多轮都是 **100.0**（基线 16，半衰期 6h），
   每来一次直接接触 +6 → 它几乎永远在满值。这就是 1.4 节 `curious(2)` 占 74% 的同一种病：
   **岛在说话，但不提供任何新信息**。日志里它每轮都显示 `连接 100(基线16)`。

## 五、它要回答什么，以及据此怎么决定 P1

跑够量（建议 ≥ 3 天、≥ 200 轮真实对话）后，`/心智状态` 与观测库会给出四组数：

| 要看 | 怎么读 | 决定什么 |
|---|---|---|
| **岛数分布** | 「5岛=61｜6岛=38｜4岛=12」 | 中位 ≥ 4 说明确实在群殴，合并有收益；中位 ≤ 2 说明大多数轮次只有一两个岛在说话，**合并的收益远小于风险** |
| **注入字数 vs 草稿字数** | 「注入 4747 字 → 草稿 136 字」 | 这是收益**上限**（草稿不含人格/事实注入） |
| **冲突数** | 「冲突 N 条（M% 的轮次）」 | 冲突是合并的**理由**：孤岛互相矛盾时模型只能瞎猜。冲突集中在哪两条规则上，P1 就先合哪两个岛 |
| **块 Top 与字数** | 见 4.5 的表 | 找出「字最多但状态贡献最小」的块 —— **那才是第一刀的对象** |

首日数据已经把靶子挪了位置：按字排下来，**第一刀该切的是「机器自我」那四个块（1416 字）
与 `join_review_history`（472 字）**，而不是情绪欲望（合计约 658 字）。
注意这四块都来自同一个插件家族（`dsh-selfaware` / `dsh-selfworth`），
所以它们**本来就该是一个岛** —— 一个插件往同一轮塞四个块，是真正的「分家」而不是「整合问题」。

**叫停条件（写在这里，免得将来只看到想看的数）**：如果 P90 岛数 ≤ 2、
或冲突率 < 5%、或「状态类块」的字数占比 < 20%，那么结论就是**不合并**，
把 P0 当长期体检表留着，转去做单点优化。

## 六、下一步

| 阶段 | 做什么 | 前提 |
|---|---|---|
| **P1** | 用一个 `<mind_state>` 块替换被判定「重复且低信息」的几个岛，每插件一个 env 开关，灰度 3 天 | 第五节的数据支持。**首日数据把第一刀指向了「机器自我」的四个块** |
| **P2** | 统一写侧 `MindStore`（各插件写自己的表，但同一套 API/衰减/清理），老的读法保留兼容 | P1 稳住 |
| **P3** | 统一动作闸门：`initiate` / `proactive` / `followup` / `poke` 现在各自算额度，合成一个「冲动」标量 + 每策略独立闸门 | P2 稳住 |

**不做的**：把 54 个插件重写成一个「大脑」插件。那会丢掉每个插件各自的文档、测试、
回滚点，也会丢掉「新东西先跑影子模式」的能力 —— 而影子模式是这个仓库唯一反复救命的东西。

**永远不进总线的**：权限/禁言/安全/出口审核。`dsh-guard` 的 HARD_KINDS
（违法/广告/色情/刷屏/直接辱骂/围攻）**永远不看心情**，这条边界与总线无关。

## 七、这次踩的坑

1. **镜像里的群号是脱敏占位符**（`100000001`），生产靠 env 给真值。
   忘了配的表现是「插件装上了、自检也过了、但一行都不记」——**静默失效**。
   钩子测试里专门写死了这一点（测试自己设 env）。
2. **改 `imagegen.env` 必须 `docker compose up -d`**，`docker restart` 不会重新读 env file
   （env 是容器创建时注入的）。用 `--no-deps` 保证不连带重建 napcat。
3. 观测层的异常有**两个层次**：外层 `try/except BaseException` 保证不影响回复，
   内层（`get_extra` 适配器坏了）退化成中性但继续观测。混成一个的话，
   适配器坏了就再也看不到任何数据，而日志里只有一行 debug。
4. **「读不到」不等于「平静」**。`errors` 里区分「无该群/无此人记录」与「读取失败」，
   前者是正常的空状态，后者是故障。混在一起会让体检表永远显示健康。
   首日实测里 `读错=1` 全部是「关系无此人记录」（群友还没被记过账），**零故障** ——
   这个区分第一天上就救了场：不然会去查一个不存在的 bug。
5. **★ 一个每轮都成立的指标，等于没有这个指标。**
   第一版把「注入块数 ≫ 活跃状态数」当成第 7 条冲突规则，上线当天真实流量里
   **每轮都成立**，冲突率恒等于 100%。已改成独立的「观测」列（日志里打 `[注:块20≫状态5]`），
