# 72 · 机器人把 API 原始报错当回复发进群了 11 次

**日期**：2026-09-13
**改动**：`dsh-leakguard` 1.0.0 → 1.1.0
**一句话**：它 11 次当着全群的面贴出自己的堆栈——带 `traceId`、带「余额不足」、
带 `retryAfterSeconds`。真人不会这样。现在一律拦成沉默。

---

## 一、怎么找到的：本来在量「套路话术」，结果量出了别的东西

目标是「更像真人」，其中一项是**套路话术**。我先量回复的重复集中度：

| | 条数 | 唯一率 | 最高频 15 条占比 |
|---|---|---|---|
| 大肥鱼 | 10149 | 75.1% | 9.6% |
| 真人 | 11483 | 87.0% | 5.4% |

看着像"机器人更爱重复"。但 n-gram 去重率**几乎一样**（三字组 56.0% vs 55.2%，
大肥鱼甚至更高），说明它的**聊天内容并不比真人单调**。

于是去看各自最高频的到底是什么：

```
大肥鱼：  [引用消息] / 慢点，还有 / 秒冷却 / [At:…] / 发不出声音：这句话不太适合念出来，换一句嘛
真人：    ？ / 神了 / 😋 / 🤔 / 来个妹妹 / 6 / 666
```

**真人的高频全是聊天反应；机器人的高频全是系统提示和报错。** 顺着这条线往下列，
就看到了这些：

```
 11× LLM 响应错误: All chat models failed: APIStatusError: … traceId: 'trace_c5917bbf-…'
  9× APIStatusError: / Error / code: / 402 / {'code': / 'INSUFFICIENT_BALANCE' / 余额不足
```

我当时的第一反应是"这是日志里的记录吧"，于是去查它有没有走 `Prepare to send`：

```
[2026-09-06 18:42:44] Prepare to send - 难谓言/2774067216: LLM 响应错误: All chat models failed: APIConnectionError: Connection error.
[2026-09-08 00:31:24] Prepare to send - 难谓言/2774067216: LLM 响应错误: All chat models failed: InternalServerError: <html>
[2026-09-10 01:57:39] Prepare to send - 难谓言/2774067216: LLM 响应错误: All chat models failed: APIStatusError: Error code: 402 - {'code': 'INSUFFICIENT_BALANCE', 'message': '余额不足', 'data': {'retryAfterSeconds': 6}, 'traceId': 'trace_19c89f88-…'}
   … 01:58:02 / 01:59:20 / 01:59:39 / 01:59:52 / 02:00:31 / 02:00:48 / 02:01:43 / 02:01:57
```

**走了。11 条全部真的发进了群。** 2026-09-10 01:57~02:01，**四分钟内连发 9 条**。

这是比泄露人格标题**更硬**的破绽：
- 真人不会贴 `traceId`，更不会贴一坨 JSON；
- 它等于告诉全群「我是个接了 API 的机器人，而且我现在余额不足」；
- 四分钟里连发九遍，任何在场的人都会确定这是个坏掉的程序。

---

## 二、根因

AstrBot 核心 `/AstrBot/astrbot/core/agent/runners/tool_loop_agent_runner.py`：

```python
# 行 631
"All chat models failed: "
# 行 891
f"LLM 响应错误: {llm_resp.completion_text or '未知错误'}"
```

采集到的异常被塞进 `llm_resp.completion_text`，然后**照常经过 respond.stage 发出去**——
框架没有区分"模型回了一句话"和"模型调用崩了"。

**不patch框架**：那是第三方代码，升级会覆盖，而且改了之后下一个升级点会很难受。
在出口拦——`dsh-leakguard` 本来就是这个位置的东西（它已经在拦人格标题泄露）。

---

## 三、为什么是沉默，不是一句安慰话

备选是发一句人话，比如「我这边卡住了，等一下」。**否掉了**，因为报错是**成串来的**：
09-10 那次四分钟九条。一句固定话术连发九遍，比贴报错**更像机器**——
真人遇到这种情况的默认行为是**没吭声**。

所以处理是 `event.clear_result()` + `event.stop_event()`：这一条不发。
真相留在日志里（`WARNING`，带原文前 160 字），要查随时能查到。

**这一条不受 `DSH_LEAKGUARD_MODE` 影响。** 它不是"人格泄露"（那种可以 strip 掉片段
再发），是"机器人坏了"——任何模式下都不该见群。

---

## 四、判据：怎么做到既不漏又不错杀

技术词在正常聊天里是会出现的：机器人有时候跟群主聊代码，
「你那个 traceId 打出来我看看」「我就余额不足，穷」都是**正常对话**。
所以分两档，**只有"整句就是一段报错"才拦**：

```python
_INFRA_STRONG = (           # 强指纹：命中一个就够，正常聊天里绝不会出现
    "LLM 响应错误", "All chat models failed", "APIStatusError",
    "APIConnectionError", "APITimeoutError", "InternalServerError",
    "RateLimitError", "Traceback (most recent call last)",
)
_INFRA_WEAK = (             # 弱指纹：要同时中两个才算
    "INSUFFICIENT_BALANCE", "余额不足", "traceId", "Error code:",
    "retryAfterSeconds", "'code':", "'message':",
)
```

### 测试用真实数据两头夹

`plugins/dsh-leakguard/test_infra.py` 的正例是**生产日志里那 11 条真实报错原文**，
负例是**大肥鱼真实说过的 8662 句话**——两头都来自生产，所以这个测试量的就是真实误伤率：

```
LEAKGUARD_INFRA_TEST_OK
  正例 11 条真实报错 → 全部拦下
  负例 8662 条真实聊天 → 0 误伤
  边界 5 条含技术词的正常聊天 → 判对
  命中行为：clear_result + stop_event（沉默，不是换一句安慰话）
  其中 402 余额不足 9 条、连接/超时/5xx 2 条
```

另外把检查挪到了 `is_model_result()` **之前**——报错那一条未必被标成 model result，
而它恰恰是最不能见群的。

## 五、部署时踩的两个坑

### 1. 镜像的群号是脱敏占位，直接 cp 会让插件失效

`dsh-leakguard` 的源码镜像里是 `DSH_LEAKGUARD_GROUPS="100000001"` /
`DSH_LEAKGUARD_OWNER="2774000001"`（占位），**生产是真号**
（`476573490` / `2774067216`）。`sudo cp 镜像 → 生产` 会让它认不出主群，静默失效。

改法：**用镜像内容 + 生产的真实 ID 行拼出生产文件**，再 diff 确认差异只有本次改动。
（这次拼完还发现镜像的 docstring 里把真实群友名脱敏成了「群友C」，
会把生产里的真名换掉——又按行还原了那两行，让改动只剩我这一处。）

**这条对所有 `dsh-*` 插件都成立，脱敏程度并不一致**：`dsh-imgctx` 的镜像用的是真号，
`dsh-leakguard` 用的是占位。所以**每个插件部署前都要单独 diff 一次**，
不能凭"上次也是这样"下手。

### 2. metadata.yaml 里一个 ASCII 冒号就能废掉整个 metadata

新写的 desc 里带了 `` `LLM 响应错误: All chat models failed: ...` ``，
**冒号+空格**把 YAML 纯量截断了：

```
[WARN] Failed to load metadata for plugin dsh-leakguard …
       in "/AstrBot/data/plugins/dsh-leakguard/metadata.yaml", line 2, column 245.
       Using default metadata.
```

插件**照常加载**，只是版本变成 `None (None)`、描述丢失、日志里多一条 WARN——
很容易被忽略。改法：desc 用双引号包起来。

**顺手做了一次全量体检**（这类低级错值得变成常规动作）：

```
55 个插件 metadata，解析失败 0 个（修好后）
```

## 六、一条差点让我改错东西的教训：宿主时钟是 UTC，日志是 UTC+8

排查过程中我盯上了另一条线：第一轮修掉的 dsh-memory 长括号
「（每 10 条消息、间隔 15 分钟才整理一次）」**在日志 09-13 00:12:30 还在发**。
生产 `main.py:1959` 明明已经是新文本，pyc 也是新版编译的，两边 md5 一致——
一切证据都说"修复生效了"，但日志说"没生效"。

**真相是时区。** 宿主 `date` 是 UTC，AstrBot 日志是 UTC+8（差 8 小时）：

| 证据 | 宿主（UTC） | 日志（UTC+8） |
|---|---|---|
| 我部署 dsh-memory 的时刻 | Sep 12 16:59:08 | **09-13 00:59:08** |
| 那句长括号出现 | Sep 12 16:12:30 | **09-13 00:12:30** |

**00:12:30 比我的部署早 46 分钟。修复没问题，是我的时间轴整体错了 8 小时。**

差点就去做一次「修一个没有坏的 bug」，而且很可能顺手把好代码改坏。
**判据**：任何"宿主文件 mtime vs 日志时间"的比对，先确认两个时钟的偏移——
`stat` 出来的 mtime 是 UTC，日志里的是 UTC+8。

## 七、可复用的结论

1. **"机器人最重复的话"和"机器人说的话有多单调"是两件事。** 前者一眼能看出问题
   （全是系统提示），后者几乎正常（n-gram 去重率与真人持平）。
   想治「套路话术」，先看**高频榜**，别急着改人设 prompt。
2. **系统提示、报错、指令回执是"客服腔"的主要载体**，不是对话本身。
   这次抓到的两个最高频真文本是 `慢点，还有 N 秒冷却`（103 次）和
   `发不出声音：这句话不太适合念出来，换一句嘛`（60 次）——都还没动，见待办。
3. **框架的错误处理路径要当成自己的出口来审。** 框架把异常塞进 `completion_text`
   是善意（便于排查），但在机器人场景里等于把堆栈念给全群听。
4. **修出口问题的判据要拿生产原文当测试数据。** 11 条真实报错当正例、
   8662 条真实聊天当负例，比手写几个 case 有说服力得多，也才能证明"不误伤"。
5. **同一个镜像，不同插件的脱敏程度不同。** 部署前必须逐个 diff。
6. **YAML 纯量里的 `": "` 会静默废掉 metadata**，日志只给一条容易被忽略的 WARN。
7. **宿主与日志差 8 小时。** 见第六节。

## 待办 / 未解决

- **→ 已由 docs/73 跟进**（`慢点，还有 N 秒冷却` 114 次已换成人话轮换；下面两条仍未动）。
- **另外两个高频系统提示还没治**（本轮只治了报错这一条）：
  * `慢点，还有 N 秒冷却` 103 次 —— **"秒冷却"是个纯机器词**，真人不会这么说。
    但它是限流提示，删了群友会不知道发生了什么；应改成更像人的说法（且要有变体，
    否则只是把一句机器话换成另一句固定的机器话）。
  * `发不出声音：这句话不太适合念出来，换一句嘛` 60 次 —— dsh-voice 的拒念提示。
    同样是需要"听起来像人"而不是"删掉"。
- **验证`拦报错`真的会在生产触发**：装好之后还没遇到新的 LLM 故障。
  `/泄露guard状态` 现在会显示「拦报错 N」；下次故障时看日志有没有
  `[leakguard] 拦下基础设施报错，改为沉默`，以及群里**没有**出现报错。
- 模型自身的口头禅（`想得美` 18 倍 / `才不是` 22 倍 / `行行行` 23.5 倍、
  `大半夜的` 真人 0 次）仍未处理。但它们的**时间聚簇很弱**（最密集一小时也才 7 次），
  属于"习惯用词"而非"复读"，是否真的算破绽需要另行设计判据。
