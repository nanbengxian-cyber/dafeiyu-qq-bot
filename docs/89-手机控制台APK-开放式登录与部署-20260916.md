# 89 · 手机控制台 APK：开放式登录与部署（第一版）

**日期**：2026-09-16
**位置**：仓库 `mobile-controller/`，包名 `com.dafeiyu.controller`，安装后叫「大肥鱼控制台」
**本次产物**：`mobile-controller/build/dafeiyu-controller.apk`（约 645 KB，minSdk 26 / targetSdk 34）

---

## 一、要做什么、为什么

用户需求原话：「把大肥鱼的登录做成开放式的，做成一个 APK，可以输入 QQ 号和密码，
并且通过内置的网页扫码登录」「可以把控制台合并上去」「不要加入我的服务器的任何配置」。

拆开是四条硬要求：

1. **开放式**：APK 不绑死任何账号、任何服务器 —— 谁装上都能填自己的 WebUI 地址和 Token；
2. **密码登录**：能填 QQ 号 + QQ 密码直接登；
3. **扫码登录**：内置网页（或等效的原生界面）出二维码扫；
4. **合并控制台**：桌面控制台的「填服务器 → 预检 → 部署 → 状态/配置」搬到手机上；
5. **零预置配置**：APK 与源码里不出现任何真实 IP、QQ 号、群号、Token、路径。

已有的两个前代各自缺一块：

| 前代 | 有的 | 缺的 |
|---|---|---|
| `console/`（com.dafeiyu.console） | 状态/配置/模式页，服务端下发 UI | 绑定固定服务器后端（8088 那套），不能给别人用；没有登录功能 |
| `desktop-controller/`（Windows EXE） | 脱敏三步部署 + 旋钮写回 | 只有 Windows 桌面版，没有登录功能 |

本版 = `desktop-controller` 的部署逻辑 + 全新的「开放式登录」页，装进一个无依赖的 Java APK。

## 二、登录页的三条路 + 一个兜底

NapCat WebUI 的登录协议全部按官方源码核实（`NapNeko/NapCatQQ` 的
`packages/napcat-webui-backend/src/api/QQLogin.ts`、`api/Auth.ts`、`helper/SignToken.ts`），
不是抓包猜的：

- **认证**：`POST /api/auth/login`，body `{"hash": sha256hex(token + ".napcat")}` →
  `data.Credential`（1 小时有效）。之后每个请求带 `Authorization: Bearer <Credential>`；
  响应外壳 `{"code","message","data"}`，`code!=0` 即失败；`message=="Unauthorized"`
  时客户端自动重登一次再重试（有单测钉死这条路径）。
- **① 扫码**：`POST /api/QQLogin/CheckLoginStatus` 每 2.5 秒轮询，返回的
  `qrcodeurl` 是**二维码内容**（QQ 跳转 URL），不是图片 —— 官方网页前端也是拿到
  字符串后用 `qrcode.react` 现画的。手机端同样本地渲染（Nayuki QR 库，
  MIT，源码随仓库走），手机 QQ 直接扫，无需第二台设备。
- **② 密码**：`POST /api/QQLogin/PasswordLogin`，body `{"uin","passwordMd5"}`
  （密码先 MD5；请求体里没有明文密码，有单测钉死）。返回 `needCaptcha` /
  `needNewDevice` 时是腾讯的网页验证组件 —— App 刻意不在原生层实现它，
  提示用户切到内置网页登录页走完官方流程。
- **③ 快速登录**：`GetQuickLoginListNew`（旧版没有此接口时回退
  `GetQuickLoginList`）列出服务器上登录过的号，点一下 `SetQuickLogin`。
  等价于 compose 里 `ACCOUNT` 免扫码那套，但不用改配置重启容器。
- **兜底**：内置 WebView 打开 `http://<服务器>/`（NapCat 官方网页登录页），
  验证码 / 新设备验证 / 2FA 都能在里面走完。不注入脚本、不拦请求。

**两步验证（2FA）**：登录接口支持 `totpCode`（RFC 6238，30 秒 / SHA-1 / 6 位），
App 有独立输入框，TOTP 实现带 RFC 附录 B 测试向量。没开 2FA 的服务器完全用不到它。

**容错**：轮询连续失败 4 次才判定「连接断了」——偶发超时不打断监控；旧版 NapCat
没有 `PasswordLogin` 时会收到 404，明确提示「该版本不支持密码登录」，扫码与快速登录不受影响。

## 三、控制台页：desktop-controller 的忠实移植

逐条对照 `desktop-controller/deployer.py` / `config_schema.py` / `knobs.py` 移植：

| 桌面版 | 手机版 | 状态 |
|---|---|---|
| DeployConfig 校验规则（主机/端口/用户名/仓库 URL/部署目录/端口冲突/镜像格式） | `DeployConfig.java` 同一套规则 | 逐条有单测 |
| 远程脚本模板（DSH_PROGRESS/DSH_ERROR 协议、`.dafeiyu-managed` 保护、compose heredoc） | `Deployer.buildRemoteScript` 同一份模板 | 模板断言在单测里 |
| 预检脚本 + `formatEnvironment` 中文输出 | 同 | 有单测 |
| `compose ps --format json` 解析（数组/逐行两形态）+ `formatContainers` | 同 | 有单测 |
| `redact()` 脱敏（URL userinfo / token=... / 长度≥6 敏感值） | 同 | 有单测 |
| SFTP 写 env 前先 `remote_dir()` 解析绝对路径 | `Deployer.remoteDir()` 同 | 同 |
| `knobs.py` 行级写回（保留注释/顺序、托管小节、bool 统一 1/0、越界 400） | `Knobs.applyEnvText` 同算法 | 39 项旋钮单测 |
| 需要 restart 的旋钮 → `compose up -d --force-recreate --no-deps astrbot` | 同 | |

**唯一刻意收窄的**：SSH 认证只支持密码（不支持私钥）。手机上选私钥文件体验很差，
v1 先不做 —— JSch 本身支持，后续版本要加只是 UI 的事。

**主机指纹**：首次连接必须勾选「接受指纹」，接受后把 `type|base64` 存进
`SharedPreferences`；之后每次连接逐字节校验，不一致直接拒绝（防中间人）。
指纹存的是 `HostKey.getKey()` 的 base64（核对过 mwiede/jsch 源码：
`Util.toBase64(key, ..., include_pad=true)`，与 `java.util.Base64` 输出一致）。

## 三之二、⑤「聊天范围 + 主聊天 API」：由使用者填，App 只负责送到服务器

这一版把「机器人该在哪儿说话、用哪个模型」也交给使用者自己填 —— App 里**没有任何**
预置群号、QQ 号或 API Key。依据全部从 AstrBot 源码与生产配置里核出来，不是猜的：

- **聊天范围** = `platform_settings.enable_id_white_list` + `platform_settings.id_whitelist`。
  `astrbot/core/pipeline/whitelist_check/stage.py` 的判据是
  `event.unified_msg_origin not in whitelist and group_id not in whitelist` → 拦掉事件，
  所以白名单里**群聊写裸群号、私聊写 `<平台id>:FriendMessage:<QQ号>`**
  （平台 id 取 `platform[0].id`，通常是 `default`）。
  打开这个开关后，服务器就「只在填进去的群和私聊里说话」，别处一律不理。
- **主聊天 API** = `provider_sources[]`（`api_base` + `key` 列表）+ `provider[]`（`model`）
  + `provider_settings.default_provider_id` 指向它。条目结构照生产配置与官方 provider
  结构写：`provider=openai`、`type=openai_chat_completion`、`provider_type=chat_completion`。
  固定 id 是 `dafeiyu-main_source` / `dafeiyu-main`，**重复写入只更新这一条**（幂等）。

三条刻意的设计：

1. **API Key 不进命令行**。它只出现在 SFTP 传上去的 600 权限载荷文件里，
   脚本读完即删（`finally` 里再删一次兜底），服务器 `ps`/shell 历史里看不到密钥。
2. **只改对应字段**。脚本按 id 找条目做 upsert，别人的 provider 一个字节不动
   （已用生产配置的副本验证：8 个 source / 11 个 provider 里其余条目字节级不变）。
3. **写完回读校验**。重新读一遍文件确认落盘内容与填写一致，否则报错。
   这条用**变异验证**证明过它真的会拦（把落盘内容改坏 → 脚本必须失败）。

App 里点「写入服务器」会先弹确认框把要写的内容念一遍（API Key 只说「已填」），
写完自动 `recreate astrbot` 让配置生效。持久化只存非密钥部分
（`chat_groups` / `chat_friends` / `api_base` / `api_model`），**API Key 与 SSH 密码同等待遇：只进内存**。

**QQ 号防呆**：登录页那个 QQ 号不只是填给密码登录用的 —— 登录成功后 App 拿
`GetQQLoginInfo` 返回的真实 uin 与它比对，对不上就红字提醒
（「服务器上登录的是 X，你填的是 Y」）。登录错号从二维码上看不出来，这是最容易犯又最难发现的错。


## 四、安全边界（与桌面版同一条线，一条不少）

- **不存密钥**：SSH 密码、WebUI Token、QQ 密码、TOTP 动态码只进内存，进程死即消失。
  持久化白名单 `DeployConfig.PERSIST_KEYS` 只有地址类字段，密码的键名根本不出现。
- **零预置配置**：构建自检 + 人工双重扫描（见第六节），真实 IP/QQ/群号/路径一个没有。
- **密码只以 MD5 过网线**（协议要求），请求体无明文（单测钉死）。
- **日志全脱敏**：进度、错误、远程输出上屏前都过 `redact()`。
- **权限只要两个**：INTERNET + ACCESS_NETWORK_STATE。不读通讯录/存储/位置。
- **只动带 `.dafeiyu-managed` 标记的目录**；部署目录是根目录/主目录直接拒绝。
- **⚠️ WebUI 是明文 HTTP**（NapCat 默认），SSH 本身加密。manifest 的
  `usesCleartextTraffic=true` 是刻意开的（NapCat 默认没 TLS），文档如实写明，不假装安全。
- minSdk 26（Android 8.0）：JSch 的 `SftpATTRS` 用了 `java.time`（API 26），
  压更低就得引入 desugaring，v1 不值得。QQ 客户端本身也早不支持 Android 8 以下。

## 五、构建与测试（全部可复现）

- **构建**：沿用 `console/build.sh` 的七步管线（aapt2 → javac → d8 → zip → zipalign →
  apksigner），不用 Gradle。两处升级：
  - build-tools 换 35.0.0 —— **34.0.0 的 d8（R8 8.2.2-dev）dex 化 JSch jar 时直接 NPE**，
    35.0.0 同输入一次通过（排查记录：先只喂我们的 class（过）、再只喂 jar（NPE）、
    换 35 的 d8 双输入（过），定位到 d8 版本）；
  - JSch 0.2.17 是 Multi-Release jar，`META-INF/versions/` 一并剥掉再入库
    （`lib/jsch-0.2.17.jar`，base 层与原版逐字节同源，仅去 MR 头）。
- **自检闸**：包名/minSdk/联网权限/图标/无密钥文件/无私钥块之外，本版新增
  「dex 里必须真的有 `com/jcraft/jsch` 与 `io/nayuki/qrcodegen`」——链接漏库这类
  「装上才炸」的问题在出包时就拦下。**踩坑**：`unzip -p xx.apk classes.dex` 进管道
  在这台机器上会丢内容误报 EOCD，先落盘再 grep。
- **测试**：`bash test/run-tests.sh`，**264 项纯 JVM 单测**（连跑 3 次全绿）：
  WebUI 协议全路径（假传输）、部署脚本生成与脱敏、旋钮解析与行级写回、
  TOTP RFC 向量、JSON 解析、以及「聊天范围 + 主聊天 API」——
  最后一项会**真的调用 python3 跑一遍生成的脚本**改一份临时 cmd_config.json，
  并带变异验证（把落盘内容改坏，回读校验必须报错）。反向检查保证可测层不混进 `android.*`。

## 八、v1.0.0 闪退事故与修复（装上一打开就崩）

**现象**：用户装上 APK 后「直接崩溃了，我进都进不去」—— 连界面都看不到。

**根因（确凿，非猜测）**：`ConsoleView` 里 `testBtn`（测试连接）、`deployBtn`（开始部署）、
`statusLine` 三个字段**只声明、从未创建**；而 `view()` 在构造界面时直接调用
`testBtn.setOnClickListener(...)` → 对 `null` 调方法 → `NullPointerException`。
`view()` 在 `MainActivity.onCreate()` 里对三个页面**全部立即构造**，
所以异常发生在第一帧之前 —— 表现就是「点开就闪退，什么都看不见」。
git 历史确认这三个字段从写出来那天就漏了（`git log -S` 查无赋值语句）。

**为什么测试没抓到**：单测刻意不覆盖 View/Activity（需要模拟器），
而这类 bug 编译期合法（Java 允许字段为 null）、运行期必崩。属于测试面的**盲区**，
不是「测了没测到」。

**修复**：
1. 在 `view()` 里创建这三个控件并加进对应卡片（`testBtn`/`deployBtn` 归「① 服务器连接」，
   `statusLine` 作页面级状态行）；
2. 新增静态检查 `test/check-unassigned-fields.py` 并接进 `run-tests.sh`：
   扫出所有「非基本类型字段 + 从未赋值 + 却被 `.方法()` 调用」的字段 —— 正是这次的事故形态；
3. 该检查器经**变异验证**：把修复注释掉，检查器立刻报
   「字段 testBtn (Button) 在第 56 行声明，从未赋值，却在第 [228, 836] 行被调用」；
   恢复后通过。证明它不是摆设。

**教训**：手搓 UI（没有布局 XML、没有 DataBinding）时，
「控件创建」和「控件使用」是两处独立代码，漏一处就是启动即崩。
现在有静态闸门兜住这一类。

## 九、私有定制版：默认就用「这台服务器」（公开版仍是零预置）

用户要求「不需要配置服务器了吧，直接默认这台服务器不是有QQ机器人吗」。
这和项目硬规矩（公开仓库/公开 APK 零真实信息）直接冲突，因此**分两个产物**：

| | 公开版 | 私有定制版 |
|---|---|---|
| 产物 | `dafeiyu-controller.apk` | `dafeiyu-controller-mine.apk`（**不发布**） |
| 服务器地址 | 无，手填 | 内置 |
| WebUI Token | 无，手填 | 内置**密文**，用一次性口令解锁 |
| 构建 | `build.sh` | `build-preset.sh --base … --token … --pass …` |

**Token 是真加密，不是写死**：APK 可反编译，写死等于公开。所以 Token 以
AES-256-GCM 密文存在包里，密钥由使用者的一次性口令经 PBKDF2-HMAC-SHA256
（20 万轮）派生；`PresetCrypto` 负责解密。
诚实边界（已写进代码注释与文档）：**口令太弱时离线暴力破解仍可行**，
迭代次数只是抬高成本；口令请用长随机串。

**「改完忘了还原」这个最大风险，用三道闸拦住**：
1. `build-preset.sh` 把「注入 → 构建 → 还原」做成原子流程，还原放在 `trap EXIT` ——
   中途失败、被 Ctrl-C 也会还原；
2. `build.sh` 的公开版自检：dex 里出现「定制版专属文案」或 `*.ts.net` 真实域名
   → 直接拒绝产出（经变异验证：注入真实地址后构建被拦下）；
3. 定制版构建走 `OUT_APK` 独立产物路径 —— 否则它会覆盖公开版产物，
   把带内置服务器的包留在公开版路径上（这个坑在开发时真的踩到了，
   自检发现「公开版里出现了定制版文案」才暴露出来）。

**实测验证**（不是「应该没问题」）：
- 定制包内含内置地址、**不含明文 Token**（直接扫 dex 字节）；
- 公开包**不含**地址、不含定制版分支代码（`Preset.HAS_PRESET=false` 时
  javac 把整段分支消除，dex 里连字符串都没有）；
- 端到端：注入 → 编译 → 运行时用正确口令解出原文，用错口令得到
  「口令不对，或者预设文件被改动过」；
- 定制版构建后 `Preset.java` md5 与构建前一致（确实还原了）。

**这台服务器的实际连接路径**（决定了定制版地址怎么填）：
生产 WebUI 只绑 `127.0.0.1:6099`，**公网连不通**（实测公网 IP 的 6099 端口返回 000）；
对外只能走 Tailscale，而 `tailscale serve` 在该端口上做了 **TLS 终止**，
所以内置地址必须是 `https://<host>.<tailnet>.ts.net:6099`（Let's Encrypt 证书，
手机不需要装 CA）。前提：**手机要登录同一个 Tailscale 网络**，否则连不上。

## 八、易踩的坑（给下一次改这个 App 的人）

- **`View.setTag(int, Object)` 的 key 必须是 resource id**，随手写个魔数
  运行时直接 IllegalArgumentException —— `UiKit.card()` 因此改成 child(0) 约定；
- **LinearLayout 里给 ScrollView 配 `WRAP_CONTENT` + weight** 会让滚动区缩成内容高，
  必须高 0 + weight 1；
