# 识图链条的「白花时间」治理

2026-09-12。dsh-vischain 1.0.0 → **1.1.1**，已上线主群 100000001。

## 一、为什么要治它

群主在群里说的原话是「现在的主要限制就是速率太慢了」。实测被 @ 之后的回复延迟，
延迟的大头集中在**带图片的那部分消息**上：不带图的中位 8.6s，带图的中位 16.6s。
8.6s 里 7.6s 是主模型生成，动不了；所以能动的就是识图这一段。

把近 70000 行生产日志里所有 `[vischain]` 行捞出来分档统计，得到这样一张表：

| 档 | 成功 | 成功中位 | 失败 | 白花秒数 | 白花/成功 |
|---|---|---|---|---|---|
| `vision-scnet` | 179 | 7.0s | 87 | 630 | 3.5s |
| `zhipu-vision`（glm-4.6v-flash） | 58 | — | 142 | 957 | 16.5s |
| `zhipu-vision:glm-4.1v-thinking-flash` | 105 | 5.0s | 33 | 309 | 2.9s |
| `zhipu-vision:glm-4v-flash` | 11 | 3.5s | 14 | 131 | 11.9s |
| **合计** | **369** | 6.3s | **293** | **2190** | **5.9s** |

「白花」= 花掉墙钟时间却没换来结果的那些失败重试。**每成功转述一张图，平均多等
5.9 秒**；273 次失败里有 58% 是撞满 `ATTEMPT_TIMEOUT`(10s) 的硬超时。

> 口径与工具：`server/observe/vischain_waste.py`。注意成功行用的是**全角括号**
> `一次过（6.0s）`，用半角去匹配会一行都匹配不到 —— 第一版就是这么把成绩
> 算成「114 次成功、平均白花 16.4 秒」的，数字整整错了三倍。

## 二、为什么 `_dead` / `_consec` 抓不住

插件本来就有两道降级机制，但都绕开了这个问题：

* `_dead`（`DEAD_TTL` 600s）只在**永久错误**上置位 —— `model_not_found`、
  `insufficient_quota` 这类「再试一百次也没用」的错。**超时和 429 都不算**，
  因为单看一次它们确实可能恢复。
* `_consec`（连续失败 3 次永久移除）方向是对的，但它是**进程内存**，而这一晚
  AstrBot 重启了十几次 —— 每次重启都从零开始数，永远攒不满 3 次。

于是每个坏档都能无限次地「先白花 10 秒再说」。

## 三、1.1.0：白花降权（SLOW_TTL）

给「不是坏、是贵」的失败单独记一笔：

```
_expensive(e, dt)  超时异常 / 文本里含 429 / 撞满 ATTEMPT_TIMEOUT×0.9
  → _slow[pid] = 时刻          # 排到最后，仍会兜底再试
```

和 `_dead` 的区别是**一个降权、一个拉黑**：被降权的档还在候选里，只是排最后；
真被走到且成功了，立刻撤销（`_slow.pop`）。`DSH_VIS_SLOW_TTL=0` 退回老行为。

`_expensive` 里必须显式判 `isinstance(e, (asyncio.TimeoutError, TimeoutError))`：
`asyncio.TimeoutError` 的 `str()` 是**空串**，只靠文本匹配会漏掉每一次超时 ——
而超时恰好是最大的一类。

## 四、1.1.0 上线后实测：**反而更差**

上线 13 分钟就跑了一次对照，每次成功平均白花从 5.9s 涨到 **8.5s**。
日志把原因写得很直白：

```
00:00:11 本轮先跳过 vision-scnet,zhipu-vision（10 分钟无通道 / 3 分钟白花过时间）
00:00:17 降级到 zhipu-vision:glm-4.1v-thinking-flash 才成功（第3档第1次）
```

`zhipu-vision` 每 180 秒**准时回到第 2 档**，再白花 10 秒，再被降权。第一版的设计
是「冷静期一到就收回原位」，于是常犯的档获得了「定期回来撞一次」的特权 ——
而定期回来撞一次，本身就是浪费。

## 五、1.1.1：递增退避 + 不回原位

改写两处：

```
_slow[pid] = (时刻, 连续白花次数)
_slow_ttl(n) = min(SLOW_TTL × 2^(n-1), SLOW_MAX)     # 180s → 360s → 720s，封顶 900s
```

`_order()` 的返回值从 `alive + dead` 变成 **`alive + cooled + dead`**：

* `alive` —— 没白花过的干净档；
* `cooled` —— 冷静期已过、但还没证明自己好使的档（**排在干净档后面**，
  不回原位）；
* `dead` —— 还在冷静期 / 判定无通道的档。

撤销只有一个条件：**真被调用而且成功了**。于是常犯的档越来越难被撞到，
偶尔抽一次的档 3 分钟就恢复，`fail-open` 一字未改（所有档始终在候选里）。

## 六、结果

上线 7 分钟的初步对照：

| | 1.0.0 全天基线 | 1.1.1 上线后 |
|---|---|---|
| 每次成功平均白花 | 5.9s | **3.3s** |
| 成功耗时 P50 | 6.3s | 5.7s |
| 成功耗时 P90 | 9.2s | 7.5s |
| `glm-4.1v-thinking-flash` 白花/成功 | 2.9s | **0.0s**（5 成功 0 失败） |

`vision-scnet` 和 `zhipu-vision` 各自白花两次后进入退避，流量稳定落在
`glm-4.1v-thinking-flash` 上；它一次没失败过。样本还小（11 次成功），
`/识图状态` 和 `vischain_waste.py` 会继续跟着看。

## 七、顺带修掉的两个观测层缺陷

* **空正文的 `Prepare to send` 不是发出去的消息。** 它只是一次「这轮不开口」的
  决定（`dsh-decide` 判沉默、`dsh-poke` 回戳），日志照样打一行，紧接着必有一条
  `stopped event propagation`；实测 688/688 都是如此。`group_digest.py` 老口径把它
  渲染成 `(非文本/空)` 并计进回复数，同一段窗口里 142 条「回复」其实只有 15 条
  真发出去。现在标成「决定不说 · 未发出」，并单列真实开口率。
* **在容器里跑单测会把测试日志灌进生产日志。** `vis.logger` 就是 astrbot 的
  loguru，挂着 `/AstrBot/data/logs/astrbot.log` 这个 sink。`test_slow_demote.py`
  现在先把 `vis.logger` 换成哑对象再跑。

## 八、没做和存疑的

* **没有动 `DSH_VIS_CHAIN`，也没有动任何 provider 配置。** 换档交给运行时的
  退避去自洽，而不是把「哪个模型好」写死在 env 里 —— 上游好坏是会变的。
* **`ATTEMPT_TIMEOUT`(10s) 是否偏紧，存疑未改。** 成功耗时的 P90 是 9.2s、
  最大 14.8s，而 58% 的失败是撞满这条线的硬超时，看起来像是砍掉了本可以成功的
  调用。但放宽超时会让真正卡死的档多等，需要先有「被砍掉的调用里有多少能在
  15s 内成功」的数据，现在还没有。
* **`dsh-imgctx._caption()` 刻意串行**（两图 ≈ 10.7s）的前提是当年为了避智谱 429；
  转述 provider 早就换过几轮，这个前提一直没重新验证。两图事件只占带图事件的
  约 11%，收益有限，暂不动。
