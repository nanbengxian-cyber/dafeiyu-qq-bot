## 一、要解决的问题

机器人账号 100000003（大肥鱼2号）会周期性被 QQ 服务端踢下线
（日志 `[KickedOffLine] 你的账号当前登录已失效，请重新登录`）。而
`docker-compose.yml` 里的 `ACCOUNT=100000003` 在 2026-09-13 被注释掉了，
于是**容器每次重启/掉线恢复都只能出示二维码等人手扫**。

用户手机常常不可达，等于「容器一重启，机器人就下线到人工介入为止」。
用户要求：把快速登录（免扫码）装上。

## 二、改动内容

### 2.1 `/opt/qqbot/docker-compose.yml` —— 恢复 `ACCOUNT`

```yaml
# [compose:account-v1 免扫码快速登录]
      - ACCOUNT=100000003
```

entrypoint.sh:222 的分支：

```sh
if [ -n "${ACCOUNT}" ]; then gosu napcat /opt/QQ/qq --no-sandbox -q $ACCOUNT
else                          gosu napcat /opt/QQ/qq --no-sandbox; fi
```

有 `ACCOUNT` 就传 `-q`，走磁盘登录态的快速登录。

备份：`/opt/qqbot/backups/docker-compose.yml.bak.quicklogin2.20260914-165050`
（改动前已 `diff` 确认与当时线上文件逐字节一致）。

### 2.2 `webui.json` —— 打开 WebUI 自动快速登录（第二层）

`/opt/qqbot/napcat/persist/napcatcfg/config/webui.json`：

```diff
-    "autoLoginAccount": "",
+    "autoLoginAccount": "100000003",
```

只替换这一行的值，其余字节原样保留。备份：
`/opt/qqbot/backups/webui.json.bak.autologin.*`。

**重要实测结论**：这一层在 `ACCOUNT` 存在时**不会被触发**。
`runWebUiConfigQuickFunction()` 在整个 napcat.mjs 里只有 **1 个调用点**，
位于 `XEe()` 的 `else` 分支（即「没有 -q 指令」时才走）。有 `ACCOUNT`
时走的是 `if (i.some(uin === r))` 分支，直接 `quickLoginWithUin`。
保留它的意义：若将来再有人注释掉 `ACCOUNT`，WebUI 层会作为兜底尝试
自动登录，而不是干等扫码。它不会与第一层冲突。

### 2.3 删除两张失效的死码

`ACCOUNT` 生效后登录成功**不会**再生成 `qrcode.png`（容器内
`/app/napcat/cache/` 为空）。网页目录里残留的旧码是上一次扫码留下的
**已失效死码**，会误导人对着一张死码扫半天，故删除：
`rm -f /opt/qqbot/public/qrcode.png`。

`sync_qr.sh` 仍每 3s 尝试 `docker cp`，文件不存在时静默失败（`|| true`），无副作用。

## 三、关键代码事实（推翻 09-13 的判断）

09-13 注释掉 `ACCOUNT` 的理由是：「ACCOUNT 会让 entrypoint 永远走
`qq -q $ACCOUNT`，QQ 会话半死时磁盘登录态仍『有效』，于是**永远不出二维码**」。

**这个归因不准确。** 逐段读 minified 代码 + 实测双向验证：

```js
// XEe() —— 有 -q 时的分支
if (i.some((a) => a.uin === r))
  e.log("正在快速登录 ", r), n.quickLoginWithUin(r).then(async (a) => {
    if (!(a.result === "0" && !a.loginErrorInfo?.errMsg)) {   // 快速登录失败
      const u = a.loginErrorInfo?.errMsg || `快速登录失败，错误码: ${a.result}`;
      e.logError("快速登录错误：", u), ve.setQQLoginError(u);
      const { success: l, attempted: d } = await s(r);         // 密码回退
      !l && !d && !t.isLogined && n.getQRCodePicture();        // ← 出码！
    }
  })
```

「未找到历史登录记录」分支同样以
`!a && !c && !t.isLogined && n.getQRCodePicture()` 结尾（第 30766xx 字节处）。

回退函数 `s()` 在**没有**配置 `NAPCAT_QUICK_PASSWORD(_MD5)` 时返回
`{ success: !1, attempted: !1 }` —— `attempted` 为假，所以
`!l && !d` 成立，**二维码一定会生成**。只有配置了密码回退、且密码登录
被真正尝试过（`attempted === !0`）时，才会压住出码。

也就是说：**真正压住二维码的是 `NAPCAT_QUICK_PASSWORD`，不是 `ACCOUNT`。**

### 实测验证（用一个没有登录态的 UIN）

把 `ACCOUNT` 临时指向 `1000000000`（绝无历史登录记录），重建容器：

```
01:18:44 error 快速登录失败，未找到该 QQ 历史登录记录，将尝试密码回退登录
01:18:44 info  QQ 1000000000 未配置回退密码环境变量…将使用二维码登录方式
01:18:45 warn  二维码已保存到 /app/napcat/cache/qrcode.png
```

二维码确实生成了（602 字节）。随后把 `ACCOUNT` 换回 `100000003` 并重建：

```
01:20:47 info 正在快速登录  100000003
```

一次成功，无二维码残留 —— 双重确认两条路径都符合预期。

**结论**：`ACCOUNT` + 不配密码回退 的组合下，快速登录失败会**自动退回扫码**，
09-13 那种「永不显示二维码」的死锁配方不复存在。因此恢复 `ACCOUNT` 是安全的。
（这一点已写进 compose 注释，避免将来又被误注释掉。）

## 五、残留风险（如实记录）

1. **半死会话仍无解**：`ACCOUNT` 让快速登录「成功」，但 QQ 服务端其实已
   作废该会话（`sendMsg` 返回 `1006514 网络连接异常`）时，日志里不会有
   失败，也就不会出码，人依旧无法扫码自救。09-13 那次的**现象**是真的，
   只是原因不是 `ACCOUNT` 本身。
   缓解：watchdog v3 的 `sendfail` 检测（30 分钟冷却后重启换码）已经覆盖
   这个场景；若真遇上，临时注释 `ACCOUNT` 重建即可出码。
2. **第二层（WebUI autoLoginAccount）在 `ACCOUNT` 存在时不生效**，
   见 2.2。它只是「将来若去掉 ACCOUNT」的保险。
3. 快速登录的前提是磁盘登录态 `login.db` 有效。2026-09-14 16:40 刚扫码
   登录过，所以是新鲜的。若长期失效，QQ 服务端会拒绝快速登录 →
   按第三节结论自动退回扫码，不会卡死。

## 七、易踩的坑

- **改 compose 的 `environment` 必须 `docker compose up -d`（重建容器）**，
  普通 `docker restart` 不会重读 environment —— 这是本次唯一必须重建的原因。
- 改完容器 IP 若漂移，`qq-proxy-ip-guard.timer` 会自动修 PREROUTING 源 IP；
  本次两次重建都拿回 `172.18.0.2`，未漂移（已 `status` 确认一致）。
- 容器重建后 `last_seen_seconds` 会短暂显示 `99999`（新日志里还没有
  `接收/发送` 行），属正常，不是故障。
- compose 文件是 `root:root 600`，`grep` 直读会 Permission denied，要 `sudo`。
