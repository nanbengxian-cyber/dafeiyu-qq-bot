# 76 · 「不知道是谁 @ 的他」：根因在框架把那个 @ 删掉了

**日期**：2026-09-13
**改动**：`dsh-spine` 1.0.0 → 1.2.0（新增「这条是不是在点你」注入）
**触发**：群主报「他现在不知道是谁艾特的他」

---

## 一、症状与那对真实语料

```
11:44:14  薛定谔的喵: [At:3752949000] 😘😘😘
11:44:2x  大肥鱼:      这仨表情是给谁的
```

回复的**投递对象是对的**（发给薛定谔的喵），但**内容里它不知道这三个表情是冲它来的**。
先把这类回复量了一遍：被 @ 的 3654 条消息里，能判读的回复 2981 条，
表现出「不知道谁在跟我说话」的只有 **7 条 = 0.2%**，而且那 7 条里 6 条是误判
（`叫我干嘛，有事说事` 其实是正确回答 —— 对方 @ 完什么都没说）。

**所以这不是一个高频统计问题，是一个低频但每次都很难看的定性问题**：
一旦发生，整条回复就是答非所问。

---

## 二、第一版假设是错的（而且是被生产数据打回来的）

我先查了最像的那个原因：

> `[At:3752949000]` 是个纯数字，而**人格提示词里 `3752949000` 出现 0 次** ——
> 它不知道这个号码就是自己。

证据链看起来很完整：
- `req.prompt = event.message_str[...]`（`astr_main_agent.py:1455`），@ 渲染成纯数字；
- 框架里没有任何地方把 self_id 告诉模型；
- 于是群友 @ 它时，它把这条读成「某人 @ 了某个陌生人」。

照这个假设写了「@ 号码对照表」注入（把请求里出现过的 `[At:数字]` 翻成
`＝@你` / `＝@难谓言`），单测全过（`AT_TEST_OK`），部署上生产 1.1.0，
然后 ——

**生产上 0 次注入。** 一条都没有。

群里那会儿明明有 `[At:3752949000] 😘` 这种消息。0 次注入只有两种解释：
判据没命中，或者根本没走到。去读框架源码，答案是**判据没命中 ——
我瞄准的那个形态在 prompt 里根本不存在**。

---

## 三、真因：框架把「第一个 @ 机器人」从正文里删掉了

`astrbot/core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py:382-391`：

```python
is_at_self = str(m["data"]["qq"]) in {abm.self_id, "all"}
...
if is_at_self and not first_at_self_processed:
    # 第一个@是机器人，不添加到message_str      ← 直接不要了
    first_at_self_processed = True
else:
    # 非第一个@机器人或@其他用户，添加到message_str
    at_parts.append(f" @{nickname}({m['data']['qq']}) ")
```

**两个方向的结论完全不同：**

| | 正文里长什么样 |
|---|---|
| 别人被 @ | ` @昵称(QQ) ` —— **带名字**，本来就看懂，不需要我修 |
| **机器人自己被 @** | **什么都没有，被删掉了** |

也就是说，`[At:3752949000] 😘😘😘` 送到模型手里的 prompt 就是：

```
😘😘😘
```

三个表情**凭空出现**。它不知道有人在点它，更不知道是谁 ——
问出「这仨表情是给谁的」是这句话唯一的合理读法。

`[At:数字]` 这个形态只存在于**日志概要**里（`get_message_outline()`，
事件总线打印的就是它）。我看到日志里满屏 `[At:...]`，就以为模型看到的也是这个 ——
**日志的渲染口径和 prompt 的渲染口径不是一回事，这是我第一版踩的坑。**

---

## 四、另外确认了两件「本来就没问题」的事

1. **「谁在说话」框架是给了的。** `_append_system_reminders()` 会往系统提示里加
   `User ID: x, Nickname: y`（`astr_main_agent.py:983`）。它的开关是
   `cfg.get("identifier")`，而 `cmd_config.json` 里 `identifier` 在**全局**
   `/provider_settings` 上是 `true`，`cfg = config.provider_settings or ...`
   拿的正是这一层。所以「谁发的」它知道 —— **缺的只是「这条在点我」**。
   （顺带确认：主 provider `bigfeiyu-justwoker-sol` 自己的 `provider_settings` 是空的
   `{}`，但那是"没有覆盖"，不是"关掉了"。）

2. **`dsh-memory` 早就在注入说话人身份**（`【正在和你说话的人：名字（QQ）】`，
   两条分支都推），所以不用重复做这件事。

## 五、修法

在 `dsh-spine` 的 `on_llm_request` 里加一段注入。**不能靠正则扫正文**
（那个 @ 已经被删了），只能回到组件层看 `At.qq`：

```python
def at_targets(event) -> tuple:
    """返回 (是否被单独 @ 了它, 是否只是 @全体成员)。"""
    ...  for comp in event.message_obj.message:  q = comp.qq
         q == "all"        -> allm = True
         q == self_id      -> direct = True
```

命中的话注入（~110 字）：

> 【这条是在点你】「薛定谔的喵」@ 了你才说的这句话，而正文里那个「@你」被框架
> 抹掉了（只留下 @别人 的痕迹）。所以你看到的正文可能很短、甚至只是一个表情或
> 半句话 —— 那不是在自言自语，是**点名直接对你说话**。照平时聊天回就行：
> 别问「这是给谁的」，也别当成没头没尾的怪话。

三处刻意设计：

- **把「说话人」也写进去**。光有框架那行 `User ID/Nickname` 不够 ——
  模型知道"谁在说话"，但不知道"这三个表情是冲我来的"。两件事得绑在一起说。
- **明说正文可能是碎片**。这才是真正的坑：`😘😘😘` / `得修` / `必须得狠狠使用`
  这类短正文看着像自言自语，把它解释成"被点名的碎片"，比单说"有人@你"更有用。
- **`@全体成员` 单独一套话术**（「不是专门点你」）。框架的判据把 `all` 和
  `self_id` 归成一类都删掉，但对模型来说这两件事完全不同，不能混。

**没有去改框架。** 改 `message_str` 的生成规则等于打上游补丁，
AstrBot 一升级就没了，而且会影响每个上下游插件对 `get_message_str()` 的假设。
注入是加法，坏了也只是少一句提示。

## 六、验证

`plugins/dsh-spine/test_at.py`，9 节：

1. **那对真实失败语料**：`At(3752949000)+Plain` 且 prompt 只有 `😘😘😘` →
   断言注入块含「点你」「说话人名」「给谁的」「抹掉」四个要点。
2. **@别人 → 零注入**（`At(3522559046)`）。
3. **@全体 → 走全体话术**，断言含「不是专门点你」。
4. **没有任何 @ → 零注入**。
5. 号码对照表：自己排第一、上限 6 个、名字查不到退回号码。
6. `_ctx_text` 吃 str / dict / list / None 四种形状。
7. 插件能装载、`_inject_at` 真跑一次能读到成员表（223 个名字）。
8. 状态面板能渲染。
9. 生产日志零污染（`Logger.add` 在 import 前置空）。

**单测抓到一个真 bug**：`_ctx_text` 原来先判 `str` 再解 `dict`，
于是 `{"content": "abc"}` 解包成 `"abc"` 之后掉进了最后的 `return ""` ——
历史里的 @ 号码会**全漏**。顺序反过来才对。这个 bug 单看代码很难发现
（`req.prompt` 那条路照常工作，所以功能"看起来是好的"）。

## 七、教训：0 次注入是一次测量，不是一次失败

这一轮真正值钱的不是那段注入，是**上线后数了一下注入次数**。
如果我按惯例只做"单测通过 + 插件加载无报错 + 版本号对"就收工，
我会交出一个**瞄准了不存在的形态**的修复，而且它看起来完全正常：
没有报错、没有日志、测试全绿、功能永远不触发。

所以记住两条：

1. **新功能上线后要数它的触发次数**，不能只数错误数。0 次触发和 0 次错误
   在日志里长得一模一样。
2. **日志的渲染口径 ≠ prompt 的渲染口径。** 我在日志里看到满屏 `[At:数字]`
   就假定模型也看到它 —— 实际上日志走 `get_message_outline()`，
   prompt 走 `message_str`，两者对 @ 的处理完全不同（一个渲染成 `[At:数字]`，
   一个把"@机器人"删掉、把"@别人"写成 ` @昵称(QQ) `）。
   **要断言模型看到什么，就得去读生成 prompt 的那几行源码。**

## 八、贴纸文字：已定位并修好 → 见 [docs/77](77-贴纸标记泄漏的第三条出口-20260913.md)

群主同时报的「还是会发贴图纸文字」当时我没复现出来（15350 条出站正文里
`[贴纸` 各 0 次）。后来群主给了例子，顺着「引用消息」捞到了真语料，
根因是**`event.send()` 是一条没人管的出口** —— 它不过装饰钩子、不过
`respond.stage`，所以那 15350 条样本里根本看不到它。

那篇文档也记了我差点犯的错：**拿一个有盲区的尺子量出 0，然后反过来怀疑用户**。
教训是「报『从来没发生过』之前，先说清样本来自哪一行日志、
哪一类情况不会留下那一行」。
