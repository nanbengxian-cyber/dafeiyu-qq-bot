# 91 · 就绪竞态：把「刚点过启动」和「没启动过」分开

日期：2026-09-17
相关：docs/90（手机 App 多开版：三配置 + 内置服务器）
影响面：`mobile-controller/server/dafeiyu-manager.py`、`app/.../RobotsView.java`

## 一、用户看到的现象

用户点完「启动」马上去填三配置，App 报：

```
实例的数据库还没生成。请先「启动」一次，等 AstrBot 初始化完再设人格。
```

他**刚点过**启动。这句话把他往完全错的方向引 —— 他会去反复点启动按钮，
而问题其实只是「再等一会儿」。

更隐蔽的是：配置**已经写进去了**，但 App 因为读超时先报了失败，
用户以为没成功，反复重试。

## 二、根因：两个文件不是同时落盘的

AstrBot 启动过程中，两个文件出现的时间差得很远：

| 文件 | 何时出现 | 后果 |
|---|---|---|
| `cmd_config.json` | 启动**早期** | 界面据此显示「运行中」 |
| `data_v4.db` | 等 ORM 初始化完才创建，**晚得多** | 人格写库撞「文件不存在」 |

`read_config()` 只看 `cmd_config.json`，所以它报 `ready=true` 的同时，
`data_v4.db` 可能还不存在 —— 界面上「已就绪」，实际操作却失败。

## 三、修法：把就绪判据合成一个，而不是多加一次等待

### 3.1 为什么不能简单地「再等一次」

App 端读超时是 120 秒（`ManagerClient` 的 `setReadTimeout(120000)`）。
`apply_config` 原本已经等两次（写前一次、重启后一次），每次上限 `READY_TIMEOUT=40` 秒：

```
40 × 2 + 30（重启开销）= 110 秒 < 120 秒     ← 只剩 10 秒余量
```

**再加第三次等待就会越过 120 秒**，表现是「App 报连不上，服务端其实成功了」——
正是要修的那类 bug。所以修法不是加等待，而是**把「文件在不在」并进同一次等待的判据里**：

```python
ready = wait_astrbot_ready(name, need_db=has_persona, need_cfg=True)
```

`wait_astrbot_ready()` 的判据从「日志说启动完成」扩展成「**文件都在 且 日志说启动完成**」：

- `need_cfg=True` → `cmd_config.json` 存在
- `need_db=True`  → `data_v4.db` 存在（要写人格时）

等待次数仍是 2 次，预算不变。

### 3.2 拿不到日志时不能死等（`NO_LOG_WAIT`）

原来拿不到 `docker logs`（测试环境、容器不存在、docker 不可用）时会**按 40 秒死等**。
这是个真缺陷：那时我们**没有任何证据**说明实例在往好的方向走 ——
文件可能 2 秒后出现，也可能永远不出现。等满 40 秒只是让用户干等，
最后给的还是同一句报错。（实测把单元测试拖到 60 秒超时，就是这么来的。）

现在给几秒宽限（`NO_LOG_WAIT = 5`），文件出现就继续，否则老实说「还在初始化」。

### 3.3 两种人要说相反的话（`astrbot_container_exists`）

缺 `cmd_config.json` 的有两种人：

| 情况 | 该说的话 | 下一步动作 |
|---|---|---|
| 从没点过「启动」（容器不存在） | 「还没跑起来过，点启动」 | 去点启动 |
| 刚点过「启动」（容器存在，在初始化） | 「正在初始化，稍等一两分钟」 | 等一会儿 |

只看文件在不在是分不出这两者的。新增 `astrbot_container_exists()`（`docker ps -a` 按名字查）
来分流；**拿不到结论时返回 `None`（不知道），不是 `False`** ——
宁可让刚启动的人多等一会儿，也不要把「请先启动」甩给他。

`read_config()` 也补了 `started` 字段，让 App 端能说对话：

```json
{"ready": false, "started": false}   // 没启动过
{"ready": false, "started": true}    // 正在初始化
{"ready": true,  ...}                // 就绪
```

### 3.4 App 端：不再因为 `ready=false` 禁用「保存」

`RobotsView` 原来在 `ready=false` 时把「保存」灰掉。既然服务端已经会先等就绪再写，
「刚点完启动就来填配置」是完全正常的操作顺序 —— 灰掉按钮只会让用户卡住。
现在改成不禁用，并按 `started` 给不同提示。

## 五、教训

1. **「测试全绿」不等于测试有效。** 变异 B 暴露了字符串断言匹配到多处的问题：
   断言要打在**行为**上（返回值/副作用），不是「源码里出现过某段文字」。
2. **等待要有证据。** 没有证据时死等满额，只是把「立刻报错」换成「等一会儿再报同样的错」。
3. **同一句报错可能对应两种人。** 报错文案要能区分「他做错了」和「他做对了但要等」——
   后者把他往错方向引，比不报错更糟。
4. **超时预算是硬约束。** 修时序问题时先算总预算，别顺手加第三次等待。
