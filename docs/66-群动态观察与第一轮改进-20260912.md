### 1. `server/observe/group_digest.py` — 对话时间线

把 `/opt/qqbot/astrbot/data/logs/astrbot.log` 还原成「谁说了什么、机器人回了什么、
哪个插件动了手」的时间线。

```
python3 group_digest.py --hours 3          # 最近 3 小时时间线
python3 group_digest.py --since 2026-09-12T20:00 --json
python3 group_digest.py --stats            # 只出统计
```

关键日志格式（时间戳 UTC+8）：

| 方向 | 行样式 |
|---|---|
| 进 | `[default] [default(aiocqhttp)] 昵称/QQ: 文本` |
| 出 | `[Core] [INFO] [respond.stage:206]: Prepare to send - 昵称/QQ: 文本` |

注意 `Prepare to send` 里的 `昵称/QQ` 是**触发这次回复的人**，不是机器人自己；
文本为空 = 发的是非文本组件（图片/语音/表情）。

### 2. `server/observe/dynamics.py` — 群动态记分卡（已上 systemd）

7 个指标，每 15 分钟跑一次，结果落 `/opt/qqbot/observe/dynamics.json`：

| 指标 | 含义 | 阈值 |
|---|---|---|
| P1 被@未回 | 被 @ 后 60s 无任何回复 | 列举 |
| P2 群主点名未回 | 群主消息且点名了机器人，120s 无回 | 列举 |
| P3 参与度 | 机器人发言 / 群友发言 | 参考 |
| P4 自我重复 | 机器人回复间 4 字 n-gram 复现 | ≥3 条 |
| P5 刷屏 | 60s 内 ≥5 条逻辑回复 | ≥5 |
| P6 功能失败 | 审核拦截 / 超时 / Traceback | 列举 |
| P7 机械提示 | 「慢点，还有 N 秒冷却」这类无水话术 | 计数 |

`logical_replies()` 把 6 秒内的多条 `Prepare to send` 合并成一次「逻辑回复」，
否则一次带图回复会被算成三条，P5 全是假阳性。

systemd：
```bash
systemctl status qqbot-dynamics.timer     # OnCalendar=*:0/15
journalctl -u qqbot-dynamics -n 50
```

已有的 `qqbot-observe.timer`（5 分钟，`observe_watch.py`）继续跑 R1~R4 故障族，
两个不冲突：一个盯**故障**，一个盯**行为质量**。

## 三、第一轮改进：dsh-voice 1.2.2

### 改了什么

**P6 — 审核误杀（8h 内 9 次）**，三个独立成因：

1. `raw == "可"` 精确比较。思考模型爱写成「可。」「"可"」「可以」「没问题」，
   全被当成拒绝。
   → 加 `_parse_censor_verdict()`：**先判否再判可**。顺序不能反——
   「不可以」里同时含「可」，先判可会把它放行。
2. `CENSOR_TIMEOUT=10s`。审核走的是会话主 provider（gpt-5.6-sol，思考模型），
   10s 会偶发超时；超时即 fail-closed，把「现在还属于内测版，我还没有正式做完呢」
   这种完全无害的话挡下来了。
   → 默认 20s，并且**拿不到结论时重试一次**（超时/答非所问都算拿不到结论）。
   真有害内容仍然一次拦死、不重试。
3. 提示词没写「玩梗不算」。「先V我50解锁转账功能」（肯德基疯狂星期四梗）
   被判成诈骗。
   → 提示词显式白名单：玩梗、网络流行语、复述引用、自嘲、夸张吐槽、
   聊钱聊游戏都判「可」。

**P7 — 机械提示刷屏（8h 内 34 条）**：
16:46~16:50 两个群友轮流敲 `/说话`，机器人往群里丢了 12 条「慢点，还有 N 秒冷却」。
→ 加 `NOTICE_GAP`（默认 90s）按群去重：窗口内第一条照发（得让人知道有冷却这回事），
之后静默只写日志。

**顺手修的一个口播事故**：工具返回里原本带着内部错误原文，模型照抄成
「发不出声音：审核通道超时」播到群里，把审核机制暴露给全群。
→ 审核失败只给人一句自然话，技术原因留在日志（`_INFRA_REASONS`）。

## 四、顺手量到的第二件事：回复延迟

群主当晚在群里说「**现在的主要限制就是速率太慢了**」。于是量了一下（60000 行日志，
236 次被 @）：

| 分段 | 中位 | P75 | P90 |
|---|---|---|---|
| 被@ → 机器人发出（整体） | 9.1s | — | 28.2s |
| 群友@ → 开始注入记忆/风格 | 4.4s | 6.5s | 12.5s |
| 注入完成 → 发出（≈ 主模型生成） | 7.6s | 8.9s | 11.2s |
| **窗口内有识图**的整体延迟 | **16.6s** | — | 36.1s |
| 窗口内无识图的整体延迟 | 8.6s | — | 24.3s |

两点结论：

1. **主模型占 7.6s**（中位）。这是群主选的 `bigfeiyu-justwoker-sol`（思考模型），
   属于接口选型，不是插件能改的。
2. **识图会给那一次回复额外加约 8s**（15% 的 @ 命中）。`dsh-imgctx._caption()`
   是**刻意串行**的（注释写明：智谱并发两张会 429），但现在的转述 provider 已经被
   `dsh-vischain` 接管成 `vision-scnet`，串行这个前提对 scnet 是否还成立没验证过。
   实测一次窗口里两张图 = 7.4s + 6.3s 串起来 ≈ 14s。

→ 下一轮候选：识图预取（图片消息一到就后台转述，回复路径直接命中缓存），
或对「被直接点名」的回复短路掉别人的图。
