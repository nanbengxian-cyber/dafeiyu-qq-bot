## 一、这一版要解决什么

用户原话（2026-09-16）：

> Tailscale？我需要降低门槛啊，有没有其他的方案？我需要只用填三个配置就可以启动
> 我这台服务器里面的 QQ 机器人，并且可以做到多开，只需要三个配置 API 密钥以及
> 相关配置，需要聊天的群聊还有私聊 QQ号，还有相对应的人格提示词改写配置。
> 实在不行你就把 Tailscale 关了，我需要最大程度的降低门槛，这样我的内部群就可以用它来测试

拆成四个要求：

1. **只填三个配置就能跑起来**：① 主聊天 API（地址/Key/模型）② 要聊天的群号与私聊 QQ 号 ③ 人格提示词。
2. **能多开**：多个 QQ 号，各自一个机器人同时在线。
3. **不要 Tailscale**：手机上不装、不依赖。
4. **服务器固定**：用户内部群直接用，不填服务器信息。

关于第 3 点有一条**不能动的约束**：用户当前正在用的 DSH 控制台绑在 Tailscale 地址上
（唯一监听地址），NapCat WebUI 也在同一网段。**关掉 Tailscale 会切断用户自己的访问**。
所以做法不是关它，而是让 App 不依赖它 —— 见第二节。

## 二、方案选择：为什么是 SSH 隧道

试过/评估过的路子：

| 方案 | 结论 |
|---|---|
| Tailscale | 要求用户装 App、登录账号、加入 tailnet。门槛最高，且与「不依赖 Tailscale」矛盾 |
| 公网直连管理端口 | 管理服务一旦暴露公网，等于把服务器管理权限挂出去。否决 |
| WireGuard 自建 | 同样要在手机上装客户端、导入配置。门槛没降下来 |
| **SSH 本地端口转发** | **采用**。手机自带能力，认证用密钥，服务器上可把账号限制成「只能转发到一个端口」 |

SSH 隧道的好处是把「认证」和「授权」都收到了最窄：

* 认证：RSA 密钥（不是密码）；
* 授权：服务器上那个专用账号被限制成 `restrict,port-forwarding,permitopen="127.0.0.1:6199"` ——
  **登不了 shell，也转发不了别的端口**；
* 管理服务只监听 `127.0.0.1`，公网上根本不存在这个端口。

这样即使 APK 泄露，攻击面也只到「能管机器人实例」，碰不到整台服务器。

### 实测验证过的限制

在服务器上用真实密钥实测（判据是 ssh 日志里的报错，不是「端口有没有监听」）：

```
转发到 6199（允许）→ channel 1: open failed: connect failed: Connection refused
                     （通道打开了、确实到了目标端，只是服务当时没起）
转发到 22          → channel 1: open failed: administratively prohibited
转发到 3306        → channel 1: open failed: administratively prohibited
```

`administratively prohibited` = sshd 直接拒绝开通道，限制生效。

登录 shell：`This account is currently not available.`（nologin）—— 被拒。

## 三、踩过的坑（都值得记下来）

### 1. ed25519 密钥在安卓上用不了

这是**最隐蔽**的一个。现象：用 ed25519 密钥连服务器，JSch 一直报
`Auth fail for methods 'publickey'`，看起来像密钥不对或账号不对。

开 JSch 日志才看到真因：

```
[jsch] ssh-ed25519 not available for identity app
```

进一步查：`com.jcraft.jsch.jce.SignatureEd25519` 的构造函数直接抛

```
java.lang.UnsupportedOperationException: SignatureEd25519 requires Java15+.
```

JSch 的 ed25519 签名实现要 **Java 15+**，而安卓上的 `Ed25519` 要 **API 33+**。
所以：**必须用 RSA 密钥**。改成 `ssh-keygen -t rsa -b 3072 -m PEM` 后一次通过。

`build-preset.sh` 里加了检查：如果传入的密钥不是 RSA 就直接拒绝构建并给出生成命令。

### 2. `command="/bin/false"` 会把隧道一起杀掉

一开始按「限制最严」的思路，authorized_keys 写成：

```
restrict,port-forwarding,permitopen="127.0.0.1:6199",command="/bin/false" ...
```

结果 `ssh -N -L` 一连上就退出 —— 强制命令执行完（返回 false）会话即结束，
端口转发跟着断。**端口转发不需要 shell**，所以正确写法是去掉 `command=`，
靠账号的 `nologin` shell 挡住交互登录和 exec：

```
restrict,port-forwarding,permitopen="127.0.0.1:<管理端口>" <公钥> <受限账号>
```

### 3. `sftp` 的端口参数是 `-P` 大写

写成 `-p 10313` 会被当成「保留时间戳」，然后连到默认的 22 端口去 ——
报错看着像认证失败，实际是连错了地方。`scp` 用 `-P`，`sftp` 也是 `-P`，
只有 `ssh` 是小写 `-p`。

### 4. scp / sftp 会静默截断

跨境传镜像时，`scp` 报「成功」但远端只有 6.8MB（应该 32MB）；
`sftp` 同样（5MB 分片只到 3.4MB）。**报成功不等于传完**。

换 `rsync --partial --inplace` 后字节数完全一致。教训：
链路上任何工具都可能悄悄少传，**只有校验过字节数/sha256 才算数**。

### 5. 管理口令和 NapCat 凭据抢同一个头

NapCat 的 WebUI 凭据放在 `Authorization: Bearer <Credential>` 里。
如果管理服务也用 `Authorization` 做认证，代理转发时两个令牌会互相覆盖。

解法：管理口令走**自定义头** `X-Dafeiyu-Token`，`Authorization` 原样透传给 NapCat。
服务端两种头都认（`/proxy/` 之外的接口仍可用 `Authorization`）。

### 6. 并行传输反而更慢

12 路并行传分片时失败率极高（互相抢链路 + 每片的 ssh 校验自己也超时）。
串行 + rsync 续传反而稳定。另外**不要用 `ssh stat` 逐片校验**：
并行时它和 rsync 抢带宽，自己超时，把已经传好的片误判成失败。

### 7. `grep -c` 的退出码陷阱（把脱敏检查写坏了）

脱敏自检最初写成：

```bash
n=$(grep -ac "$pat" "$APK" || echo 0)
if [ "$n" != "0" ]; then echo "❌ 含 $pat"; fi
```

`grep -c` 在**没匹配到**时返回 0 **并且**退出码 1，于是 `|| echo 0` 又补了一行，
`n` 变成 `"0\n0"`，不等于 `"0"` → 16 个模式全部误报为「含敏感信息」。

正确写法：

```bash
if grep -qa "$pat" "$APK"; then echo "❌ 含 $pat"; fi
```

**教训：脱敏检查本身也会错，误报和漏报都要防。** 看到「全部命中」时先怀疑检查脚本。

## 四、做出来的东西

### 服务器侧：`mobile-controller/server/dafeiyu-manager.py`

一个只监听 `127.0.0.1:6199` 的管理服务（systemd 常驻）。

* **实例编排**：`create/start/stop/destroy`，每个实例 = 一套 napcat + astrbot 容器
  + 独立数据目录 + 独立端口（从 16000 起，每实例 3 个）。
* **端口自动分配**：实例名只允许 `[a-z0-9-]`（防路径穿越），端口从 meta 读，
  分配前再实测端口是否空闲。
* **固定 MAC**：QQ 把 MAC 算进设备指纹，随机 MAC 会让每次登录都被当成新设备
  （生产机踩过）。所以创建实例时就生成并固定。
* **三配置写入**：群号写裸号、私聊写 `<平台id>:FriendMessage:<QQ>`，
  主聊天 API 写 `provider_sources` + `provider`，人格写 **SQLite 的 personas 表**
  （见下面「人格到底存哪」）。写前备份、写后**回读校验**。
* **WebUI 反代**：`/proxy/<实例>/<路径>` 转发到该实例的 NapCat WebUI，
  这样 App 只需要一条隧道（服务器上那个受限账号也只放行了 6199）。
* **API Key 不回显**：`read_config` 只报告「有没有设」，不返回明文。

配置格式注意：AstrBot 的 `cmd_config.json` 是 **utf-8-sig（带 BOM）**，
按它的格式写（`write_json_bom`），否则它读不进去。

### 人格到底存哪（这一版最大的坑）

用户要求「人格提示词改写配置」，我一开始按最直觉的做法写进了
`cmd_config.json` 的 `persona` 字段。**这是错的，而且错得完全无声。**

翻 AstrBot 源码才发现（`core/config/default.py:306`）：

```python
"persona": [],  # deprecated
```

那个字段是**废弃的**。写进去 AstrBot 根本不读 —— 用户会以为人格设好了，
实际机器人还是老样子，**没有任何报错、没有任何提示**。这种错最难发现。

真实位置在 SQLite（`core/persona_mgr.py` 用 `db.get_persona_by_id` 取）：

```
data_v4.db → personas 表
  persona_id(唯一) / system_prompt / begin_dialogs(JSON)
  tools(JSON, NULL=用全部) / skills / custom_error_message
  folder_id(NULL=根目录) / sort_order / created_at / updated_at
```

再由 `provider_settings.default_personality` 指定当前用哪一条。

所以改成：写 `personas` 表（新实例的 persona_id 用 `dafeiyu-mine`）
+ 把 `default_personality` 指过去。

`tools` 字段写 `NULL`（= 用全部工具）是刻意的：用户只填了人格提示词，
没表达任何工具限制意图，不该替他收窄能力。

**验证方式**：光看文件写进去了不算数，要看 AstrBot 认没认。日志给出了铁证：

```
[core.persona_mgr:38] Loaded 0 personas.     ← 写入前
[core.persona_mgr:38] Loaded 1 personas.     ← 写入后
```

`0 → 1` 才说明人格真的生效了。

另外，写库的 SQL 用**生产库副本**验证过（`docker cp` 出来在副本上插入、
确认成功、清理、删除副本），确保字段和真实结构一致，全程没碰生产库。

### 主机指纹校验（防中间人）

`Tunnel.open()` 里在**建立转发之前**比对指纹，对不上立刻断开且一个字节都没转发。
指纹算法必须和 `ssh-keyscan | ssh-keygen -lf -` 一致：

```java
byte[] blob = Base64.getDecoder().decode(hk.getKey());  // getKey() 返回 base64 字符串
String b64 = Base64.getEncoder().encodeToString(sha256(blob));
```

实测与官方 `ssh-keygen -lf` 的输出逐字符一致（具体指纹值属真实基础设施信息，不写进仓库）。

一个刻意的设计：**空输入返回空串，而不是 `SHA256(空)`**。
后者是一个「合法的哈希」，调用方看到非空会以为校验有效，实际等于没校验。

## 六、镜像传输（基建）

湖北机到 Docker Hub 各镜像源只有 ~10KB/s（3.3GB 要 7 小时+），但到国内 CDN 有 4.9MB/s。
结论：**不能靠 Docker Hub 拉**。

做法：在海外生产机上 `docker save` 两个镜像（3.12GB）→ `zstd` 压缩到 1.05GB（压缩率 3.3 倍，
10 秒完成）→ 切成 216 个 5MB 分片 → rsync 串行传输（带 `--partial --inplace` 续传）
→ 湖北机合并后比 sha256 → `docker load`。

跨境单连接 0.05MB/s、8 路并行 0.40MB/s，瓶颈是**单连接限速**而非总带宽。

## 八、这一版新踩的坑

### 8. 路由顺序：`/instance/config` 被 `/instance/<名字>` 抢走

`GET /instance/config?name=qq1` 报 **「没有这个实例：config」**。

看着像「实例不存在」，实际是通用路由把 `"config"` 当成了实例名。
这种错误信息会把你往完全错的方向引 —— 你可能会去查实例为什么没了，
而真正的问题只是一行 `elif` 的顺序。

修法是把精确路由排在通配路由之前。并加了回归测试
（直接检查源码里两个 `find` 的先后位置），变异验证确认能抓。

### 9. `install` 同文件会中断整个脚本

重跑 `server-setup.sh` 时报：

```
install: '.../dafeiyu-manager.py' and '.../dafeiyu-manager.py' are the same file
```

在 `set -e` 下这直接中断脚本 —— 于是**后面的 systemd 注册全都不执行**。
而「重跑」正是这个脚本的正常用法（改完管理服务要重装）。
加了个 `[ "$SRC" = "$DST" ]` 分支绕开。

### 10. 一个「总是报警」的检查比没有检查更糟

`build-preset.sh` 的私钥自检写的是
`unzip -p "$OUT" classes.dex | grep -qa "BEGIN RSA PRIVATE KEY"`。
dex 在 zip 里是压缩的，这么取有时取不到，于是**每次都警告**「产物里没找到私钥」。

假警报的害处是会训练人忽略警告。改成在整个 APK 上 `grep -a`
（原始字节搜索）—— 实测准了。

### 11. 脱敏检查的例外不能只看「字符串在不在」

公开版 APK 里确实有 `BEGIN RSA PRIVATE KEY` 这个串，来自 JSch 的
`KeyPairRSA.class`（解析 PEM 私钥用的格式标记），不是泄露。

但如果例外就判「这串来自库里」→ 放行，那么**往公开版塞一段真实私钥也能蒙混过关**
（塞进去之后这串当然「来自库」）。实测确认了这个漏洞。

改成按**出现次数**判：JSch 只提供 1 个格式标记，所以公开版应恰好 1 次；
内部版内置真密钥 → 2 次。公开版 ≥2 次就拦。变异验证：塞真私钥 → 抓到了。

## 九、结论

用户要的四件事都做到了：

1. **只填三个配置** ✅ 群号/私聊 QQ、API 地址+Key+模型、人格提示词。
   服务器地址、SSH 端口、账号、密钥、口令全部内置，用户看不到也不用填。
2. **能多开** ✅ 实测两个 QQ 号各自一套容器同时在线，端口与 MAC 自动错开，
   凭据互相独立。
3. **不用 Tailscale** ✅ 改成 SSH 隧道，手机不需要装任何东西。
   （Tailscale 本身没关 —— 那是用户访问 DSH 控制台的唯一入口。）
4. **内部群能直接用** ✅ 内部版 APK 打开就能连。

安全边界（诚实说明）：内部版 APK 里内置了服务器连接信息，
**拿到 APK 的人就能管理服务器上的机器人实例**。所以只发给信得过的人。
服务器上那个账号被限制成「只能转发到 6199」，登不了 shell、连不了别的端口，
即使 APK 泄露，损失面也只到机器人管理。

## 追加：AstrBot 版本差异导致「配置成功但被静默抹掉」（2026-09-17 修复）

### 现象

`POST /instance/config` 返回 `{"ok": true, "verified": true}` 并列出三项改动，
但过一会儿 `GET /instance/config` 显示全空，AstrBot 日志里也只有
`Loaded 0 personas`。**没有任何报错**，用户会以为配置成功了。

### 根因（三层，逐层剥出来的）

**第一层：写完就重启，校验在重启之前。**
`apply_config` 的顺序是「写文件 → 回读校验 → 重启 astrbot」。
而 AstrBot 启动/退出时会把**内存里**的配置写回 `cmd_config.json`，
这次写回会把我们刚写的覆盖掉。校验发生在覆盖之前，所以报的是成功。

**第二层：AstrBot 4.28 删掉了两个配置键。**
| 键 | 4.27 | 4.28 |
|---|---|---|
| `provider_settings.default_provider_id` | 有 | **已删除** |
| `provider_settings.default_personality` | 有 | **已删除** |

`check_config_integrity()` 对 schema 里不认识的键是**直接删**：

```python
for key in list(conf.keys()):
    if key not in refer_conf:
        logger.info("Config key removed: %s", path_)
        has_new = True
```

所以写进去也会在启动时被抹掉，日志里只有一行 `Config key removed`。

**第三层：4.28 改用别的位置，且是「列表顺序」。**
`provider/manager.py:_resolve_using_provider()`：

```
先看 agent_runner.config.model.provider_id
  → 没有就取 provider_insts[0]   ← 列表第一个就是默认
```

`persona_mgr.py:resolve_selected_persona()`：

```
agent_runner.config.persona.persona_id
```

### 修法

1. **写之前等 AstrBot 完全启动**（`wait_astrbot_ready`），消掉时序窗口；
   这样用户不用知道任何时序细节，也不会看到「稍后再试」。
2. **重启之后再回读一次**，只有重启后仍在才算 `verified: true`；
   否则抛出可行动的提示（而不是静默成功）。
3. **主 provider 放在 `provider[]` 第一位** —— 列表顺序在 4.27/4.28 都有效。
4. **人格同时写两个位置**（4.27 的 `default_personality` + 4.28 的
   `agent_runner.config.persona.persona_id`），不认的那个会被当未知键删掉，无害。
5. `provider` / `provider_sources` 条目补齐 4.28 必需的字段：
   `enable` / `modalities` / `custom_extra_body` 等。少 `enable` 会直接
   `KeyError: 'enable'`，日志里只有 traceback，界面上完全看不出是缺字段。

### 验证（真实服务器，非模拟）

- 启动后 25 秒写入 → 等 90 秒 → 三项全部保住，`provider_ok: true`
- 再 `docker restart` 一次 → 仍然保住
- 多开：两个实例端口 `16000-16002` / `16003-16005`，MAC 不同，
  分别配 `deepseek-chat` 和 `kimi-k2`，互不干扰
- `Traceback` 数：0
- 测试：管理器 109 项（连跑 3 次）、JVM 321 项、字段检查 25 文件全过

### 教训

**「接口返回成功」不等于「状态真的生效」。** 凡是「写文件 → 通知另一个进程」
的链路，校验必须放在**通知之后**，因为那个进程可能在启动/退出时反向覆盖文件。
只校验「文件里现在是什么」会漏掉这一类 bug。
